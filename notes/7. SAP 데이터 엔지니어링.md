# Kinesis 계열 한 번에 구분

Kinesis는 스트리밍 데이터를 다루는 서비스 묶음이다.
시험에서는 특히 **Kinesis Data Streams와 Kinesis Data Firehose의 차이**를 자주 물어본다.

```text
Kinesis Data Streams = 실시간 스트림 수집/처리
Kinesis Data Firehose = 목적지로 근실시간 적재
Kinesis Data Analytics = 스트림 데이터 실시간 분석
```

| 서비스 | 한 줄 정의 | 시험 키워드 |
|---|---|---|
| Kinesis Data Streams, KDS | 대량 스트리밍 데이터를 낮은 지연 시간으로 수집하고 consumer가 직접 읽음 | shard, partition key, replay, 여러 consumer, 실시간 처리 |
| Kinesis Data Firehose | 데이터를 S3/Redshift/OpenSearch/Splunk/HTTP 등 목적지로 자동 적재 | 완전 관리형, 자동 스케일링, 근실시간, buffer, replay 없음 |
| Kinesis Data Analytics | 스트림 데이터를 SQL 또는 Flink로 실시간 분석 | moving average, anomaly detection, 실시간 집계 |

강의에서는 `Kinesis Streams`, `Kinesis Firehose`, `Kinesis Analytics`라고 부르기도 한다.
현재 AWS 네이밍에서는 `Kinesis Data Streams`, `Amazon Data Firehose`, `Amazon Managed Service for Apache Flink` 같은 이름이 같이 보일 수 있다.
시험에서는 문맥상 역할로 구분하면 된다.

## 전체 아키텍처 감각

```text
클릭스트림 / IoT / 로그 / 지표
→ Kinesis Data Streams
→ Kinesis Data Analytics, 선택
→ Kinesis Data Firehose
→ S3 / Redshift / OpenSearch / Splunk 등
```

- KDS는 스트림 데이터를 받아 보관하고 consumer가 읽게 한다.
- Analytics는 스트림 중간에서 실시간 계산을 한다.
- Firehose는 데이터를 최종 저장소나 분석 목적지로 밀어 넣는다.

# Kinesis Data Streams, KDS

KDS는 Kafka나 Redis Stream처럼 **이벤트를 시간순 로그처럼 쌓고 consumer가 읽는 서비스**에 가깝다.
SQS처럼 consumer가 읽었다고 메시지가 바로 삭제되는 큐가 아니다.

## 핵심 특징

```text
Producer → Kinesis Data Stream → Consumer
```

- stream은 여러 **shard**로 나뉜다.
- shard는 Kafka partition 같은 감각이다.
- record는 partition key를 기준으로 shard에 들어간다.
- 같은 shard 안에서는 record 순서가 유지된다.
- 데이터는 한 번 들어가면 수정/삭제하지 않는다.
- 보존 기간이 지나면 만료되어 사라진다.
- 기본 보존은 24시간, 최대 365일까지 연장 가능하다.
- 보존 기간 안에서는 replay, 재처리가 가능하다.
- 여러 consumer가 같은 stream을 동시에 읽을 수 있다.

SQS와 가장 큰 차이:

```text
SQS
→ consumer가 메시지를 처리하고 삭제
→ 보통 한 메시지는 한 consumer가 처리

Kinesis Data Streams
→ record가 보존 기간 동안 남음
→ 여러 consumer가 같은 데이터를 각자 읽을 수 있음
→ replay 가능
```

## Shard와 순서 보장

KDS의 순서 보장은 전체 stream 전체가 아니라 **shard 안의 순서**다.

```text
partition key = customerId
→ 같은 고객의 이벤트는 같은 shard로 감
→ 그 고객 이벤트의 순서가 유지됨
```

시험 감각:

```text
고객별 주문 순서 유지
대량 주문 이벤트 처리
partition key = customerId
→ Kinesis Data Streams
```

SQS FIFO도 `MessageGroupId = customerId`로 고객별 순서를 유지할 수 있다.
하지만 문제에서 `수만 개`, `streaming`, `여러 consumer`, `replay`, `real-time analytics` 느낌이 강하면 KDS가 더 자연스럽다.

## 용량 모드

| 모드 | 설명 | 시험 감각 |
|---|---|---|
| On-demand | 용량 계획 없이 AWS가 처리량에 맞게 자동 확장 | 운영 부담 최소화 |
| Provisioned | shard 수를 직접 관리 | 처리량 예측 가능, shard split/merge 고려 |

프로비저닝 모드에서는 처리량을 늘리려면 shard를 늘린다.
처리량을 줄이려면 shard를 병합한다.

```text
처리량 부족
→ ProvisionedThroughputException
→ shard 추가 또는 partition key 분산 확인
```

## Producer

| Producer | 언제 쓰는가 |
|---|---|
| AWS SDK | 단순하게 record를 직접 전송 |
| KPL, Kinesis Producer Library | batch, compression, retry가 필요할 때 |
| Kinesis Agent | EC2 로그 파일을 모니터링해서 KDS 또는 Firehose로 보낼 때 |

시험 감각:

```text
애플리케이션에서 직접 전송
→ SDK 또는 KPL

EC2 로그 파일을 수집해서 Kinesis로 전송
→ Kinesis Agent
```

## Consumer

| Consumer | 특징 |
|---|---|
| AWS SDK | 단순 consumer |
| Lambda event source mapping | KDS record를 Lambda로 처리 |
| KCL, Kinesis Client Library | 여러 worker가 shard를 나눠 읽고 checkpoint 관리 |

KCL은 진행 상황을 DynamoDB에 checkpoint로 저장한다.

```text
KCL app
→ KDS shard에서 읽음
→ 처리한 위치를 DynamoDB에 checkpoint
→ 여러 KCL worker가 병렬로 shard를 나눠 처리
```

시험 감각:

```text
Kinesis consumer를 여러 EC2/worker로 확장
checkpoint 필요
병렬 읽기 조율 필요
→ KCL + DynamoDB checkpoint
```

## 처리량 제한

Producer 쓰기 처리량:

```text
shard당 1MB/s 또는 1,000 records/s
```

Classic consumer 읽기 처리량:

```text
shard당 총 2MB/s
shard당 초당 최대 5 GetRecords API 호출
```

Enhanced fan-out consumer:

```text
consumer별 shard당 2MB/s
push 모델
API polling 부담 감소
지연 시간 감소
여러 consumer가 많을 때 유리
```

시험 감각:

```text
consumer가 많아서 서로 읽기 처리량을 나눠 먹는 문제가 있음
각 consumer에게 전용 처리량 필요
낮은 지연 시간 필요
→ Enhanced fan-out
```

# Kinesis Data Firehose

Firehose는 스트림 데이터를 직접 분석하는 서비스라기보다, 데이터를 목적지로 **자동 적재하는 배달 서비스**다.
KDS처럼 consumer 코드를 직접 작성해서 읽는 구조가 아니다.

```text
Producer / Kinesis Data Streams / CloudWatch Logs / IoT
→ Kinesis Data Firehose
→ 선택적 Lambda 변환
→ S3 / Redshift / OpenSearch / Splunk / HTTP endpoint
```

## Firehose 목적지

| 종류 | 목적지 |
|---|---|
| AWS 목적지 | S3, Redshift, OpenSearch |
| 파트너 목적지 | Splunk, Datadog, New Relic, MongoDB 등 |
| Custom 목적지 | HTTP endpoint |

Redshift로 보낼 때는 Firehose가 먼저 S3에 적재한 뒤, Redshift `COPY` 명령으로 로드한다.

```text
Firehose → S3 → Redshift COPY
```

## Firehose 특징

- 완전 관리형이다.
- 서버 관리가 없다.
- 자동 스케일링된다.
- 통과한 데이터량 기준으로 비용을 낸다.
- Lambda로 데이터 변환이 가능하다.
- 압축, 포맷 변환, 암호화 등을 지원한다.
- 실패한 record나 원본 record를 S3에 백업할 수 있다.
- 자체 데이터 저장소가 아니다.
- replay 기능이 없다.

시험 감각:

```text
코드 없이 S3/Redshift/OpenSearch/Splunk로 적재
운영 부담 최소화
근실시간 적재
자동 스케일링
→ Kinesis Data Firehose
```

## Firehose는 근실시간

Firehose는 record를 바로바로 한 건씩 목적지에 쓰는 것이 아니라, **버퍼링 후 batch로 flush**한다.

flush 조건:

```text
buffer size 도달
또는
buffer interval 도달
```

예:

```text
buffer size = 32MB
buffer interval = 60초

32MB가 먼저 차면 바로 flush
60초가 먼저 지나면 그때 flush
```

따라서 Firehose는 실시간이 아니라 **near real-time**이다.
시험에서 "실시간으로 즉시 S3에 써야 한다"는 뉘앙스면 Firehose보다 KDS consumer 또는 Lambda 처리를 고려한다.

```text
KDS에서 S3로 거의 즉시 처리해야 함
버퍼 지연이 허용되지 않음
→ Firehose 부적합, Lambda/consumer 직접 처리 고려
```

# Kinesis Data Analytics

Kinesis Data Analytics는 스트림 중간에서 **실시간 계산/분석**을 하는 서비스다.
시험에서는 깊은 구현보다 입력, 출력, 사용 사례만 잡으면 된다.

```text
Kinesis Data Streams 또는 Firehose
→ Kinesis Data Analytics
→ 출력 stream / error stream
```

## 입력과 출력

| 구분 | 내용 |
|---|---|
| 입력 스트림 | Kinesis Data Streams 또는 Firehose |
| 참조 데이터 | S3의 정적 reference table |
| 처리 방식 | SQL 또는 Apache Flink |
| 출력 | Kinesis Data Streams 또는 Firehose |
| 오류 출력 | error stream으로 분리 가능 |

참조 데이터는 동적으로 계속 흘러오는 스트림이 아니라, 비교나 조인에 쓰는 정적인 테이블 감각이다.

```text
입력 스트림: 주문 이벤트
참조 데이터: S3의 상품 정보 테이블
→ SQL/Flink로 실시간 집계/변환
→ 출력 스트림
```

출력 결과를 S3나 Redshift로 보내려면 보통 Firehose를 붙인다.

```text
Kinesis Data Analytics output
→ Kinesis Data Firehose
→ S3 / Redshift
```

## 사용 사례

```text
streaming ETL
실시간 집계
moving average
anomaly detection
실시간 leaderboard
특정 조건 필터링 후 알림
→ Kinesis Data Analytics
```

## 특징

- 서버리스다.
- 오토 스케일링된다.
- 사용한 리소스에 비례해서 과금된다.
- 입력/출력 스트림에 접근할 IAM role이 필요하다.
- 스키마 검색으로 입력 데이터의 컬럼과 타입을 파악할 수 있다.
- Lambda로 데이터를 사전 처리할 수 있다.

시험 감각:

```text
스트림 데이터를 저장하기 전에 실시간으로 계산/집계/변환
SQL이나 Flink로 streaming analytics
정적 참조 데이터와 조인
출력 stream과 error stream 필요
→ Kinesis Data Analytics
```

# Kinesis Data Streams vs Firehose

| 구분 | Kinesis Data Streams | Kinesis Data Firehose |
|---|---|---|
| 목적 | 스트림 수집 및 실시간 처리 | 목적지로 데이터 적재 |
| 처리 방식 | consumer 코드가 직접 읽음 | Firehose가 관리형으로 전달 |
| 지연 시간 | 매우 낮음, 실시간 처리 | 근실시간, buffer 후 전달 |
| 스케일링 | shard 관리 또는 on-demand | 자동 스케일링 |
| 데이터 보존 | 24시간 기본, 최대 365일 | 저장 없음 |
| replay | 가능 | 불가능 |
| 여러 consumer | 가능 | consumer 개념보다 delivery 목적 |
| 목적지 | consumer가 원하는 곳으로 처리 | S3, Redshift, OpenSearch, Splunk, HTTP 등 |
| 비용 감각 | shard/provisioned 또는 on-demand 처리량 | 통과 데이터량 |

## 시험에서 이렇게 고른다

```text
대량 이벤트를 낮은 지연 시간으로 처리
여러 consumer가 같은 stream을 읽음
record replay 필요
partition key로 순서 보장
custom consumer 코드 필요
→ Kinesis Data Streams
```

```text
S3/Redshift/OpenSearch/Splunk로 쉽게 적재
서버나 consumer 코드 관리 싫음
near real-time이면 충분
Lambda로 간단 변환 후 저장
replay 필요 없음
→ Kinesis Data Firehose
```

```text
스트림에서 이동 평균, 실시간 집계, 이상 탐지
SQL/Flink로 streaming analytics
→ Kinesis Data Analytics
```

# 한 줄 암기

```text
KDS = 스트림을 쌓고 consumer가 읽는다
Firehose = 스트림을 목적지로 배달한다
Analytics = 스트림을 실시간으로 분석한다
```

# Kinesis 기반 데이터 파이프라인 조합

Kinesis 계열은 단독으로도 쓰지만, 시험에서는 여러 서비스를 조합한 아키텍처로 자주 나온다.

```text
Producer
→ Kinesis Data Streams
→ Kinesis Data Analytics, 선택
→ Kinesis Data Streams 또는 Firehose
→ S3 / Redshift / OpenSearch 등
```

## Producer 선택

```text
애플리케이션이 직접 record 전송
→ SDK 또는 KPL

EC2 로그 파일 수집
→ Kinesis Agent

바로 목적지로 적재하고 싶음
→ Kinesis Data Firehose에 직접 전송 가능
```

KPL과 Kinesis Agent는 Kinesis Data Streams뿐 아니라 Firehose에도 직접 데이터를 보낼 수 있다.

## 처리 계층 선택

| 하고 싶은 일 | 선택 |
|---|---|
| 스트림을 직접 읽고 커스텀 처리 | EC2/ECS/Lambda consumer |
| 여러 worker가 shard를 나눠 읽고 checkpoint | KCL + DynamoDB |
| SQL/Flink로 실시간 집계/변환 | Kinesis Data Analytics |
| 목적지에 코드 없이 적재 | Kinesis Data Firehose |

## 장기 보관

KDS는 스트림 보존 서비스이지 장기 데이터 lake가 아니다.
보존 기간이 지나면 record는 사라진다.
장기 보관이 필요하면 보통 Firehose를 붙여 S3로 내보낸다.

```text
Kinesis Data Streams
→ Kinesis Data Firehose
→ S3
```

시험 감각:

```text
실시간 처리는 KDS
장기 보관은 S3
KDS에서 S3로 쉽게 적재는 Firehose
```

# 스트리밍/메시징/스토리지 선택 비교

비슷해 보여도 데이터 성격, 보존, 순서, 확장성, reader, 지연 시간이 다르다.

| 서비스 | 데이터 변경 | 보존 | 순서 | 확장성/처리량 | Reader/Consumer | 지연 시간 감각 |
|---|---|---|---|---|---|---|
| Kinesis Data Streams | immutable | 기본 24시간, 최대 365일 | shard 안에서 순서 | shard 또는 on-demand | EC2/Lambda/KCL/Firehose/Analytics | 낮음, 실시간 |
| Kinesis Data Firehose | 저장소 아님 | 자체 보존 없음 | 목적지 적재 중심 | 자동 스케일링 | 목적지로 delivery | 근실시간, buffer |
| SQS Standard | 메시지 자체는 변경하지 않음 | 최대 14일 | 순서 보장 없음 | 거의 무한 확장 | EC2/Lambda worker | 낮음 |
| SQS FIFO | 메시지 자체는 변경하지 않음 | 최대 14일 | MessageGroupId별 FIFO | Standard보다 제한, batch로 처리량 증가 | EC2/Lambda worker | 낮음 |
| SNS | 저장소 아님 | 보존 없음 | 순서 보장 없음 | fanout 확장 | HTTP/Lambda/SQS/Email 등 subscriber | 낮음 |
| DynamoDB | mutable | 사실상 무한, TTL 가능 | 기본 순서 없음 | WCU/RCU, on-demand, auto scaling | SDK, DynamoDB Streams는 Lambda/EC2 | 낮음 |
| S3 | object overwrite/versioning 가능 | 사실상 무한, lifecycle 가능 | 순서 없음 | prefix당 높은 요청 처리량 | SDK, S3 event notification | 낮음 |

## 비용 선택 감각

초당 1KB 메시지 3,000개처럼 순수 스트리밍 ingest가 많다면 Kinesis가 DynamoDB보다 비용 효율적일 수 있다.

```text
Kinesis Data Streams
→ shard 단위 비용
→ 스트리밍 수집에 적합

DynamoDB + DynamoDB Streams
→ WCU/스토리지 비용
→ 데이터를 테이블로 오래 저장하고 조회해야 할 때 적합
```

강의 예시 감각:

```text
초당 1KB 메시지 3,000개
→ KDS는 shard 3개 정도로 처리 가능
→ DynamoDB에 모두 쓰면 WCU 비용이 커질 수 있음
```

둘 다 작동할 수 있어도, SAP 시험에서는 **작동 여부가 아니라 더 적합하고 비용 효율적인 아키텍처**를 고르는 것이 중요하다.

## 서비스별 고르는 기준

### Kinesis Data Streams

```text
대량 실시간 스트림 ingest
여러 consumer
replay 필요
partition key 기준 순서
custom processing
→ KDS
```

### Kinesis Data Firehose

```text
S3/Redshift/OpenSearch/Splunk로 쉽게 적재
consumer 코드 관리 싫음
near real-time 허용
replay 불필요
→ Firehose
```

### SQS Standard

```text
작업 queue
순서 중요하지 않음
worker가 꺼내 처리 후 삭제
retry/DLQ/visibility timeout
→ SQS Standard
```

### SQS FIFO

```text
작업 queue인데 순서가 중요
MessageGroupId별 순서 유지
중복 제거 필요
→ SQS FIFO
```

### SNS

```text
하나의 이벤트를 여러 subscriber에게 fanout
알림, push, pub/sub
SQS 여러 개로 이벤트 복제
→ SNS
```

### DynamoDB

```text
스트림이 아니라 실제 애플리케이션 데이터 저장/조회
키 기반 빠른 조회
mutable 데이터
TTL 필요
DynamoDB Streams로 변경 이벤트 처리
→ DynamoDB
```

### S3

```text
장기 저장
데이터 lake
객체 단위 보관
lifecycle로 IA/Glacier 이동
S3 event로 후속 처리
→ S3
```

# Amazon EMR

EMR은 **Elastic MapReduce**의 약자다.
쉽게 말하면 AWS에서 Hadoop/Spark 같은 빅데이터 처리 클러스터를 빠르게 띄워 주는 관리형 서비스다.

```text
온프레미스 Hadoop/Spark 클러스터
→ AWS에서 필요할 때만 EMR 클러스터로 실행
→ 작업 끝나면 클러스터 종료
→ 비용 절감
```

## EMR이 와닿는 비유

EMR은 데이터 저장소라기보다 **대규모 데이터 처리 공장**에 가깝다.

```text
S3 = 원재료와 결과물을 오래 보관하는 창고
EMR = 필요할 때 켜서 데이터를 가공하는 공장
EC2 = 공장 안에서 일하는 기계들
Spark/Hive/Presto/Flink = 공장에서 돌리는 처리 엔진
```

예를 들어 S3에 로그가 100TB 쌓여 있다고 하자.
이걸 일반 서버 한 대로 처리하면 너무 오래 걸린다.
EMR은 EC2 인스턴스 수십~수백 대로 클러스터를 만들고, Spark나 Hive 작업을 병렬로 실행해서 빠르게 처리한다.
작업이 끝나면 클러스터를 꺼서 비용을 줄인다.

## 언제 EMR을 쓰는가

```text
대용량 배치 처리
온프레미스 Hadoop/Spark 마이그레이션
로그 분석
웹 인덱싱
머신러닝 전처리
대규모 ETL
Hive / Spark / Presto / Flink / HBase 사용
→ EMR
```

시험 감각:

```text
기존 Hadoop 생태계 사용
수백 대 EC2로 빅데이터 처리
작업이 끝나면 클러스터 종료해서 비용 절감
→ EMR
```

## EMR 클러스터 구조

EMR 클러스터는 여러 EC2 인스턴스로 구성된다.
노드는 역할에 따라 나뉜다.

| 노드 | 역할 | 비용 전략 |
|---|---|---|
| Master node | 클러스터 관리, 작업 조율, 상태 관리 | 중단되면 곤란하므로 On-Demand 또는 Reserved |
| Core node | 작업 실행 + HDFS 데이터 저장 | 장시간 실행, On-Demand 또는 Reserved 적합 |
| Task node | 작업 실행만 담당, 데이터 저장 안 함 | 선택 사항, Spot 사용 후보 |

감각적으로:

```text
Master = 현장 관리자
Core = 일도 하고 임시 데이터도 들고 있는 작업자
Task = 계산만 도와주는 임시 알바
```

Task node는 중간에 사라져도 HDFS 데이터를 잃는 구조가 아니므로 Spot 인스턴스를 붙이기 좋다.
반대로 Master/Core는 클러스터 안정성과 데이터 저장에 중요하므로 더 안정적인 구매 옵션을 쓴다.

## EMR 스토리지: HDFS vs EMRFS/S3

EMR에서 헷갈리기 쉬운 부분이 스토리지다.

| 스토리지 | 위치 | 성격 | 언제 쓰는가 |
|---|---|---|---|
| HDFS | EMR 클러스터 EC2/EBS 위 | 빠른 임시 분산 파일시스템 | 작업 중간 데이터, 임시 처리 |
| EMRFS + S3 | S3 | 영구적이고 내구성 높은 저장소 | 원본 데이터, 최종 결과, 장기 보관 |

HDFS는 클러스터 안에 있다.
클러스터를 종료하거나 AZ 장애가 나면 데이터 손실 위험이 있다.
그래서 오래 보관할 데이터는 HDFS가 아니라 S3에 둔다.

```text
빠른 임시 처리
→ HDFS / EBS

장기 보관, 높은 내구성, multi-AZ 성격
→ S3 / EMRFS
```

EMRFS는 EMR이 S3를 Hadoop 파일시스템처럼 읽고 쓸 수 있게 해주는 연결 계층이라고 보면 된다.

```text
Spark/Hive 작업
→ EMRFS를 통해 S3 데이터 읽기
→ 처리
→ 결과를 다시 S3에 저장
```

시험 감각:

```text
EMR 클러스터는 계산용
영구 데이터는 S3
HDFS/EBS는 임시 작업용
```

## 네트워크와 배치

EMR은 VPC 안에서 실행된다.
시험 맥락에서는 보통 클러스터가 같은 AZ/서브넷 안에서 배치된다고 생각하면 된다.
이렇게 하면 노드 간 네트워크 지연이 낮고 비용도 줄어든다.

주의:

```text
같은 AZ 안의 HDFS/EBS
→ 빠르지만 AZ 장애에 취약

S3
→ 더 내구성 높고 장기 보관에 적합
```

## EMR과 다른 AWS 서비스 통합

EMR은 S3와 가장 자주 엮인다.

```text
S3 원본 데이터
→ EMR Spark/Hive 처리
→ S3 결과 저장
```

또한 Hive를 사용해 DynamoDB 테이블을 읽고 분석할 수도 있다.

```text
EMR + Hive
→ DynamoDB 테이블 분석
```

즉 DynamoDB 운영 데이터를 직접 대량 분석해야 하는 경우, EMR/Hive 연동이 선택지로 나올 수 있다.

## 비용 최적화

EMR은 EC2 인스턴스 비용이 핵심이다.
따라서 노드 역할에 따라 구매 옵션을 다르게 가져간다.

| 구매 옵션 | 특징 | EMR에서 어울리는 곳 |
|---|---|---|
| On-Demand | 안정적, 중단 없음 | Master/Core |
| Reserved | 장기 실행 시 할인 | 오래 켜둘 Master/Core |
| Spot | 싸지만 중단 가능 | Task node |

시험 감각:

```text
장시간 실행되는 클러스터
→ Master/Core는 Reserved 고려

일시적인 분석 작업
→ 작업 끝나면 클러스터 종료

비용 절감
→ Task node에 Spot 사용
```

## Instance Group vs Instance Fleet

EMR에서 인스턴스를 구성하는 방식은 크게 두 가지로 볼 수 있다.

| 구성 방식 | 설명 | 감각 |
|---|---|---|
| Uniform Instance Group | 노드 그룹마다 인스턴스 타입과 구매 옵션을 정함 | 단순하고 예측 가능, Auto Scaling 사용 가능 |
| Instance Fleet | 여러 인스턴스 타입과 On-Demand/Spot 조합, 목표 용량 기반 | 유연하게 용량 확보, Spot 활용에 유리 |

Uniform Instance Group 예:

```text
Master: m5.xlarge On-Demand
Core: r5.xlarge On-Demand
Task: c5.xlarge Spot
```

Instance Fleet 예:

```text
Core fleet:
  On-Demand 6 capacity
  Spot 10 capacity
  여러 인스턴스 타입 후보 지정

EMR이 가능한 조합으로 클러스터 구성
```

시험에서 깊은 설정값까지 외우기보다는:

```text
단순한 고정 구성
→ Instance Group

여러 타입/구매 옵션을 섞어 유연하게 용량 확보
→ Instance Fleet
```

## EMR이 답인 경우

```text
Hadoop/Spark/Hive/Presto/Flink 기반 빅데이터 처리
온프레미스 Hadoop 클러스터를 AWS로 이전
수백 대 EC2로 병렬 처리
작업 완료 후 클러스터 종료
S3 데이터를 대규모로 ETL/분석
→ EMR
```

반대로:

```text
서버리스 SQL로 S3 데이터 바로 조회
→ Athena

완전 관리형 ETL, Spark 작업이지만 서버 관리 최소화
→ AWS Glue

실시간 스트리밍 수집/처리
→ Kinesis Data Streams / Analytics

목적지로 근실시간 적재
→ Firehose
```

## 한 줄 암기

```text
EMR = Hadoop/Spark 빅데이터 클러스터를 AWS에서 필요할 때 빌려 쓰는 서비스
HDFS = 빠른 임시 작업장
S3/EMRFS = 오래 보관하는 창고
Master/Core = 안정적으로
Task = Spot으로 싸게
```

# Amazon MSK, Managed Streaming for Apache Kafka

MSK는 **AWS가 관리해 주는 Apache Kafka 클러스터**다.
Kafka를 직접 EC2에 설치하고 운영하는 대신, AWS가 브로커 생성, 업데이트, 복구, 멀티 AZ 배치 같은 운영 부담을 줄여준다.

```text
Apache Kafka를 직접 운영하기 어려움
기존 Kafka 애플리케이션/프로토콜을 유지하고 싶음
Kafka ecosystem을 그대로 쓰고 싶음
→ Amazon MSK
```

## Kafka가 하는 일

Kafka는 Kinesis Data Streams처럼 스트리밍 데이터를 topic에 쌓고 consumer가 읽는 구조다.

```text
Producer
→ Kafka Topic
→ Consumer
```

감각적으로:

```text
Kinesis Data Streams = AWS 네이티브 스트림
Amazon MSK = AWS 관리형 Kafka
```

Kafka topic은 여러 partition으로 나뉘고, consumer는 topic에서 데이터를 읽어 원하는 곳으로 처리한다.

예:

```text
Producer
→ MSK Topic
→ Consumer
→ EMR / S3 / SageMaker / Kinesis / RDS 등
```

## MSK가 관리해 주는 것

- Kafka broker node 생성/관리
- ZooKeeper node 관리, 또는 Kafka 버전에 따라 관리형 메타데이터 구성
- 멀티 AZ 배치
- 일반적인 Kafka 장애 자동 복구
- EBS 기반 데이터 저장
- 클러스터 생성, 업데이트, 삭제

시험 감각:

```text
Kafka는 쓰고 싶지만 직접 운영은 싫다
→ Amazon MSK
```

## MSK Serverless

MSK Serverless는 broker 용량을 직접 프로비저닝하지 않는 Kafka 옵션이다.
MSK가 자동으로 compute와 storage를 확장한다.

```text
Kafka 호환성 필요
broker 용량 관리 부담 줄이고 싶음
→ MSK Serverless
```

## Kinesis Data Streams vs Amazon MSK

둘 다 스트리밍 데이터 처리 서비스지만 운영 모델과 생태계가 다르다.

| 구분 | Kinesis Data Streams | Amazon MSK |
|---|---|---|
| 성격 | AWS 네이티브 스트림 | 관리형 Apache Kafka |
| 데이터 단위 | Stream + Shard | Topic + Partition |
| 메시지 크기 | record 크기 제한이 더 엄격함 | Kafka 설정으로 더 크게 조정 가능 |
| 확장 | shard split/merge | partition 추가 가능, 보통 제거는 어려움 |
| 보존 | 기본 24시간, 최대 365일 | EBS 스토리지 비용을 내며 더 길게 보존 가능 |
| 암호화 | 전송 중/저장 시 암호화 지원 | TLS 또는 plaintext 전송, 저장 시 암호화 지원 |
| 운영 감각 | AWS 서비스에 더 밀착 | Kafka 생태계/기존 앱 호환 |

시험에서 중요한 감각:

```text
AWS 네이티브로 스트림 처리
샤드, KCL, Lambda event source, Firehose 연계
→ Kinesis Data Streams

기존 Kafka 클라이언트/프로토콜/토픽/파티션 유지
Kafka ecosystem 필요
온프레미스 Kafka를 AWS로 옮김
→ Amazon MSK
```

## MSK Producer와 Consumer

MSK에 데이터를 넣으려면 Kafka producer를 사용한다.
읽을 때는 Kafka consumer를 사용하거나 AWS 서비스와 연동할 수 있다.

| 역할 | 선택지 |
|---|---|
| Producer | Kafka producer app |
| Consumer | Kafka consumer app on EC2/ECS/EKS |
| Serverless 처리 | Lambda event source mapping |
| Streaming analytics | Kinesis Data Analytics for Apache Flink |
| ETL | AWS Glue Streaming ETL |

예:

```text
MSK Topic
→ Lambda
→ 이벤트 처리
```

```text
MSK Topic
→ Kinesis Data Analytics for Apache Flink
→ 실시간 분석
```

```text
MSK Topic
→ AWS Glue Streaming ETL
→ S3/Data Lake 적재
```

## MSK가 답인 경우

```text
Kafka 기반 애플리케이션을 AWS로 이전
Kafka producer/consumer 코드를 유지
topic/partition 기반 스트리밍 필요
Kafka 생태계 도구 사용
직접 Kafka/ZooKeeper 운영 부담을 줄이고 싶음
→ Amazon MSK
```

반대로:

```text
AWS 네이티브 스트림이 필요하고 Kafka 호환성이 중요하지 않음
→ Kinesis Data Streams

코드 없이 S3/Redshift/OpenSearch/Splunk로 적재
→ Kinesis Data Firehose

스트림을 SQL/Flink로 실시간 분석
→ Kinesis Data Analytics
```

## 한 줄 암기

```text
MSK = AWS가 관리해 주는 Kafka
KDS = AWS 네이티브 Kafka 비슷한 스트림
Kafka 호환성/기존 Kafka 이전이면 MSK
AWS 네이티브 연동 중심이면 KDS
```

# AWS에서 작업 실행 방법 고르기

AWS에서 주기 작업, 이벤트 반응 작업, 장기 실행 작업을 돌리는 방법은 여러 가지다.
시험에서는 “그냥 EC2에 cron”보다 **서버리스/관리형/확장 가능한 방식**을 선호한다.

## 선택지 한눈에 보기

| 방식 | 언제 쓰는가 | 시험 감각 |
|---|---|---|
| EC2 + cron | 단순하지만 직접 서버 관리 | HA/확장성 약함, 추천 답안으로는 조심 |
| EventBridge Scheduler/Rule + Lambda | 짧은 주기 작업, 서버리스 cron | 가장 서버리스한 기본 선택 |
| AWS 이벤트 + Lambda | S3/SQS/SNS/API Gateway 등 이벤트에 즉시 반응 | 이벤트 기반 워크플로 |
| EventBridge + AWS Batch | 오래 걸리는 배치/컨테이너 작업 | 장기 실행, 대규모 batch |
| EventBridge + ECS/Fargate task | 비교적 단순한 컨테이너 작업 | Batch보다 단순한 컨테이너 실행 |
| EMR | 아주 큰 빅데이터/Hadoop/Spark 작업 | 클러스터 기반 대규모 처리 |

## EC2 + cron

가장 전통적인 방식이다.

```text
EC2 인스턴스
→ cron
→ 주기 작업 실행
```

하지만 솔루션 아키텍트 시험에서는 보통 좋은 답이 아니다.

문제점:

- EC2 인스턴스를 직접 관리해야 한다.
- 인스턴스가 죽으면 cron도 멈춘다.
- 기본적으로 고가용성이 아니다.
- 자동 확장성이 없다.
- 패치, 모니터링, 장애 복구를 직접 챙겨야 한다.

시험 감각:

```text
cron이 익숙하다고 EC2 한 대에 올리는 방식
→ 단순하지만 HA/확장성 부족
→ 서버리스 대안이 있으면 보통 그쪽이 더 좋음
```

## EventBridge + Lambda

서버리스 cron의 대표 조합이다.

```text
EventBridge schedule rule
→ Lambda
→ 작업 실행
```

좋은 점:

- 서버 관리가 없다.
- 주기 실행이 쉽다.
- 고가용성/확장성은 AWS가 관리한다.
- 짧은 작업에 적합하다.

주의:

- Lambda timeout 제한이 있다.
- 긴 작업이나 무거운 컨테이너 작업에는 부적합할 수 있다.

시험 감각:

```text
매일/매시간/몇 분마다 짧은 작업 실행
서버리스 cron
→ EventBridge + Lambda
```

## 이벤트 기반 Lambda 워크플로

시간 기반이 아니라 AWS 리소스에서 이벤트가 발생했을 때 Lambda를 실행하는 방식이다.

예:

```text
S3 object 생성
→ Lambda 실행

API Gateway 요청
→ Lambda 실행

SQS message 도착
→ Lambda event source mapping

SNS publish
→ Lambda 구독자 호출

EventBridge event
→ Lambda target 호출
```

이 방식은 “무언가 발생하면 즉시 반응”하는 구조다.

시험 감각:

```text
AWS 서비스 이벤트에 반응
객체 업로드, 메시지 도착, API 호출, 운영 이벤트
→ Lambda 기반 이벤트 처리
```

## EventBridge + AWS Batch

오래 걸리는 배치 작업이나 컨테이너 기반 작업은 Lambda보다 Batch가 어울린다.

```text
EventBridge schedule
→ AWS Batch job
→ 컨테이너 작업 실행
```

AWS Batch는 작업 큐, 컴퓨팅 환경, 재시도, 의존성, 대규모 병렬 실행 같은 배치 기능을 제공한다.

시험 감각:

```text
몇 시간 걸리는 작업
컨테이너 배치 처리
대규모 병렬 job
Lambda timeout을 넘는 작업
→ AWS Batch
```

## EventBridge + ECS/Fargate task

Batch까지는 필요 없고, 단순히 컨테이너 하나를 주기적으로 실행하고 싶다면 Fargate task를 EventBridge 대상으로 실행할 수 있다.

```text
EventBridge schedule
→ ECS RunTask
→ Fargate task 실행
```

감각:

```text
컨테이너를 서버리스로 한 번 실행
Batch의 복잡한 기능까지는 필요 없음
→ EventBridge + Fargate
```

Batch와 비교:

| 구분 | AWS Batch | ECS/Fargate task |
|---|---|---|
| 성격 | 배치 작업 관리 서비스 | 컨테이너 실행 방식 |
| 기능 | job queue, retry, dependency, 대규모 병렬 처리 | 단순 컨테이너 실행 |
| 적합 | 복잡한/대규모/장기 batch | 단순 scheduled container |

## EMR

아주 큰 빅데이터 작업, Hadoop/Spark/Flink/Hive 클러스터 작업이면 EMR을 본다.

```text
대규모 로그/데이터 처리
Hadoop/Spark 클러스터 필요
작업 완료 후 클러스터 종료
→ EMR
```

Lambda, Batch, Fargate가 일반 작업 실행이라면 EMR은 빅데이터 클러스터 처리에 가깝다.

## 시험 선택 기준

```text
짧은 주기 작업
→ EventBridge + Lambda

AWS 이벤트에 반응
→ Lambda event source / EventBridge / S3 event

긴 컨테이너 배치 작업
→ AWS Batch

단순 scheduled container
→ EventBridge + ECS/Fargate task

Hadoop/Spark 빅데이터 클러스터
→ EMR

EC2 한 대 cron
→ 가능은 하지만 HA/확장성 부족, 시험 답으로는 신중
```

## 한 줄 암기

```text
짧고 서버리스 → EventBridge + Lambda
길고 배치성 → AWS Batch
단순 컨테이너 → Fargate task
빅데이터 클러스터 → EMR
EC2 cron → 최후의 단순 선택, 시험에서는 비추
```

# AWS Batch

AWS Batch는 **Docker 컨테이너로 만든 배치 작업을 대규모로 실행하는 서비스**다.
직접 EC2에 작업 스케줄러를 만들지 않고, Batch가 작업 큐와 실행 환경을 관리해 준다.

```text
Docker image
→ AWS Batch job
→ Fargate 또는 EC2/Spot에서 실행
```

감각적으로:

```text
Lambda = 짧은 함수 실행
Fargate task = 컨테이너 하나를 단순 실행
AWS Batch = 많은 컨테이너 작업을 큐에 넣고 대규모로 처리
```

## Batch가 하는 일

AWS Batch는 작업 자체를 실행하는 서비스라기보다, 작업을 어디서 어떻게 실행할지 관리하는 계층이다.

주요 구성:

| 구성 요소 | 의미 |
|---|---|
| Job | 실행할 배치 작업 |
| Job Queue | 제출된 작업이 대기하는 큐 |
| Job Definition | Docker image, vCPU, memory, IAM role 같은 실행 정의 |
| Compute Environment | 작업을 실행할 Fargate 또는 EC2/Spot 환경 |

흐름:

```text
SubmitJob API
→ Job Queue
→ Compute Environment가 용량 확보
→ Docker image pull, 보통 ECR
→ 컨테이너 실행
→ 작업 완료
```

## 실행 환경: Fargate vs EC2/Spot

AWS Batch 작업은 크게 두 방식으로 실행할 수 있다.

| 실행 방식 | 특징 | 언제 쓰는가 |
|---|---|---|
| Fargate | 서버리스, EC2 관리 없음 | 운영 부담 최소화, 일반 컨테이너 배치 |
| EC2/Spot | VPC 안에 EC2 인스턴스를 동적으로 프로비저닝 | 비용 최적화, 더 세밀한 제어, 대규모 작업 |

시험 감각:

```text
서버 관리 없이 배치 컨테이너 실행
→ AWS Batch on Fargate

비용 절감, Spot 활용, 인스턴스 타입 제어
→ AWS Batch managed EC2 compute environment
```

기본 리소스 비용은 Fargate 또는 EC2/Spot 사용량 기준으로 낸다.

## S3 이벤트로 Batch 작업 실행

예: S3에 이미지가 업로드되면 썸네일 생성 배치 작업을 실행한다.

방법 1:

```text
S3 Event Notification
→ Lambda
→ AWS SDK로 SubmitJob 호출
→ AWS Batch job 실행
```

방법 2:

```text
S3 Event
→ EventBridge
→ AWS Batch target
→ Batch job 실행
```

EventBridge를 쓰면 필터링이 강하고, 중간 Lambda 코드를 줄일 수 있다.

시험 감각:

```text
S3 업로드 이벤트로 Batch 실행
코드 최소화, 이벤트 필터링
→ S3 EventBridge integration + AWS Batch
```

## Batch job 안에서 필요한 권한

Batch job은 Docker 컨테이너로 실행된다.
컨테이너가 S3에서 파일을 읽고, 결과를 S3에 쓰고, DynamoDB에 메타데이터를 저장하려면 IAM role이 필요하다.

예:

```text
Batch job
→ S3 원본 이미지 GetObject
→ 이미지 처리
→ S3 결과 PutObject
→ DynamoDB 메타데이터 PutItem
```

시험 감각:

```text
Batch 컨테이너가 AWS API를 호출해야 함
→ Job role / IAM role 권한 확인
```

## Lambda vs AWS Batch

| 구분 | Lambda | AWS Batch |
|---|---|---|
| 실행 시간 | timeout 제한 있음 | 장시간 작업 가능 |
| 런타임 | Lambda runtime 또는 Lambda용 컨테이너 이미지 | Docker image면 비교적 자유로움 |
| 디스크 | 임시 스토리지 제한 | EC2/EBS/Instance store 또는 Fargate 자원 사용 |
| 적합 | 짧은 이벤트 처리 | 긴 배치, 대규모 병렬 작업 |
| 운영 | 완전 서버리스 | Batch가 Fargate/EC2 환경 관리 |

시험 감각:

```text
짧고 이벤트성
→ Lambda

오래 걸림, 대량 병렬 처리, 임의 Docker image 필요
→ AWS Batch
```

## Managed Compute Environment

관리형 컴퓨팅 환경에서는 AWS Batch가 용량과 인스턴스 유형을 관리한다.
사용자는 최소/최대 vCPU, 인스턴스 타입 후보, On-Demand/Spot 여부를 지정한다.

```text
Job Queue에 작업 증가
→ Batch가 필요 vCPU 계산
→ EC2/Spot 인스턴스 자동 프로비저닝
→ 작업 감소
→ 인스턴스 축소
```

중요 포인트:

- On-Demand 또는 Spot을 선택할 수 있다.
- Spot 최대 가격을 설정할 수 있다.
- 인스턴스는 사용자의 VPC 안에서 시작된다.
- 프라이빗 서브넷에서 실행하면 ECS/ECR 등 AWS 서비스 접근 경로가 필요하다.

프라이빗 서브넷 주의:

```text
Batch EC2 인스턴스가 프라이빗 서브넷에 있음
→ ECS/ECR/CloudWatch Logs 등에 접근 필요
→ NAT Gateway 또는 VPC Endpoint 고려
```

시험 감각:

```text
Batch 인스턴스가 private subnet에서 AWS 서비스에 접근 못 함
→ NAT Gateway 또는 VPC Endpoint
```

## Unmanaged Compute Environment

비관리형 컴퓨팅 환경에서는 인스턴스 구성, 프로비저닝, 스케일링을 직접 관리한다.
제어권은 더 크지만 운영 책임도 커진다.

```text
운영 부담 줄이고 싶음
→ Managed compute environment

인스턴스 구성을 직접 통제해야 함
→ Unmanaged compute environment
```

시험에서는 대부분 관리형 컴퓨팅 환경이 더 자연스럽다.

## vCPU 기반 스케일링 감각

Batch는 “몇 대의 인스턴스”보다 **컴퓨팅 환경의 vCPU 용량**을 기준으로 생각한다.

예:

```text
min vCPU = 0
max vCPU = 256
instance type 후보 = m5.large, c5.xlarge, r5.2xlarge
```

작업 큐에 작업이 쌓이면 Batch가 필요한 vCPU를 보고 적절한 인스턴스를 띄운다.
작업이 줄면 인스턴스를 줄인다.

## Multi-node Parallel Job

일반 Batch job은 보통 하나의 컨테이너/노드에서 실행된다.
하지만 HPC처럼 여러 노드가 동시에 협력해야 하는 작업은 **multi-node parallel job**을 사용할 수 있다.

```text
하나의 Batch job
→ main node 1개
→ child node 여러 개
→ 여러 EC2 인스턴스가 동시에 작업
```

사용 사례:

```text
HPC
긴밀하게 결합된 병렬 계산
여러 인스턴스 간 빠른 네트워크 통신 필요
```

중요 시험 포인트:

- multi-node parallel job은 Spot 인스턴스와 호환되지 않는다.
- EC2 기반으로 실행한다.
- Cluster placement group을 사용하면 네트워크 성능에 유리하다.
- 같은 AZ 안에서 인스턴스를 가깝게 배치해 낮은 지연 시간을 노린다.

시험 감각:

```text
HPC, 여러 EC2 노드가 동시에 협력
Spot 사용 불가
네트워크 성능 중요
→ AWS Batch multi-node parallel job + cluster placement group
```

## AWS Batch가 답인 경우

```text
Docker image로 배치 작업 실행
Lambda timeout을 넘는 작업
수천 개 작업을 병렬 실행
EventBridge로 예약 실행
Step Functions로 작업 조정
S3 이벤트 이후 대량 처리
Spot으로 비용 최적화
HPC multi-node job
→ AWS Batch
```

반대로:

```text
짧은 이벤트 처리
→ Lambda

단순 컨테이너 한 번 실행
→ ECS/Fargate task

Hadoop/Spark 빅데이터 클러스터
→ EMR
```

## 한 줄 암기

```text
AWS Batch = Docker 배치 작업을 큐에 넣고 Fargate/EC2/Spot에서 대규모로 실행
Lambda보다 오래 돌 수 있고, 컨테이너 자유도가 높다
Managed compute environment = Batch가 용량 관리
Multi-node job = HPC용, Spot 불가, cluster placement group 유리
```
