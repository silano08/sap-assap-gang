# SAP 마이그레이션

# Cloud Migration Strategy, 7R

마이그레이션 전략은 시험에서 "어떤 방식으로 옮길 것인가"를 고르는 문제로 나온다.
이름은 7R이지만, 실제 문제에서는 문장 힌트를 보고 매칭하는 감각이 중요하다.

| 전략 | 의미 | 시험 힌트 |
| --- | --- | --- |
| Retire | 안 쓰는 애플리케이션 폐기 | 사용률 낮음, 제거해 비용 절감 |
| Retain | 당장 옮기지 않고 유지 | 규정/의존성/일정 때문에 보류 |
| Rehost | 거의 그대로 lift-and-shift | 빠른 이전, 코드 변경 최소 |
| Replatform | 약간 수정해서 관리형 플랫폼으로 이동 | DB를 RDS로, 컨테이너를 ECS로 |
| Repurchase | SaaS 제품으로 교체 | 기존 CRM을 Salesforce 같은 SaaS로 |
| Refactor / Re-architect | 아키텍처를 클라우드 네이티브로 재설계 | 마이크로서비스, 서버리스, 큰 변경 |
| Relocate | VMware 같은 플랫폼을 통째로 이동 | VMware Cloud on AWS |

시험 감각:

```text
최소 변경으로 빠르게 이전
→ Rehost

운영 부담을 줄이기 위해 RDS/ECS 같은 관리형으로 약간 변경
→ Replatform

애플리케이션을 새로 설계해서 클라우드 네이티브화
→ Refactor / Re-architect

상용 SaaS로 갈아탐
→ Repurchase
```

# Storage Gateway

Storage Gateway는 온프레미스 환경과 AWS 스토리지를 연결하는 하이브리드 스토리지 서비스다.
핵심은 온프레미스 애플리케이션은 기존 프로토콜로 접근하고, 데이터는 AWS 스토리지에 저장/연동된다는 점이다.

```text
On-premises application
→ Storage Gateway appliance
→ AWS Storage
```

## File Gateway

File Gateway는 NFS/SMB 파일 인터페이스를 제공하고, 뒤에서는 S3에 객체로 저장한다.

시험 감각:

```text
온프레미스에서 파일 공유처럼 쓰고 싶다
데이터는 S3에 객체로 저장하고 싶다
NFS/SMB로 접근해야 한다
→ S3 File Gateway
```

FSx File Gateway는 온프레미스에서 Amazon FSx for Windows File Server에 접근할 때 쓴다.
Windows 파일 공유/SMB/AD 통합 쪽 힌트가 나오면 FSx File Gateway를 본다.

## Volume Gateway

Volume Gateway는 iSCSI 블록 스토리지 인터페이스를 제공한다.

```text
Cached Volume
→ 주요 데이터는 S3에 있고, 자주 쓰는 데이터만 온프레미스 캐시

Stored Volume
→ 전체 데이터는 온프레미스에 있고, AWS에는 스냅샷 백업
```

시험 감각:

```text
온프레미스 앱이 블록 스토리지/iSCSI를 원한다
AWS에 백업 또는 클라우드 기반 확장성을 붙이고 싶다
→ Volume Gateway
```

## Tape Gateway

Tape Gateway는 물리 테이프 백업을 가상 테이프로 대체한다.

```text
기존 백업 소프트웨어가 tape library를 기대한다
물리 테이프 대신 S3/Glacier로 백업하고 싶다
→ Tape Gateway
```

시험 감각:

```text
NFS/SMB 파일
→ File Gateway

iSCSI block volume
→ Volume Gateway

가상 테이프 백업
→ Tape Gateway
```

# Snow Family

Snow Family는 네트워크로 전송하기 어려운 대용량 데이터를 물리 장비로 옮기거나, 엣지에서 컴퓨팅할 때 쓴다.

```text
네트워크 대역폭이 부족함
수십 TB~PB 데이터를 AWS로 옮겨야 함
인터넷 연결이 불안정한 현장/공장/선박/원격지에서 처리 필요
→ Snow Family
```

대표 장비 감각:

| 장비 | 감각 |
| --- | --- |
| Snowcone | 가장 작음, 휴대성, 엣지/소규모 데이터 |
| Snowball Edge Storage Optimized | 대용량 데이터 전송 |
| Snowball Edge Compute Optimized | 엣지 컴퓨팅 비중 높음 |
| Snowmobile | 엑사바이트급 초대규모 이전 |

시험 포인트:

- Snowball Edge에는 스토리지뿐 아니라 EC2/Lambda 같은 엣지 컴퓨팅도 가능하다.
- DataSync agent가 Snowcone에 포함될 수 있어 네트워크가 제한된 환경에서 동기화 시나리오가 나온다.
- 대용량 전송 성능을 높이려면 여러 Snowball 장비를 병렬로 쓰거나, 파일을 작은 단위로 병렬 복사하는 식의 최적화가 필요하다.

시험 감각:

```text
수백 TB 데이터를 인터넷으로 전송하면 너무 오래 걸림
→ Snowball Edge

엣지 위치에서 데이터를 수집/전처리 후 AWS로 반입
→ Snowball Edge Compute Optimized

데이터센터 전체급 초대규모 이전
→ Snowmobile
```

# AWS DMS, Database Migration Service

AWS DMS는 데이터베이스를 AWS로, 또는 AWS 안팎으로 마이그레이션/복제하는 서비스다.
시험에서는 "데이터를 옮기는 서비스"와 "스키마를 바꾸는 도구"를 구분하는 게 중요하다.

```text
데이터 이관/복제
→ AWS DMS

DB 엔진이 달라져서 schema 변환 필요
→ AWS SCT, Schema Conversion Tool
```

## DMS 핵심 감각

- 데이터베이스를 빠르고 안전하게 이관한다.
- 마이그레이션 중에도 source database는 계속 사용할 수 있다.
- replication instance가 실제 복제 작업을 수행한다.
- 장애가 나도 복구/재시도하는 자가 복구 감각이 있다.
- homogeneous migration과 heterogeneous migration을 모두 지원한다.
- CDC, Change Data Capture로 변경분을 계속 복제할 수 있다.

기본 구조:

```text
Source DB
→ DMS Replication Instance
→ Target DB / Target Service
```

시험 감각:

```text
운영 DB를 계속 열어둔 채 AWS로 이전
초기 full load 후 변경분 계속 복제
DB migration downtime 최소화
→ DMS
```

## Migration Type

| 방식 | 의미 | 사용 상황 |
| --- | --- | --- |
| Full Load | 기존 데이터를 한 번에 전부 이관 | 단순 초기 이전 |
| Full Load + CDC | 기존 데이터 이관 후 변경분 계속 복제 | downtime 최소화 마이그레이션 |
| CDC Only | 특정 시점 이후 변경분만 복제 | 이미 초기 데이터가 들어간 상태에서 변경분 동기화 |

시험에서 "마이그레이션 중 source DB를 계속 사용"하거나 "cutover 전까지 변경분 동기화"가 나오면 Full Load + CDC를 본다.

```text
초기 대량 이관
→ Full Load

초기 이관 + 운영 중 변경사항 계속 반영
→ Full Load + CDC

이미 데이터는 옮겼고 변경분만 필요
→ CDC Only
```

## Homogeneous vs Heterogeneous

DMS는 같은 엔진 간 이관과 다른 엔진 간 이관을 모두 지원한다.

```text
Homogeneous
= Oracle → Oracle
= PostgreSQL → PostgreSQL

Heterogeneous
= SQL Server → Aurora PostgreSQL
= Oracle → MySQL
```

단, 이종 엔진으로 바꾸면 스키마와 코드가 달라질 수 있으므로 SCT가 필요하다.

```text
같은 DB 엔진
→ DMS만으로 충분한 경우 많음

다른 DB 엔진
→ SCT로 schema 변환
→ DMS로 data migration
```

## DMS Source와 Target

DMS source가 될 수 있는 것:

```text
On-premises DB
EC2 위 DB
Oracle / SQL Server / MySQL / MariaDB / PostgreSQL
MongoDB / SAP / DB2
Azure SQL Database
RDS / Aurora
Amazon S3
DocumentDB
```

DMS target이 될 수 있는 것:

```text
On-premises DB
EC2 위 DB
Oracle / SQL Server / MySQL / MariaDB / PostgreSQL / SAP
RDS / Aurora
Redshift
DynamoDB
S3
OpenSearch Service
Kinesis Data Streams
DocumentDB
```

시험 함정:

```text
Redshift / Kinesis Data Streams / OpenSearch
→ DMS target 가능
→ DMS source는 아님
```

즉:

```text
MySQL → OpenSearch
→ DMS 가능

OpenSearch → 다른 DB
→ DMS source로는 불가
```

OpenSearch 데이터를 다른 곳으로 옮기려면 OpenSearch 전용 export 도구나 S3 export 같은 다른 방식을 고려한다.

## SCT, Schema Conversion Tool

SCT는 source DB의 schema를 target DB 엔진에 맞게 변환하는 도구다.
DMS가 데이터를 옮긴다면, SCT는 테이블 구조/인덱스/뷰/프로시저 같은 스키마를 변환한다.

```text
SQL Server / Oracle
→ MySQL / PostgreSQL / Aurora
→ SCT 필요 가능

Teradata / Oracle
→ Redshift
→ SCT 필요 가능
```

SCT가 필요 없는 대표 상황:

```text
On-premises PostgreSQL
→ RDS PostgreSQL
```

엔진은 PostgreSQL로 같고, RDS는 플랫폼만 바뀐 것이다.
이건 re-platform 감각이지 DB 엔진 변경이 아니다.

시험 감각:

```text
엔진 같음
→ SCT 보통 불필요

엔진 다름
→ SCT로 schema 변환 + DMS로 data migration
```

## 네트워크 연결

DMS는 다양한 네트워크 연결에서 동작할 수 있다.

```text
VPC Peering
Site-to-Site VPN
Software VPN
Direct Connect
```

온프레미스 DB에서 AWS target으로 마이그레이션할 때는 source DB와 DMS replication instance가 통신할 수 있어야 한다.

```text
On-premises DB
→ VPN / Direct Connect
→ DMS Replication Instance
→ RDS / Aurora / Redshift 등
```

## Oracle 관련 포인트

시험에서 깊게 나오진 않지만 다음 함정은 기억한다.

- Oracle source의 TDE는 Binary Reader를 통해 지원 가능.
- target의 BLOB도 지원한다.
- BLOB을 RDS Oracle로 이관할 때는 BLOB이 들어 있는 테이블에 primary key가 필요하다.

시험 감각:

```text
Oracle BLOB migration
→ primary key 필요
```

## DMS + Snowball

매우 큰 데이터베이스를 네트워크로 전부 옮기기 어렵다면 Snowball과 DMS를 함께 쓸 수 있다.

흐름:

```text
1. SCT로 local에서 schema/data 변환 준비
2. 대량 데이터를 Snowball Edge에 적재
3. Snowball을 AWS로 배송
4. Snowball 데이터가 S3에 적재
5. DMS가 S3 데이터를 target DB로 로드
6. 배송 중 source DB에서 바뀐 변경분은 CDC로 target에 반영
```

이 패턴의 장점:

```text
초기 대량 데이터
→ Snowball로 오프라인 전송

배송 중 발생한 변경분
→ DMS CDC로 지속 복제
```

시험 감각:

```text
DB가 너무 커서 네트워크 이관이 비현실적
마이그레이션 중에도 source DB는 계속 변경됨
→ Snowball + DMS + CDC
```

## DMS가 답인 경우

```text
데이터베이스를 AWS로 이관
마이그레이션 중 source DB 계속 사용
full load 후 변경분 계속 복제
동종/이종 DB 마이그레이션
온프레미스 DB → RDS/Aurora/Redshift/S3/DynamoDB/OpenSearch/Kinesis
대량 DB 이전에서 Snowball과 CDC 조합
→ AWS DMS
```

비교해서 기억:

```text
Schema 변환
→ AWS SCT

데이터 복제/이관
→ AWS DMS

대용량 오프라인 데이터 운송
→ Snowball

초기 대량 데이터는 Snowball, 이후 변경분은 DMS CDC
→ Snowball + DMS
```

# AWS CART, Cloud Adoption Readiness Tool

CART는 클라우드 도입 준비 상태를 평가하는 도구다.
기술 마이그레이션 도구라기보다 조직이 클라우드를 받아들일 준비가 되었는지 점검하는 쪽에 가깝다.

시험 감각:

```text
조직의 클라우드 도입 준비도 평가
운영/보안/비즈니스/사람/프로세스 관점의 readiness 확인
→ AWS CART
```

# Disaster Recovery

DR 문제는 RPO와 RTO를 기준으로 전략을 고른다.

```text
RPO
= 얼마나 많은 데이터 손실을 감당할 수 있는가

RTO
= 얼마나 빨리 복구해야 하는가
```

대표 전략:

| 전략 | 비용 | 복구 속도 | 감각 |
| --- | --- | --- | --- |
| Backup and Restore | 가장 저렴 | 가장 느림 | 백업만 다른 리전에 보관 |
| Pilot Light | 낮음 | 중간 | 핵심 DB/최소 인프라만 켜둠 |
| Warm Standby | 중간 | 빠름 | 축소된 전체 환경을 항상 가동 |
| Multi-site / Active-Active | 가장 비쌈 | 가장 빠름 | 양쪽 리전이 동시에 서비스 |

시험 감각:

```text
비용 최우선, 복구가 느려도 됨
→ Backup and Restore

핵심 데이터베이스만 복제해두고 앱 서버는 재생성
→ Pilot Light

작은 규모의 전체 환경이 다른 리전에 이미 떠 있음
→ Warm Standby

두 리전 모두 실시간 트래픽 처리
→ Multi-site / Active-Active
```

Route 53, CloudWatch alarm, Lambda를 조합해서 DR 자동화를 만들 수 있다.
하지만 CloudWatch가 직접 RDS를 전환해 주는 것은 아니다.

```text
CloudWatch alarm
→ EventBridge / SNS
→ Lambda 실행
→ Read replica 승격, DNS 업데이트 같은 작업 수행
```

# AWS FIS, Fault Injection Simulator

FIS는 장애를 일부러 주입해서 시스템 복원력을 검증하는 서비스다.

시험 감각:

```text
Chaos engineering
EC2 종료, 네트워크 지연, RDS failover 같은 장애 실험
운영 환경의 복원력 검증
→ AWS Fault Injection Simulator
```

FIS는 장애를 "예방"하는 서비스가 아니라, 장애가 났을 때 아키텍처가 버티는지 실험하는 서비스다.

# VM Migration Services

VM/서버 마이그레이션은 "애플리케이션 코드를 크게 고치지 않고 서버를 AWS로 옮긴다"는 감각이다.

## AWS Application Migration Service, MGN

MGN은 물리 서버/VM/클라우드 서버를 AWS로 lift-and-shift 마이그레이션할 때 쓰는 대표 서비스다.

```text
Source server
→ replication agent
→ staging area in AWS
→ cutover 시 EC2로 launch
```

시험 감각:

```text
온프레미스 서버를 최소 변경으로 EC2로 이전
지속 복제로 cutover downtime 최소화
lift-and-shift 서버 마이그레이션
→ AWS Application Migration Service, MGN
```

## Migration Hub

Migration Hub는 여러 마이그레이션 도구의 진행 상태를 한 곳에서 추적하는 서비스다.

```text
DMS, MGN, Discovery Service 등
→ Migration Hub에서 진행 상황 집계/추적
```

## Application Discovery Service

Application Discovery Service는 온프레미스 서버의 사용률, 의존성, 네트워크 통신 정보를 수집해 마이그레이션 계획을 돕는다.

시험 감각:

```text
마이그레이션 전에 온프레미스 서버 인벤토리와 의존성 파악
→ Application Discovery Service
```

# AWS Migration Evaluator

Migration Evaluator는 온프레미스 환경의 비용과 사용량을 분석해서 AWS 이전 비용을 추정하는 도구다.

시험 감각:

```text
현재 온프레미스 비용/사용량을 기반으로 AWS 이전 비용 산정
비즈니스 케이스 작성
→ AWS Migration Evaluator
```

# AWS Backup

AWS Backup은 여러 AWS 서비스의 백업 정책을 중앙에서 관리하는 서비스다.

시험 감각:

```text
여러 계정/여러 서비스의 백업을 중앙 정책으로 관리
백업 주기, 보존 기간, 복사, 감사
Organizations 단위 백업 정책
→ AWS Backup
```

지원 대상 감각:

```text
EBS
EC2
RDS / Aurora
DynamoDB
EFS
FSx
Storage Gateway
```

AWS Backup Vault Lock은 백업 삭제/변경을 막아 WORM 성격의 보존 요구를 만족시키는 데 사용된다.

# 마이그레이션 서비스 선택

```text
DB 데이터 이관/CDC
→ DMS

DB schema 변환
→ SCT

온프레미스 파일/스토리지와 AWS 연결
→ Storage Gateway

대용량 오프라인 데이터 전송
→ Snowball

서버/VM lift-and-shift
→ Application Migration Service, MGN

마이그레이션 진행 상황 중앙 추적
→ Migration Hub

온프레미스 서버 의존성/인벤토리 파악
→ Application Discovery Service

AWS 이전 비용 평가
→ Migration Evaluator

중앙 백업 정책
→ AWS Backup

복원력 실험
→ FIS
```
