# SAP 보안

## CloudTrail 아키텍처 정리

CloudTrail은 AWS 계정에서 일어난 API 호출 기록을 남기는 감사 로그 서비스다.

예를 들면 누가 EC2를 종료했는지, 누가 IAM Role을 만들었는지, 누가 S3 버킷 정책을 바꿨는지 같은 기록을 남긴다.

시험에서는 CloudTrail 자체보다, CloudTrail 로그를 어디로 보내고 어떻게 반응할지 묻는 아키텍처 문제가 자주 나온다.

## CloudTrail 로그를 S3에 저장하는 경우

CloudTrail은 로그 파일을 S3 버킷으로 전달할 수 있다.

느낌은 이거다.

```text
AWS 계정의 API 호출
→ CloudTrail이 기록
→ S3 버킷에 로그 파일 저장
```

CloudTrail 로그는 보통 몇 분 단위로 S3에 쌓인다. 강의에서는 약 5분마다 S3에 전달된다고 보면 된다고 설명했다.

S3에 저장하면 좋은 점은 보관, 암호화, 삭제 방지, 장기 분석을 S3 기능으로 처리할 수 있다는 것이다.

알아둘 기능:

- 기본 암호화는 SSE-S3를 사용할 수 있다.
- 필요하면 SSE-KMS를 설정해서 KMS 키로 암호화할 수 있다.
- S3 Lifecycle 정책으로 오래된 로그를 S3 IA, Glacier 계층으로 보낼 수 있다.
- S3 Versioning으로 실수 삭제나 변경에 대비할 수 있다.
- MFA Delete로 삭제를 더 어렵게 만들 수 있다.
- S3 Object Lock으로 로그가 삭제되거나 수정되지 않게 만들 수 있다.
- CloudTrail 로그 파일 무결성 검증으로 로그 파일이 조작되지 않았는지 확인할 수 있다.

즉 S3는 CloudTrail 로그를 오래 보관하고, 나중에 감사/분석/포렌식할 때 쓰는 저장소 역할이다.

## CloudTrail + S3 이벤트

CloudTrail 로그가 S3에 도착하면 S3 이벤트 알림을 사용할 수 있다.

```text
CloudTrail 로그 파일 생성
→ S3 객체 생성 이벤트
→ SQS / SNS / Lambda 호출
```

또는 CloudTrail이 직접 SNS로 알림을 보낼 수도 있다.

```text
CloudTrail
→ SNS
→ SQS / Lambda / Email 등
```

시험에서 포인트는 “방법이 하나만 있는 게 아니다”라는 점이다.

S3에 로그가 떨어진 뒤 S3 이벤트로 처리해도 되고, CloudTrail에서 SNS로 직접 알림을 보내도 된다. 문제에서 요구하는 지연 시간, 처리 방식, 확장성에 따라 고르면 된다.

## 다중 계정 CloudTrail 로그 중앙화

여러 AWS 계정을 운영하면 각 계정의 CloudTrail 로그를 한 보안 계정으로 모으는 구조가 자주 나온다.

```text
Account A CloudTrail ┐
Account B CloudTrail ├→ Security Account의 S3 버킷
Account C CloudTrail ┘
```

이때 중요한 것은 대상 S3 버킷 정책이다.

CloudTrail이 다른 계정의 S3 버킷에 로그를 쓸 수 있으려면, 보안 계정의 S3 버킷 정책에서 CloudTrail 쓰기를 허용해야 한다.

읽기 권한이 필요하면 선택지가 있다.

- 각 계정이 보안 계정의 Role을 AssumeRole해서 로그를 읽게 한다.
- S3 버킷 정책에서 특정 계정/역할에 읽기 권한을 준다.

보안 계정을 따로 두는 이유는 CloudTrail 로그를 일반 워크로드 계정과 분리해서 더 강하게 보호하기 위해서다.

운영 계정이 털리거나 실수로 설정이 바뀌어도, 감사 로그는 보안 계정에 남아 있게 만드는 구조다.

## 특정 API 호출에 알람 만들기

특정 API 호출이 발생했을 때 알람을 만들고 싶으면 CloudTrail 로그를 CloudWatch Logs로 보낼 수 있다.

예를 들면 EC2 인스턴스 종료 API가 호출될 때 알림을 보내고 싶다고 하자.

```text
CloudTrail
→ CloudWatch Logs
→ Metric Filter
→ CloudWatch Alarm
→ SNS
→ Email / Lambda / SQS
```

흐름은 이렇다.

1. CloudTrail 이벤트를 CloudWatch Logs로 보낸다.
2. CloudWatch Logs에서 Metric Filter를 만든다.
3. Metric Filter가 `TerminateInstances` 같은 API 호출을 찾는다.
4. 찾으면 메트릭 값을 증가시킨다.
5. CloudWatch Alarm이 메트릭 기준을 넘으면 SNS로 알림을 보낸다.

이 구조는 단일 API뿐 아니라 “이상한 패턴”을 잡는 데도 쓸 수 있다.

예:

- EC2 종료 API 호출 감지
- IAM 사용자/Role 변경 감지
- AccessDenied가 비정상적으로 많이 발생하는지 감지
- 특정 사용자의 API 호출 횟수 집계
- 짧은 시간에 로그인 실패가 많이 발생하는지 감지

즉 CloudWatch Logs + Metric Filter + Alarm은 CloudTrail 이벤트를 세고, 조건에 맞으면 경고하는 구조다.

## CloudTrail Organization Trail

AWS Organizations를 쓰는 경우, 조직 전체에 대한 CloudTrail 추적을 만들 수 있다.

이걸 Organization Trail, 즉 조직 추적이라고 한다.

핵심은 이거다.

```text
관리 계정에서 Organization Trail 생성
→ 조직 안의 모든 멤버 계정 이벤트 수집
→ 중앙 S3 버킷에 저장
```

중요한 시험 포인트:

- 조직 추적은 멤버 계정이 아니라 Organizations의 관리 계정에서 만든다.
- 또는 CloudTrail 위임 관리자 계정에서 관리할 수 있다.
- 조직 안의 모든 멤버 계정 이벤트가 추적된다.
- 새 멤버 계정이 조직에 추가되면 조직 추적 대상에 포함된다.
- 로그는 중앙 S3 버킷으로 모을 수 있다.
- S3 로그 경로에는 계정 ID가 포함되어 어떤 계정의 로그인지 구분할 수 있다.

쉽게 말하면 계정마다 CCTV를 따로 설치하는 게 아니라, 본사에서 전 지점 CCTV 녹화를 한 번에 켜는 느낌이다.

```text
관리 계정
├─ Dev OU
│  ├─ Dev Account 1
│  └─ Dev Account 2
├─ Prod OU
│  ├─ Prod Account 1
│  └─ Prod Account 2
└─ Security Account

관리 계정의 Organization Trail
→ 모든 멤버 계정의 CloudTrail 이벤트 수집
```

조직 전체 감사, 보안 통제, 사고 조사에는 이 방식이 훨씬 낫다.

## CloudTrail 이벤트에 가장 빨리 반응하려면

CloudTrail 로그 전달은 약간 지연될 수 있다. 강의에서는 CloudTrail 이벤트가 전달되기까지 최대 15분 정도 걸릴 수 있다고 설명했다.

가장 빠르게 반응해야 한다면 EventBridge를 고려한다.

```text
AWS API 호출
→ CloudTrail 이벤트
→ EventBridge Rule
→ Lambda / SNS / SQS / Step Functions 등
```

EventBridge는 CloudTrail API 이벤트와 깊게 통합되어 있어서, 특정 API 호출이 발생했을 때 빠르게 후속 동작을 실행하기 좋다.

예:

- 누가 보안 그룹을 열면 바로 Lambda로 되돌리기
- 루트 계정 로그인 감지 후 SNS 알림
- IAM 정책 변경 감지 후 보안팀 알림
- CloudTrail 중지 시도 감지 후 즉시 대응

## 목적별로 무엇을 써야 하나

시험에서는 “CloudTrail 로그가 있는데 어디로 보내야 가장 맞는가?”를 자주 묻는다.

정리하면 이렇게 보면 된다.

| 목적 | 적합한 서비스 |
| --- | --- |
| API 이벤트에 빠르게 반응 | EventBridge |
| API 호출 횟수 집계, 임계치 알람 | CloudWatch Logs + Metric Filter + CloudWatch Alarm |
| 장기 보관, 감사, 포렌식, 대규모 분석 | S3 |
| 여러 계정 로그를 중앙에서 수집 | Organization Trail + 중앙 S3 버킷 |
| 로그 삭제/변조 방지 | S3 Object Lock, Versioning, MFA Delete, 로그 무결성 검증 |
| 오래된 로그 비용 절감 | S3 Lifecycle → S3 IA / Glacier |

## 시험용 요약

CloudTrail은 AWS API 호출 감사 로그다.

S3로 보내면 장기 보관, 암호화, 수명 주기, Object Lock, 무결성 검증 같은 S3 기능을 활용할 수 있다.

CloudWatch Logs로 보내면 Metric Filter와 Alarm으로 특정 API 호출이나 이상 패턴에 대한 경고를 만들 수 있다.

EventBridge를 쓰면 CloudTrail 이벤트에 가장 빠르게 반응할 수 있다.

AWS Organizations 환경에서는 관리 계정에서 Organization Trail을 만들면 모든 멤버 계정의 CloudTrail 이벤트를 중앙에서 수집할 수 있다.

## KMS 개념 정리

KMS는 AWS Key Management Service다.

AWS에서 “암호화 키 관리”라는 말이 나오면 거의 KMS를 떠올리면 된다.

KMS가 해주는 일은 크게 두 가지다.

- 암호화 키를 안전하게 만들고 보관한다.
- 누가 그 키를 사용할 수 있는지 IAM/키 정책으로 제어한다.

KMS는 AWS 서비스들과 많이 통합되어 있다.

예:

- S3
- EBS
- RDS
- Redshift
- SSM Parameter Store
- CloudTrail
- Lambda

즉, 서비스에서 “KMS 키로 암호화” 옵션을 켜면 내부적으로 KMS가 키 관리를 맡는다.

## KMS와 봉투 암호화

KMS는 큰 데이터를 직접 전부 암호화하는 용도라기보다, 보통 봉투 암호화에서 상위 키 역할을 한다.

흐름은 이렇다.

```text
원본 데이터
→ Data Key로 암호화
→ 암호화된 데이터

Data Key
→ KMS Key로 암호화
→ 암호화된 Data Key

저장되는 것:
암호화된 데이터 + 암호화된 Data Key
```

즉 실제 데이터는 Data Key가 암호화하고, 그 Data Key를 KMS Key가 감싸서 보호한다.

시험식으로 말하면:

> Envelope Encryption = 데이터를 Data Key로 암호화하고, Data Key를 KMS Key로 다시 암호화하는 방식

## KMS 키 타입: 대칭 키와 비대칭 키

KMS 키는 크게 대칭 키와 비대칭 키로 나뉜다.

### 대칭 KMS 키

대칭 키는 같은 키로 암호화와 복호화를 모두 한다.

```text
하나의 KMS Key
→ Encrypt
→ Decrypt
```

AWS 서비스들이 KMS와 통합해서 사용하는 기본 방식은 대부분 대칭 KMS 키다.

특징:

- 암호화와 복호화에 같은 키를 쓴다.
- 봉투 암호화에 사용된다.
- KMS 키 자체를 평문으로 꺼내 볼 수 없다.
- KMS API를 호출해서 암호화/복호화 작업을 요청해야 한다.
- S3, EBS, RDS 등 대부분의 AWS 서비스 통합에 사용된다.

쉽게 말하면 “KMS 안에 들어 있는 잠긴 열쇠”다. 사용자는 열쇠를 직접 들고 나오는 게 아니라, KMS에게 “이거 암호화해줘”, “이거 복호화해줘”라고 요청한다.

### 비대칭 KMS 키

비대칭 키는 공개 키와 개인 키 한 쌍으로 이루어진다.

```text
Public Key  = 암호화 / 서명 검증
Private Key = 복호화 / 서명 생성
```

특징:

- 공개 키는 다운로드할 수 있다.
- 공개 키는 외부나 신뢰할 수 없는 환경에 줘도 된다.
- 공개 키로 암호화한 데이터는 개인 키로만 복호화할 수 있다.
- 개인 키는 평문으로 꺼낼 수 없다.
- 개인 키 작업은 KMS API를 통해서만 수행한다.

사용 사례:

- AWS 밖에서 데이터를 암호화해야 하는 경우
- KMS API를 직접 호출할 수 없는 클라이언트가 공개 키로 먼저 암호화해야 하는 경우
- 디지털 서명/검증이 필요한 경우

예를 들면 외부 사용자가 공개 키로 데이터를 암호화해서 AWS로 보내면, AWS 안에서는 KMS의 개인 키로만 복호화할 수 있다.

## KMS 키 소유/관리 유형

KMS 키는 누가 만들고 관리하느냐에 따라 세 종류로 보면 된다.

| 구분 | 누가 관리? | 볼 수 있음? | 직접 사용/관리? | 회전 | CloudTrail 감사 |
| --- | --- | --- | --- | --- | --- |
| 고객 관리 키 | 사용자 | 가능 | 가능 | 사용자가 설정 가능 | 가능 |
| AWS 관리 키 | AWS 서비스 | 메타데이터/정책 확인 가능 | 직접 관리 불가 | AWS가 자동 회전 | 가능 |
| AWS 소유 키 | AWS | 불가 | 불가 | AWS 내부 관리 | 사용자 계정에서 감사 불가 |

### 고객 관리 키

Customer managed key는 사용자가 직접 KMS에서 만들고 관리하는 키다.

할 수 있는 것:

- 키 생성
- 키 활성화/비활성화
- 키 정책 설정
- IAM 정책과 함께 권한 제어
- 자동 회전 설정
- 온디맨드 회전
- CloudTrail로 키 사용 감사

사용자가 직접 제어해야 하는 중요한 암호화에는 고객 관리 키를 쓴다.

예:

- 특정 S3 버킷을 우리 KMS 키로 암호화
- RDS 암호화에 특정 KMS 키 지정
- CloudTrail 로그를 SSE-KMS로 암호화
- 애플리케이션에서 직접 KMS API 호출

### AWS 관리 키

AWS managed key는 AWS 서비스가 내 계정 안에 만들어서 관리하는 키다.

예를 들어 S3, EBS 같은 서비스에서 AWS 관리형 KMS 키를 선택하면 서비스가 관리하는 키를 쓰게 된다.

특징:

- 내 계정 안에 존재한다.
- 메타데이터와 키 정책은 볼 수 있다.
- 사용자가 직접 키를 관리하거나 회전을 트리거할 수 없다.
- AWS가 자동으로 회전한다.
- CloudTrail에서 사용 기록을 감사할 수 있다.

즉 “내 계정에 있지만 AWS 서비스가 관리하는 키”다.

### AWS 소유 키

AWS owned key는 AWS가 내부적으로 소유하고 관리하는 키다.

특징:

- 내 계정에 보이지 않는다.
- 키 정책도 볼 수 없다.
- 직접 사용할 수 없다.
- CloudTrail로 내 계정 관점에서 키 사용을 추적할 수 없다.
- 여러 AWS 계정의 리소스 보호에 AWS 내부적으로 쓰일 수 있다.

즉 존재는 하지만 사용자에게 노출되지 않는 AWS 내부 키다.

## 키 정책과 IAM

KMS는 IAM과 통합되어 있지만, KMS에서는 키 정책이 특히 중요하다.

KMS 키는 리소스 자체에 붙는 키 정책을 가진다.

```text
IAM 정책 = 이 사용자/Role이 무엇을 할 수 있는가
키 정책 = 이 KMS 키를 누가 사용할 수 있는가
```

KMS 키를 쓰려면 보통 두 조건이 맞아야 한다.

- IAM 정책이나 권한에서 KMS 사용이 허용되어야 한다.
- KMS 키 정책에서도 해당 principal이 허용되어야 한다.

시험에서는 “IAM 권한은 있는데 KMS 복호화가 안 된다” 같은 문제가 나오면 키 정책을 의심해야 한다.

## KMS 키 자료 원본

KMS 키를 만들 때 중요한 설정이 키 자료 원본이다.

키 자료 원본은 “실제 암호화 키 재료를 어디에서 만들고 보관할 것인가”를 의미한다.

생성 후에는 바꿀 수 없다.

주요 선택지는 세 가지다.

| 키 자료 원본 | 의미 |
| --- | --- |
| AWS_KMS | KMS가 키 자료를 생성하고 KMS 안에서 관리 |
| EXTERNAL | 사용자가 외부에서 만든 키 자료를 KMS로 가져오기 |
| Custom Key Store | CloudHSM 같은 전용 HSM에 키 자료 저장 |

## AWS_KMS 키 자료

가장 일반적인 방식이다.

```text
사용자가 KMS 키 생성
→ KMS가 키 자료 생성
→ KMS 내부에서 안전하게 저장/관리
```

대부분의 일반적인 AWS 암호화 요구사항은 이 방식으로 충분하다.

## 외부 키 자료 가져오기

EXTERNAL origin은 사용자가 AWS 밖에서 만든 키 자료를 KMS로 가져오는 방식이다.

흐름은 대략 이렇다.

```text
KMS 키 생성, origin = EXTERNAL
→ 아직 키 자료는 없음
→ KMS에서 공개 키와 import token 다운로드
→ 외부에서 만든 키 자료를 공개 키로 암호화
→ import token과 함께 KMS에 업로드
→ KMS 키에 키 자료가 들어감
```

이 방식을 쓰면 키 자료를 사용자가 직접 생성했다는 통제권을 가질 수 있다.

대신 책임도 사용자에게 온다.

사용자 책임:

- AWS 외부에 있는 키 자료 원본 보안
- 키 자료 백업
- 키 자료 가용성
- 키 자료 내구성
- 직접 회전 전략 관리

주의점:

- 외부 키 자료는 자동 회전이 제한된다.
- 키 자료가 만료되거나 삭제되면 해당 KMS 키는 사용할 수 없게 된다.
- Custom Key Store와 같이 사용할 수 없다.

시험식으로 말하면:

> 외부 키 자료 = 키를 내가 만들어 KMS에 가져오는 방식. 통제권은 커지지만 키 자료 보안/백업/회전 책임도 내가 진다.

## CloudHSM 기반 Custom Key Store

Custom Key Store는 KMS와 CloudHSM을 연결해서, 키 자료를 사용자가 관리하는 HSM 클러스터 안에 보관하는 방식이다.

```text
사용자
→ KMS API 호출
→ KMS가 CloudHSM Custom Key Store 사용
→ 실제 키 자료와 암호화 작업은 CloudHSM에서 처리
```

중요한 점은 사용자는 여전히 KMS API를 쓴다는 것이다.

겉으로는 KMS를 쓰지만, 내부적으로는 내가 소유하고 관리하는 CloudHSM 클러스터가 키 저장과 암호화 작업을 담당한다.

구조:

```text
KMS
↔ Custom Key Store
↔ CloudHSM Cluster
   ├─ HSM in AZ A
   └─ HSM in AZ B
```

고가용성을 위해 보통 여러 AZ에 HSM을 둔다.

사용 사례:

- 규정상 전용 HSM이 필요한 경우
- 키 자료가 AWS 관리형 KMS 저장소가 아니라 내가 관리하는 HSM에 있어야 하는 경우
- 더 강한 키 통제권이 필요한 경우
- 금융/공공/강한 컴플라이언스 요구사항

주의점:

- 일반 KMS보다 운영 부담이 크다.
- CloudHSM 클러스터 가용성도 신경 써야 한다.
- 비용과 관리 복잡도가 올라간다.

## KMS 키 회전

키 회전은 KMS 키의 논리적 ID는 유지하면서, 내부 키 자료를 새 것으로 바꾸는 것이다.

```text
KMS Key ID는 유지
키 자료 버전만 변경
```

기존 데이터는 다시 암호화하지 않는다. KMS는 어떤 키 자료 버전으로 암호화했는지 알고 있어서, 복호화할 때 맞는 키 자료를 자동으로 사용한다.

정리:

- 고객 관리 대칭 키는 자동 회전을 설정할 수 있다.
- 기본 자동 회전 주기는 365일이다.
- 필요하면 회전 주기를 지정할 수 있다.
- 즉시 회전이 필요하면 온디맨드 회전을 사용할 수 있다.
- AWS 관리 키는 AWS가 자동으로 회전한다.
- 비대칭 키, HMAC 키, Custom Key Store 키는 자동 회전 대신 수동 회전이 필요할 수 있다.

시험에서 중요한 말:

> 키 회전은 KMS 키 자체를 바꾸는 게 아니라 키 자료를 바꾸는 것이다. 기존 암호문은 KMS가 이전 키 자료를 사용해 계속 복호화할 수 있다.

## 다중 리전 KMS 키

Multi-Region Key는 여러 리전에 복제할 수 있는 KMS 키다.

예:

```text
us-east-1 Primary KMS Key
→ eu-west-1 Replica KMS Key
→ ap-northeast-2 Replica KMS Key
```

다중 리전 키는 같은 키 ID와 같은 키 자료를 가진다.

그래서 한 리전에서 암호화한 데이터를 다른 리전의 관련 KMS 키로 복호화할 수 있다.

```text
us-east-1에서 암호화
→ ap-northeast-2에서 복호화 가능
```

장점:

- 리전 간 복호화를 위해 원래 리전의 KMS로 API 호출하지 않아도 된다.
- 데이터를 다른 키로 다시 암호화하지 않아도 된다.
- 재해 복구와 글로벌 애플리케이션에 좋다.

사용 사례:

- 재해 복구
- DynamoDB Global Tables
- active-active 멀티 리전 애플리케이션
- 글로벌 데이터 관리
- 여러 리전에서 서명/검증이 필요한 애플리케이션

주의점:

- 다중 리전 키는 글로벌 키가 아니다.
- 기본 키와 복제 키가 있는 구조다.
- 각 리전의 키는 독립적으로 관리된다.
- 별칭, 태그, 키 정책, grants, 활성화/비활성화는 리전별로 관리한다.
- 한 번에 하나의 primary key만 있다.
- replica를 primary로 승격할 수 있다.
- AWS 관리 키는 다중 리전 키가 아니라 단일 리전 키다.
- Custom Key Store에서는 다중 리전 키를 만들 수 없다.

시험식으로 말하면:

> Multi-Region KMS Key = 같은 키 ID/키 자료를 여러 리전에 복제해서, 리전 간 재암호화나 원격 KMS 호출 없이 암호화/복호화할 수 있게 하는 키. 단, 글로벌 키는 아니고 각 리전 키는 독립 관리된다.

## KMS 선택 기준

| 요구사항 | 선택 |
| --- | --- |
| AWS 서비스 암호화 기본 선택 | 대칭 KMS 키 |
| 내가 키 정책/회전/권한을 직접 통제 | 고객 관리 키 |
| 서비스가 알아서 관리해도 됨 | AWS 관리 키 |
| 키를 볼 필요도 없고 서비스 내부 보호면 충분 | AWS 소유 키 |
| 외부 사용자가 AWS 밖에서 암호화해야 함 | 비대칭 KMS 키의 공개 키 |
| 키 자료를 내가 만들어 가져와야 함 | EXTERNAL origin |
| 전용 HSM에서 키 자료를 통제해야 함 | CloudHSM Custom Key Store |
| 멀티 리전 DR/active-active | Multi-Region KMS Key |

## KMS 시험용 요약

KMS는 AWS의 암호화 키 관리 서비스다.

대칭 키는 하나의 키로 암호화/복호화하며 대부분의 AWS 서비스 통합과 봉투 암호화에 사용된다.

비대칭 키는 공개 키/개인 키 쌍이며, 공개 키는 외부에 배포해서 AWS 밖에서 암호화하거나 서명 검증에 사용할 수 있다.

고객 관리 키는 사용자가 직접 만들고 정책/회전/감사를 제어한다.

AWS 관리 키는 AWS 서비스가 내 계정에서 관리하며 사용자는 직접 제어하지 못한다.

AWS 소유 키는 AWS 내부 키라 사용자 계정에서 볼 수도, 감사할 수도 없다.

키 자료 원본은 생성 후 바꿀 수 없고, `AWS_KMS`, `EXTERNAL`, `Custom Key Store`가 있다.

CloudHSM Custom Key Store는 KMS API는 그대로 쓰되 실제 키 자료와 암호화 작업을 내가 관리하는 HSM에서 처리한다.

Multi-Region KMS Key는 같은 키 ID/키 자료를 여러 리전에 복제해 DR과 글로벌 애플리케이션에 유리하지만 글로벌 키는 아니다.

## Secrets Manager, Parameter Store, KMS 차이

세 서비스는 같이 나오지만 역할이 다르다.

```text
KMS = 암호화 키 관리
Secrets Manager = 비밀번호/API Key 같은 비밀값 저장 + 자동 교체
Parameter Store = 설정값 저장, 필요하면 SecureString으로 암호화
```

비유하면 이렇다.

```text
KMS
= 금고를 잠그는 키 관리소

Secrets Manager
= 비밀번호 금고 + 주기적으로 비밀번호 바꿔주는 기능

Parameter Store
= 애플리케이션 설정값 수첩
  단, SecureString은 KMS로 잠글 수 있음
```

## AWS Secrets Manager

Secrets Manager는 이름 그대로 secret을 저장하는 서비스다.

저장 대상:

- DB 비밀번호
- API Key
- OAuth Token
- 애플리케이션 credential
- 외부 서비스 접속 정보

핵심 기능은 자동 교체(rotation)다.

```text
Secrets Manager
→ 주기적으로 Lambda 호출
→ 새 비밀번호 생성
→ RDS/Redshift/DocumentDB 쪽 비밀번호 변경
→ Secrets Manager에 저장된 secret 값도 변경
```

RDS, Redshift, DocumentDB 같은 AWS 데이터베이스는 Secrets Manager와 자동 rotation 통합이 잘 되어 있다.

다른 데이터베이스나 외부 서비스의 비밀번호를 자동 교체하려면, 직접 Lambda 함수를 만들어 Secrets Manager rotation에 연결해야 한다.

특징:

- secret은 KMS로 암호화된다.
- 자동 rotation을 지원한다.
- RDS, Redshift, DocumentDB와 잘 통합된다.
- ECS, CodeBuild, CloudFormation, Fargate, EKS 등과 통합된다.
- ECS Task 시작 시 secret을 환경 변수로 주입할 수 있다.
- secret에 리소스 기반 정책을 붙일 수 있다.

예를 들어 ECS 태스크가 RDS 비밀번호를 써야 하면:

```text
ECS Task 시작
→ Secrets Manager에서 DB 비밀번호 조회
→ 컨테이너 환경 변수로 주입
→ 애플리케이션이 RDS 접속
```

앱 코드나 이미지 안에 비밀번호를 박아두지 않아도 된다.

## CloudFormation과 Secrets Manager

CloudFormation에서도 Secrets Manager secret을 만들고 참조할 수 있다.

예를 들면:

```text
1. Secrets Manager Secret 생성
2. RDS DB Instance에서 그 secret 참조
3. SecretTargetAttachment로 secret과 RDS를 연결
```

SecretTargetAttachment는 “이 secret은 이 RDS의 비밀번호다”라고 Secrets Manager에 알려주는 역할이다.

그래야 rotation이 일어날 때 Secrets Manager가 RDS 실제 비밀번호도 같이 바꿔야 한다는 걸 안다.

## Secrets Manager cross-account 공유

Secrets Manager secret을 다른 AWS 계정과 공유할 때는 AWS RAM을 쓰는 게 아니다.

필요한 권한은 두 가지다.

```text
1. Secret 리소스 기반 정책
   → 다른 계정/Role에 secretsmanager:GetSecretValue 허용

2. KMS 키 정책
   → 다른 계정/Role에 kms:Decrypt 허용
```

왜 둘 다 필요할까?

```text
Secret 읽기 권한만 있음
→ 암호화된 secret은 가져와도 복호화 못 함

KMS Decrypt 권한만 있음
→ secret 자체를 읽을 수 없음

둘 다 있어야 함
→ GetSecretValue + KMS Decrypt
```

KMS 키 정책에는 `kms:ViaService` 조건을 걸 수 있다.

```text
kms:ViaService = secretsmanager.<region>.amazonaws.com
```

이렇게 하면 KMS 복호화가 Secrets Manager를 통해 호출될 때만 허용된다.

즉 다른 계정에 KMS Decrypt 권한을 주더라도, 그 키를 아무 데서나 직접 쓰지 못하게 제한할 수 있다.

시험 포인트:

- Secrets Manager secret은 RAM으로 공유하지 않는다.
- secret 리소스 정책과 KMS 키 정책이 둘 다 필요하다.
- KMS가 customer managed key라면 cross-account 쪽 KMS Decrypt 권한을 반드시 확인한다.

## Parameter Store

SSM Parameter Store는 설정값 저장소다.

저장 대상:

- `/app/prod/db/host`
- `/app/prod/log-level`
- `/app/prod/ami-id`
- `/app/prod/feature-flag`
- 간단한 비밀번호나 토큰

Parameter Store는 계층형 이름을 쓰기 좋다.

```text
/myapp/dev/db/host
/myapp/dev/db/password
/myapp/prod/db/host
/myapp/prod/db/password
```

값 타입:

- String
- StringList
- SecureString

`SecureString`을 쓰면 KMS로 암호화할 수 있다.

하지만 Parameter Store의 기본 성격은 “설정값 저장소”다.

Secrets Manager처럼 secret rotation이 핵심 기능은 아니다.

## Secrets Manager와 Parameter Store rotation 차이

Secrets Manager는 rotation이 내장 기능에 가깝다.

```text
Secrets Manager
→ rotation 설정
→ Lambda가 주기적으로 실행
→ DB 비밀번호와 secret 값이 같이 변경
```

Parameter Store로도 비슷하게 만들 수는 있지만 직접 조립해야 한다.

```text
Parameter Store에 비밀번호 저장
→ EventBridge 스케줄 생성
→ Lambda 직접 작성
→ DB 비밀번호 변경
→ Parameter Store 값 변경
```

즉:

```text
Secrets Manager = rotation을 서비스가 도와줌
Parameter Store = rotation 자동화를 직접 만들어야 함
```

## 세 서비스 비교

| 구분 | KMS | Secrets Manager | Parameter Store |
| --- | --- | --- | --- |
| 주 역할 | 암호화 키 관리 | secret 저장/교체 | 설정값 저장 |
| 저장 대상 | KMS Key | DB password, API key, token | URL, 환경값, AMI ID, 간단한 secret |
| secret 자동 교체 | 해당 없음 | 지원 | 직접 구현 필요 |
| KMS 암호화 | 본체 | 필수 | SecureString에서 사용 |
| 리소스 정책 | 키 정책 | secret 리소스 정책 | 일반적으로 IAM 중심 |
| 비용 | 키/API 사용 비용 | 상대적으로 비쌈 | 상대적으로 단순/저렴 |
| 대표 사용처 | S3/EBS/RDS 암호화 키 | RDS 비밀번호 rotation | 앱 설정값 중앙 관리 |

## 선택 기준

| 요구사항 | 선택 |
| --- | --- |
| 암호화 키를 만들고 제어해야 함 | KMS |
| DB 비밀번호/API Key를 저장하고 자동 교체해야 함 | Secrets Manager |
| RDS/Redshift/DocumentDB credential rotation | Secrets Manager |
| 앱 설정값, URL, AMI ID, feature flag 관리 | Parameter Store |
| 간단한 비밀값을 싸게 저장 | Parameter Store SecureString |
| cross-account secret 공유 | Secrets Manager 리소스 정책 + KMS 키 정책 |
| 비밀번호 rotation을 직접 만들고 싶음 | Parameter Store + EventBridge + Lambda |

## 시험용 요약

KMS는 비밀값 저장소가 아니라 암호화 키 관리 서비스다.

Secrets Manager는 비밀번호/API Key 같은 secret을 저장하고 자동 rotation까지 해주는 서비스다.

Parameter Store는 애플리케이션 설정값 저장소이고, `SecureString`을 쓰면 KMS로 암호화된 간단한 secret도 저장할 수 있다.

Secrets Manager는 KMS 암호화가 필수이고, Parameter Store는 SecureString일 때 KMS 암호화를 사용한다.

RDS 비밀번호를 자동으로 교체하려면 Secrets Manager가 정석이다.

다른 계정에 Secrets Manager secret을 공유하려면 secret 리소스 정책과 KMS 키 정책이 둘 다 필요하다.

# RDS

RDS는 저장 데이터는 KMS로 EBS 볼륨/스냅샷 암호화하고, Oracle/SQL Server는 TDE도 가능하며, 전송 데이터는 SSL/TLS로 암호화할 수 있음.

IAM DB 인증은 MySQL/PostgreSQL만 지원하고 “로그인 인증”만 IAM이 맡으며, 실제 DB 권한 부여는 DB 내부 권한으로 관리함.

암호화 안 된 스냅샷은 암호화된 스냅샷으로 복사 가능하고, CloudTrail은 RDS API 호출만 추적하지 SQL 쿼리 내용 추적용은 아님.

# SSL/TLS, SNI, 중간자 공격

## SSL/TLS 기본

SSL은 오래된 이름이고, 요즘 실제로 쓰는 것은 대부분 TLS다. 그래도 AWS 강의나 시험에서는 SSL/TLS를 섞어 부르는 경우가 많다.

TLS는 클라이언트와 서버 사이 통신을 암호화해서 중간에서 내용을 훔쳐보거나 바꾸기 어렵게 만든다.

작동 방식은 대략 이렇다.

```text
1. 클라이언트가 서버에 접속
2. 서버가 TLS 인증서를 제시
3. 클라이언트가 CA 서명과 도메인명을 확인
4. 서로 실제 통신에 쓸 임시 대칭키를 합의
5. 이후 데이터 통신은 빠른 대칭 암호화로 처리
```

핵심은 비대칭 암호화는 주로 handshake와 신뢰 확인에 쓰고, 실제 데이터 통신은 대칭 암호화를 쓴다는 점이다.

## SNI

SNI는 Server Name Indication이다.

한 서버나 로드 밸런서에 여러 TLS 인증서를 올려두고, 클라이언트가 접속하려는 도메인에 맞는 인증서를 골라주는 기능이다.

```text
클라이언트: www.mycorp.com 접속할래
ALB: mycorp.com 인증서 사용

클라이언트: domain1.example.com 접속할래
ALB: example.com 인증서 사용
```

TLS handshake 초반에 클라이언트가 “나는 이 hostname으로 접속하려고 한다”라고 알려주면, 서버나 로드 밸런서가 그 hostname에 맞는 인증서를 선택한다.

시험 포인트:

- SNI는 하나의 엔드포인트에서 여러 도메인/여러 인증서를 처리할 때 필요하다.
- ALB는 SNI를 지원한다.
- NLB도 SNI를 지원한다.
- CloudFront도 SNI를 지원한다.
- 구세대 CLB는 SNI를 지원하지 않는다.

따라서 여러 도메인과 여러 인증서를 하나의 로드 밸런서에서 처리하려면 ALB/NLB/CloudFront를 생각한다.

CLB를 쓰면 SNI가 안 되므로, 도메인이나 인증서별로 CLB를 따로 두는 식의 구조가 필요할 수 있다.

## 중간자 공격

중간자 공격은 사용자와 서버 사이에 공격자가 끼어드는 공격이다.

HTTP는 평문 통신이라 공격자가 중간에서 내용을 볼 수 있고, 바꿀 수도 있다.

```text
사용자
→ 공격자
→ 진짜 서버
```

HTTPS/TLS를 쓰면 클라이언트가 서버 인증서를 검증한다.

공격자가 가짜 서버 인증서를 내밀어도, 정상 클라이언트는 CA 서명이나 도메인명이 맞지 않으면 경고를 띄운다.

다만 아래 상황에서는 여전히 위험할 수 있다.

- 사용자가 인증서 경고를 무시함
- 사용자 기기가 감염되어 공격자 인증서를 신뢰함
- 사내 프록시/보안 장비가 자체 루트 인증서를 설치하고 TLS를 가로채는 구조
- 약한 TLS 버전이나 취약한 암호 스위트를 사용함

## DNS 공격과 DNSSEC

HTTPS/TLS는 통신 내용을 보호하지만, DNS 응답 위조까지 전부 막지는 않는다.

공격자가 DNS 응답을 조작하면 사용자가 잘못된 서버 IP로 갈 수 있다.

```text
사용자: example.com IP가 뭐야?
가짜 DNS 응답: 공격자 서버 IP야
```

DNSSEC는 DNS 응답에 전자서명을 붙여서, DNS 응답이 조작되지 않았는지 검증하게 해준다.

시험 포인트:

- MITM 방어 기본은 HTTPS/TLS다.
- DNS 응답 위조 방어는 DNSSEC다.
- Route 53은 DNSSEC를 지원한다.
- 직접 DNSSEC를 구성해야 하면 EC2에서 BIND, dnsmasq, KnotDNS, PowerDNS 같은 DNS 서버를 운영할 수도 있다.

## 시험용 요약

TLS는 처음 handshake에서 인증서와 비대칭 암호화로 신뢰를 확인하고, 이후 실제 통신은 대칭 암호화로 처리한다.

SNI는 하나의 ALB/NLB/CloudFront에서 여러 도메인의 여러 인증서를 처리하게 해주는 기능이다.

CLB는 SNI를 지원하지 않는다.

중간자 공격을 막으려면 공개 웹 통신은 HTTP가 아니라 HTTPS/TLS를 사용해야 한다.

DNS 위조까지 고려하면 DNSSEC를 사용한다.

# ACM

ACM은 AWS Certificate Manager다.

AWS에서 SSL/TLS 인증서를 발급, 가져오기, 관리하는 서비스다.

## ACM으로 인증서를 쓰는 방법

공개 SSL/TLS 인증서를 AWS에서 쓰는 방법은 크게 두 가지다.

```text
1. 외부에서 산 인증서를 ACM에 직접 업로드
2. ACM에서 공인 인증서를 발급
```

ACM에서 발급한 공인 인증서는 무료이고, 조건이 맞으면 자동 갱신된다.

반대로 외부에서 구매해서 ACM에 업로드한 인증서는 직접 갱신해야 한다.

## ACM과 통합되는 서비스

ACM 인증서는 보통 AWS 관리형 엔드포인트에 붙인다.

대표 예:

- ALB
- NLB
- Elastic Beanstalk이 만든 로드 밸런서
- CloudFront
- API Gateway

즉 EC2 안의 Nginx/Apache에 ACM public certificate의 private key를 내려받아 직접 설치하는 방식이 아니다.

ACM이 인증서를 관리하고, ALB/CloudFront/API Gateway 같은 서비스가 TLS handshake와 TLS 종료를 처리한다.

## ALB에서 TLS 종료

ALB에 ACM 인증서를 붙이면 클라이언트와 ALB 사이가 HTTPS가 된다.

```text
Client
→ HTTPS
→ ALB가 TLS 종료
→ HTTP 또는 HTTPS
→ EC2
```

ALB가 TLS 종료를 하면 EC2는 인증서 관리나 TLS 복호화 CPU 비용을 덜 수 있다.

Target Group을 HTTP로 잡으면 ALB 뒤쪽은 평문 HTTP이고, 내부 구간까지 암호화해야 하면 ALB에서 EC2로도 HTTPS를 설정한다.

## Public Certificate와 Private Certificate

ACM에서는 public certificate와 private certificate를 다룰 수 있다.

Public certificate:

- 인터넷 사용자가 접속하는 공개 도메인용
- 공인 CA가 신뢰하는 인증서
- DNS 검증 또는 이메일 검증 필요
- ACM에서 발급하면 자동 갱신 가능

Private certificate:

- 내부 애플리케이션용
- 사설 CA로 발급
- 외부 브라우저/클라이언트가 자동으로 신뢰하지 않음
- 해당 애플리케이션이나 클라이언트가 private CA를 신뢰하도록 설정해야 함

쉽게 말하면 public certificate는 인터넷용, private certificate는 회사 내부 시스템용이다.

## ACM은 리전 서비스

ACM은 리전 서비스다.

즉 서울 리전 ALB에 붙일 인증서는 서울 리전 ACM에 있어야 한다.

버지니아 리전 ALB에 붙일 인증서는 버지니아 리전 ACM에 있어야 한다.

```text
ap-northeast-2 ALB
→ ap-northeast-2 ACM 인증서 필요

us-east-1 ALB
→ us-east-1 ACM 인증서 필요
```

ACM 인증서를 리전 간 복사해서 쓰는 개념이 아니다. 같은 도메인이라도 리전별로 인증서를 발급해야 한다.

CloudFront는 글로벌 서비스라 예외적으로 ACM 인증서를 `us-east-1` 리전에 만들어서 연결한다.

## 시험용 요약

ACM은 AWS에서 SSL/TLS 인증서를 발급하고 관리하는 서비스다.

ACM에서 발급한 public certificate는 무료이고 자동 갱신된다.

외부 인증서를 ACM에 업로드할 수 있지만, 이 경우 갱신은 직접 해야 한다.

ACM 인증서는 ALB, NLB, CloudFront, API Gateway 등에 붙여 TLS 종료에 사용한다.

Private certificate는 내부용이며, 클라이언트가 private CA를 신뢰하도록 설정해야 한다.

ACM은 리전 서비스라 ALB가 있는 각 리전에 인증서가 필요하다.

CloudFront에 붙일 ACM 인증서는 `us-east-1` 리전에 있어야 한다.

# CloudHSM

## CloudHSM 요약표

| 항목 | 내용 |
| --- | --- |
| 정체 | AWS에서 제공하는 전용 Hardware Security Module |
| 핵심 목적 | 암호화 키를 전용 하드웨어 안에서 직접 관리 |
| AWS 책임 | HSM 하드웨어 프로비저닝/인프라 제공 |
| 사용자 책임 | 키 생성, 보관, 백업, 사용자, 권한, 보안 관리 |
| 키를 잃어버리면 | AWS가 복구해줄 수 없음 |
| 테넌시 | 단일 테넌트 |
| 암호화 방식 | 대칭/비대칭 암호화, 디지털 서명, 해싱 지원 |
| 접근 방식 | KMS API가 아니라 CloudHSM Client 사용 |
| 권한 관리 | IAM이 아니라 CloudHSM 자체 사용자/권한 |
| HA 구성 | 여러 AZ에 HSM 디바이스를 둔 CloudHSM Cluster 구성 |
| 네트워크 | 특정 VPC에 배포, VPC Peering 등으로 공유 가능 |
| 사용 예 | SSL/TLS 오프로딩, Oracle TDE, Redshift, SSE-C 키 생성 |
| 규정 준수 | 변조 방지 하드웨어, FIPS 140-2 Level 3 |
| 비용 | 무료 티어 없음 |

## KMS vs CloudHSM

| 비교 | KMS | CloudHSM |
| --- | --- | --- |
| 서비스 성격 | AWS 관리형 키 관리 서비스 | 전용 HSM 클러스터 |
| 테넌시 | 다중 테넌트 | 단일 테넌트 |
| 키 관리 책임 | AWS와 사용자 분담 | 사용자 책임이 훨씬 큼 |
| 키 종류 | AWS owned, AWS managed, customer managed key | 고객이 직접 관리하는 키 |
| 권한 관리 | IAM + Key Policy | CloudHSM 자체 사용자/권한 |
| 접근 방식 | KMS API | CloudHSM Client |
| AWS 서비스 통합 | 매우 넓음 | 제한적, 일부 서비스 연동 |
| HA | 서비스에 내장 | 여러 AZ에 HSM을 직접 구성 |
| 키 위치 | KMS 리전 범위, 다중 리전 키 가능 | 특정 VPC의 CloudHSM 클러스터 |
| 암호화 기능 | 대칭/비대칭, 서명 등 | 대칭/비대칭, 서명, 해싱, 암호화 가속 |
| SSL/TLS 오프로딩 | 직접 목적 아님 | 가능 |
| Oracle TDE | 보통 KMS 통합 또는 DB 옵션 사용 | CloudHSM 연동 가능 |
| 감사 | CloudTrail 중심 | CloudTrail/CloudWatch + CloudHSM 자체 관리 |
| MFA | IAM/MFA 정책과 연계 | CloudHSM 자체 MFA 지원 |
| 무료 티어 | 있음 | 없음 |
| 추천 상황 | 대부분의 AWS 암호화 요구사항 | 전용 HSM/강한 키 통제/규정 요구 |

## 시험용 한 줄

| 포인트 | 기억할 말 |
| --- | --- |
| KMS | 편하고 AWS 서비스 통합이 넓은 관리형 키 관리 |
| CloudHSM | 어렵고 비싸지만 전용 하드웨어에서 키를 직접 통제 |
| 책임 차이 | CloudHSM은 키 보안/백업/사용자 관리가 사용자 책임 |
| HA 차이 | KMS는 내장, CloudHSM은 다중 AZ 클러스터 직접 구성 |

# S3 Object Lambda

## 핵심 개념

S3 Object Lambda는 S3 객체를 애플리케이션에 반환하기 직전에 Lambda 함수로 가공해서 돌려주는 기능이다.

중요한 점은 원본 객체를 바꾸는 게 아니라, 요청자에게 나가는 응답만 변환한다는 것이다.

```text
애플리케이션
→ S3 Object Lambda Access Point
→ Lambda 함수 실행
→ 원본 S3 객체 읽기
→ 내용 가공
→ 가공된 객체 응답
```

즉 같은 S3 버킷 하나를 두고도 애플리케이션마다 다른 형태의 객체를 받을 수 있다.

## “삭제된 객체”라는 말의 의미

강의에서 말하는 “삭제된 객체”는 S3 객체 자체가 삭제됐다는 뜻이 아니다.

정확히는 객체 내용 중 일부가 삭제/마스킹된 버전, 즉 redacted object를 말한다.

예를 들어 원본 객체가 이렇다고 하자.

```json
{
  "name": "Kim",
  "email": "kim@example.com",
  "cardNumber": "1234-5678-9999-0000"
}
```

분석 애플리케이션에는 PII나 카드번호를 보여주면 안 되므로, Object Lambda가 응답 직전에 내용을 지운다.

```json
{
  "name": "Kim",
  "email": "***",
  "cardNumber": "***"
}
```

이때 S3 버킷의 원본 객체는 그대로 있고, 분석 애플리케이션만 민감정보가 제거된 응답을 받는다.

## 왜 쓰는가

원본 버킷을 여러 개로 복사하지 않고, 요청자별로 필요한 형태의 데이터를 즉석에서 만들기 위해 쓴다.

```text
원본 버킷 하나
├─ 전자상거래 앱: 원본 객체 조회
├─ 분석 앱: PII 제거된 객체 조회
└─ 마케팅 앱: 고객 충성도 정보가 보강된 객체 조회
```

객체별 변환본을 미리 저장해두지 않아도 되므로, 중복 저장과 데이터 동기화 부담을 줄일 수 있다.

## 구성 요소

| 구성 요소 | 역할 |
| --- | --- |
| S3 Bucket | 원본 객체 저장 |
| S3 Access Point | 원본 버킷에 접근하는 지원 액세스 포인트 |
| Lambda Function | 객체를 읽은 뒤 변환하는 코드 |
| Object Lambda Access Point | 애플리케이션이 호출하는 변환 전용 엔드포인트 |

## 활용 사례

| 사용 사례 | 설명 |
| --- | --- |
| PII 제거 | 분석/비프로덕션 환경에 개인정보 제거 후 제공 |
| 형식 변환 | XML을 JSON으로 변환 |
| 이미지 처리 | 요청 시 이미지 리사이즈 |
| 워터마크 | 사용자에게 반환되는 이미지에만 워터마크 추가 |
| 데이터 보강 | 고객 DB나 충성도 DB 정보를 붙여 응답 |
| 메타데이터 조정 | HEAD/LIST 요청 결과를 애플리케이션에 맞게 수정 |

## 현재 서비스 주의점

AWS 문서 기준으로 2025년 11월 7일부터 S3 Object Lambda는 기존 사용 고객과 일부 APN 파트너에게만 제공된다.

시험에서는 개념이 나올 수 있으니 “S3 객체를 반환하기 직전에 Lambda로 변환한다”는 구조를 기억한다.

## 시험용 요약

S3 Object Lambda는 S3 Access Point와 Lambda를 이용해 S3 객체 응답을 즉석에서 변환한다.

원본 객체를 수정하거나 복사본 버킷을 만드는 게 아니라, 요청자에게 반환되는 결과만 바꾼다.

PII 제거, XML to JSON 변환, 이미지 리사이즈, 워터마크, 데이터 보강에 사용할 수 있다.

“삭제된 객체”는 삭제된 파일이 아니라 민감정보가 제거된 응답 버전을 뜻한다.

# DDoS 방어

## DDoS 핵심

DDoS는 여러 봇/공격자가 대량 트래픽을 보내서 서버가 정상 사용자 요청을 처리하지 못하게 만드는 공격이다.

## 공격 유형

| 유형 | 설명 |
| --- | --- |
| SYN Flood | TCP 연결 요청을 대량으로 보내는 Layer 4 공격 |
| UDP Reflection | UDP 트래픽을 반사시켜 대량 요청 유도 |
| DNS Flood | DNS 서버를 마비시켜 도메인 조회 불가 |
| Slow Loris | HTTP 연결을 오래 붙잡아 서버 리소스 고갈, Layer 7 공격 |
| Application Attack | 캐시 무효화, 큰 요청, 비싼 API 호출 등 앱 특화 공격 |

## AWS DDoS 방어 서비스

| 서비스 | 시험 포인트 |
| --- | --- |
| AWS Shield Standard | 무료, 기본 활성화, Layer 3/4 DDoS 방어 |
| AWS Shield Advanced | 유료, 24/7 DDoS Response Team, 비용 보호, 더 강한 보호 |
| AWS WAF | Layer 7 애플리케이션 요청 필터링, 규칙 기반 차단 |
| CloudFront | 엣지에서 트래픽 흡수/완화, Shield 적용 |
| Route 53 | 고가용 DNS, Shield 적용 |
| Auto Scaling | 공격 트래픽이 들어와도 인스턴스 확장으로 버팀 |
| S3 + CloudFront | 정적 콘텐츠를 분리해서 오리진 부하 감소 |

## Shield Standard vs Shield Advanced

| 구분 | Shield Standard | Shield Advanced |
| --- | --- | --- |
| 비용 | 무료 | 유료 |
| 적용 | 모든 AWS 고객 기본 적용 | 선택 가입 |
| 방어 | SYN/UDP Reflection 등 Layer 3/4 기본 DDoS | 더 정교한 DDoS |
| 보호 대상 | 기본 AWS 리소스 | EC2, ELB, CloudFront, Global Accelerator, Route 53 등 |
| 대응팀 | 없음 | 24/7 DDoS Response Team |
| 비용 보호 | 없음 | DDoS로 인한 스케일링 비용 보호 |

## 시험용 아키텍처

```text
Route 53
→ CloudFront + WAF
→ ALB
→ Auto Scaling Group
```

정적 파일은 S3 + CloudFront로 분리해서 EC2/ALB 오리진 부하를 줄인다.

## 시험용 요약

DDoS 기본 방어는 Shield Standard다.

애플리케이션 계층 필터링은 WAF가 담당한다.

엣지 방어와 트래픽 흡수는 CloudFront와 Route 53이 중요하다.

엔터프라이즈급 대응, DDoS Response Team, 비용 보호가 필요하면 Shield Advanced를 사용한다.

# WAF

## WAF 핵심

WAF는 Web Application Firewall이다.

Layer 7 HTTP/HTTPS 웹 공격을 방어하는 서비스다.

DDoS의 기본 방어는 Shield가 담당하고, WAF는 SQL Injection, XSS, 비정상 HTTP 패턴, rate 기반 요청 폭주 같은 애플리케이션 계층 공격을 막는다.

## WAF 적용 대상

| 적용 대상 | 시험 포인트 |
| --- | --- |
| ALB | 리전 단위 웹 보호 |
| API Gateway | 리전/엣지 API 보호 |
| CloudFront | 모든 엣지 로케이션에서 전역 보호 |
| AppSync | GraphQL API 보호 |

CLB, EC2, S3 Website, custom origin을 보호하려면 보통 CloudFront 앞에 두고 CloudFront에 WAF를 연결한다.

## Web ACL 규칙 조건

| 조건 | 예시 |
| --- | --- |
| IP 주소 | 특정 IP 차단/허용 |
| HTTP Header | 특정 헤더 값 검사 |
| HTTP Body | 본문 패턴 검사 |
| URI String | 특정 경로 차단 |
| SQL Injection | SQLi 방어 |
| XSS | Cross-site scripting 방어 |
| Size Constraint | 요청 크기 제한 |
| Geo Match | 특정 국가 차단/허용 |
| Rate-based Rule | 일정 횟수 이상 요청하면 차단 |

## WAF Rule Action

| Action | 의미 |
| --- | --- |
| Allow | 허용 |
| Block | 차단 |
| Count | 차단하지 않고 카운트만 함. 규칙 테스트/오탐 확인용 |
| CAPTCHA | 사용자 검증 후 통과 |

`Count`는 새 규칙을 바로 차단으로 걸기 전에 오탐을 확인할 때 중요하다.

## Managed Rules

| 종류 | 예시 |
| --- | --- |
| Baseline Rule Groups | CommonRuleSet, AdminProtectionRuleSet |
| Use-case Specific | SQLi, Windows, PHP, WordPress |
| IP Reputation | AmazonIpReputationList, Anonymous IP |
| Bot Control | BotControlRuleSet |

관리형 규칙은 AWS나 AWS Marketplace 셀러가 제공하는 ready-to-use 규칙이다.

## WAF Logging

| 대상 | 포인트 |
| --- | --- |
| CloudWatch Logs | 초당 최대 5MB 전송 |
| S3 | 약 5분마다 로그 전달 |
| Kinesis Data Firehose | 대량 로그/고급 라우팅에 적합, S3/Redshift/OpenSearch 등으로 전달 가능 |

트래픽이 많고 로깅 요구가 크면 Kinesis Data Firehose를 고려한다.

## CloudFront에서 온 요청만 ALB 허용

직접 ALB URL로 접근하는 것을 막고, CloudFront를 거친 요청만 허용하는 패턴이다.

```text
1. CloudFront가 origin 요청에 커스텀 헤더 추가
   X-Origin-Verify: secret-value

2. ALB에 WAF 연결

3. ALB WAF에서 해당 헤더가 있는 요청만 허용

4. 헤더 없으면 차단
```

보안 강화:

```text
Secrets Manager + Lambda
→ secret 헤더 값 주기적 교체
→ CloudFront 설정과 WAF 규칙도 같이 업데이트
```

## WAF 시험용 요약

WAF는 Layer 7 웹 공격 방어용이다.

ALB, API Gateway, CloudFront, AppSync에 붙일 수 있다.

관리형 규칙, Count 액션, Rate-based Rule, WAF Logging이 시험 포인트다.

CloudFront custom header + ALB WAF로 ALB 직접 접근을 차단할 수 있다.

# Firewall Manager

Firewall Manager는 AWS Organizations 전체 계정에 보안 정책을 중앙 배포/관리하는 서비스다.

## Firewall Manager 적용 대상

| 관리 대상 | 예시 |
| --- | --- |
| AWS WAF | ALB, API Gateway, CloudFront 등에 Web ACL 배포 |
| Shield Advanced | 여러 계정/리소스에 DDoS 고급 보호 적용 |
| Security Group 정책 | EC2, ALB, ENI 보안 그룹 관리 |
| AWS Network Firewall | VPC 수준 방화벽 정책 관리 |
| Route 53 Resolver DNS Firewall | DNS 방화벽 정책 관리 |

## WAF, Shield, Firewall Manager 차이

| 서비스 | 역할 |
| --- | --- |
| WAF | 개별 리소스의 Layer 7 웹 공격 방어 |
| Shield | DDoS 방어 |
| Firewall Manager | 여러 계정/리소스에 WAF/Shield/방화벽 정책을 중앙 배포 |

## Firewall Manager 시험용 요약

한 리소스만 보호하면 WAF를 직접 설정한다.

여러 계정/여러 리소스에 같은 WAF 규칙을 자동 적용하려면 Firewall Manager를 사용한다.

새 ALB 같은 리소스가 생겨도 정책 대상이면 Firewall Manager가 보안 정책을 자동 적용할 수 있다.

Shield Advanced를 조직 전체에 배포할 때도 Firewall Manager를 사용할 수 있다.

# 네트워크 방어선: IP 차단 위치

## 아키텍처별 차단 위치

| 아키텍처 | 클라이언트 IP 차단 위치 | 핵심 포인트 |
| --- | --- | --- |
| Client → EC2 Public IP | NACL | VPC/Subnet 레벨에서 특정 IP `Deny` 가능. 빠르고 저렴 |
| Client → EC2 Public IP | Security Group | `Deny` 불가, `Allow`만 가능. 허용할 IP 범위를 알 때 유용 |
| Client → EC2 Public IP | EC2 Host Firewall | 인스턴스 내부에서 차단. 이미 EC2까지 트래픽이 도달해서 CPU 사용 발생 |
| Client → ALB → EC2 | ALB Security Group | 클라이언트 IP 범위를 알면 ALB SG에서 허용 범위 제한 가능 |
| Client → ALB → EC2 | EC2 Security Group | EC2 입장에서는 소스가 클라이언트가 아니라 ALB. EC2 SG는 ALB SG만 허용 |
| Client → ALB → EC2 | NACL | 글로벌 앱처럼 ALB SG가 `0.0.0.0/0` 허용이면 NACL에서 특정 IP 차단 가능 |
| Client → ALB + WAF → EC2 | WAF | ALB에 연결해서 IP 필터링, Rate-based rule, Layer 7 조건 필터링 가능 |
| Client → CloudFront → ALB → EC2 | ALB/NACL | ALB/NACL에서 보이는 소스 IP는 보통 클라이언트가 아니라 CloudFront IP |
| Client → CloudFront → ALB → EC2 | CloudFront Geo Restriction | 특정 국가 단위 차단 가능 |
| Client → CloudFront + WAF → ALB → EC2 | WAF | CloudFront 앞단에서 특정 IP, HTTP 조건, Rate-based rule 차단 가능 |

## 보안 그룹 구성 포인트

| 대상 | 허용해야 하는 소스 |
| --- | --- |
| ALB Security Group | 클라이언트 IP 범위 또는 `0.0.0.0/0` |
| EC2 Security Group behind ALB | ALB Security Group |
| Load Balancer 뒤 EC2 | Load Balancer Security Group |
| CloudFront 뒤 ALB | CloudFront IP 범위 또는 CloudFront custom header + WAF 패턴 |

## 방어선 비교

| 방어선 | Deny 가능? | 장점 | 단점 |
| --- | --- | --- | --- |
| NACL | 가능 | 빠르고 저렴, subnet 레벨 차단 | Stateless, 규칙 관리 필요 |
| Security Group | 불가 | Stateful, 리소스 단위 허용 제어 | 차단 규칙 없음 |
| Host Firewall | 가능 | OS 내부에서 세밀한 차단 | 이미 인스턴스까지 도달해서 리소스 소모 |
| WAF | 가능 | Layer 7 조건, IP, rate-limit 가능 | 비용 발생, HTTP/HTTPS 중심 |
| CloudFront Geo Restriction | 가능 | 국가 단위 차단 쉬움 | 세밀한 IP/요청 조건은 WAF가 더 적합 |

## 시험용 요약

EC2 직접 접근은 NACL, Security Group, Host Firewall을 비교한다.

Security Group은 `Deny`가 없고 `Allow`만 있다.

ALB 뒤 EC2는 EC2 Security Group에서 클라이언트 IP가 아니라 ALB Security Group을 허용한다.

CloudFront 앞단이 있으면 ALB/NACL에서 보이는 소스는 보통 클라이언트가 아니라 CloudFront IP다.

CloudFront 뒤에서 클라이언트 IP/HTTP 조건을 차단하려면 WAF나 Geo Restriction을 사용한다.

# Amazon Inspector

## Inspector 핵심

Amazon Inspector는 취약점 관리 서비스다.

워크로드를 자동으로 발견하고 계속 스캔해서 소프트웨어 취약점과 의도하지 않은 네트워크 노출을 finding으로 만든다.

## 스캔 대상

| 대상 | 시험 포인트 |
| --- | --- |
| EC2 | CVE, 네트워크 노출, 네트워크 도달 가능성, OS/패키지 취약점 스캔 |
| ECR | 컨테이너 이미지 취약점 스캔, enhanced scanning |
| Lambda | 함수와 Layer의 의존성 취약점 스캔 |
| Lambda Code Scanning | 선택 기능, Lambda 코드 취약점 스캔 |

EC2 스캔은 SSM Agent 또는 EBS snapshot 기반 agentless scanning을 사용할 수 있다.

## 운영 포인트

| 항목 | 내용 |
| --- | --- |
| 스캔 방식 | 수동 1회 점검보다 지속적 자동 스캔에 가까움 |
| 재스캔 | 새 패키지 설치, 패치, 새 CVE 공개, Lambda 업데이트 등에 반응 |
| Finding | 취약점 세부 정보, 영향받은 리소스, remediation 권장사항 포함 |
| Risk Score | CVSS 기반이지만 AWS 환경 맥락을 반영해 조정 |
| Organizations | 위임 관리자 계정으로 조직 전체 Inspector 중앙 관리 가능 |
| EventBridge | finding 이벤트를 EventBridge로 보내 자동 대응 가능 |
| Security Hub | finding을 Security Hub로 통합 가능 |

## 시험용 요약

Inspector는 EC2, ECR 이미지, Lambda의 취약점을 지속적으로 스캔한다.

GuardDuty가 위협 탐지라면, Inspector는 취약점 스캔/취약점 관리에 가깝다.

EC2는 SSM Agent 또는 EBS snapshot 기반 agentless scanning이 포인트다.

Organizations 위임 관리자로 여러 계정의 Inspector finding을 중앙 관리할 수 있다.

Inspector finding은 EventBridge와 Security Hub로 연동할 수 있다.

# Systems Manager와 AWS Config

## AWS Systems Manager

AWS Systems Manager는 EC2와 서버 운영 작업을 중앙에서 관리하는 서비스다.

보통 SSM이라고 부른다.

## Systems Manager 주요 기능

| 기능 | 하는 일 |
| --- | --- |
| Session Manager | SSH 없이 EC2에 접속 |
| Run Command | 여러 EC2에 명령어 원격 실행 |
| Patch Manager | OS 패치 자동화 |
| Parameter Store | 설정값/간단한 비밀값 저장 |
| Automation | 런북 기반 자동 복구/작업 |
| Inventory | 서버 소프트웨어/설정 정보 수집 |
| State Manager | 인스턴스가 원하는 상태를 유지하게 관리 |
| Maintenance Windows | 정해진 시간에 작업 실행 |
| OpsCenter | 운영 이슈 모아서 관리 |

SSM을 쓰려면 보통 EC2에 SSM Agent가 있어야 하고, 인스턴스에는 Systems Manager 접근 권한이 있는 IAM Role이 필요하다.

## SSM Automation

SSM Automation은 Systems Manager의 런북 기반 자동화 기능이다.

사람이 콘솔에서 하던 반복 작업이나 복구 작업을 문서로 만들어 자동 실행한다.

예:

```text
AWS Config가 보안 그룹 22번 public open 감지
→ NON_COMPLIANT
→ SSM Automation Runbook 실행
→ 해당 ingress rule 삭제
```

즉 Config가 문제를 찾고, SSM Automation이 고치는 구조로 자주 나온다.

## AWS Config

AWS Config는 AWS 리소스의 설정 상태를 기록하고, 규칙에 맞는지 평가하는 서비스다.

중요한 점은 Config가 변경을 사전에 막는 서비스는 아니라는 것이다.

```text
SCP = API 실행 전 차단
Config = 변경 후 상태 기록/평가/감지
SSM Automation = 감지된 문제 자동 수정
```

## Config를 쓰는 이유

| 용도 | 설명 |
| --- | --- |
| 변경 이력 기록 | 리소스가 언제, 어떻게 바뀌었는지 추적 |
| 규정 준수 평가 | Config Rule로 COMPLIANT/NON_COMPLIANT 판단 |
| 기존 리소스 검사 | 예전에 만들어진 잘못된 리소스도 찾아냄 |
| 자동 수정 | Remediation으로 SSM Automation 실행 가능 |
| 감사 증거 | 보안 감사/컴플라이언스 보고에 사용 |

## 예시

| 요구사항 | 적합한 서비스 |
| --- | --- |
| SSH 22번 포트를 절대 열지 못하게 막기 | SCP |
| SSH 22번 포트가 열린 보안 그룹 찾기 | AWS Config |
| 열린 SSH 규칙을 자동으로 닫기 | Config Remediation + SSM Automation |
| SSH 없이 EC2 접속하기 | SSM Session Manager |
| 여러 EC2에 명령 실행하기 | SSM Run Command |

## 시험용 요약

Systems Manager는 EC2/서버 운영 관리를 중앙화하는 서비스다.

Session Manager를 쓰면 SSH 없이 EC2에 접속할 수 있어 22번 포트를 열 필요가 줄어든다.

SSM Automation은 런북 기반 자동화이고, Config Remediation과 자주 같이 나온다.

AWS Config는 리소스 설정 변경 이력과 규정 준수 상태를 기록/평가한다.

Config는 사전 차단이 아니라 사후 감지/기록/자동 수정 쪽이고, 절대 금지는 SCP가 더 적합하다.

# AWS 관리형 로그

AWS 관리형 로그는 AWS 서비스가 자동으로 만들어주는 운영/보안 분석용 로그다.

시험에서는 “어떤 로그가 무엇을 기록하고, 어디로 보낼 수 있는지”를 구분하면 된다.

| 로그 | 기록하는 것 | 보낼 수 있는 곳 |
| --- | --- | --- |
| Load Balancer Access Log | ALB/CLB 요청 상세 정보, NLB TLS 연결 정보 | S3 |
| CloudTrail Log | 계정 내 AWS API 호출 기록 | S3, CloudWatch Logs |
| VPC Flow Log | VPC 네트워크 인터페이스의 IP 트래픽 정보 | S3, CloudWatch Logs, Kinesis Data Firehose |
| Route 53 Query Log | Public hosted zone DNS 쿼리 정보 | CloudWatch Logs |
| Route 53 Resolver Query Log | VPC Resolver DNS 쿼리 정보 | CloudWatch Logs, S3, Kinesis Data Firehose |
| S3 Access Log | S3 버킷에 대한 객체 요청/접근 정보 | 다른 S3 버킷 |
| CloudFront Access Log | CloudFront가 받은 사용자 요청 상세 정보 | S3 |
| AWS Config 기록 | AWS 리소스 구성 변경/상태 정보 | S3 |

## 시험용 요약

CloudTrail은 API 호출 기록, VPC Flow Log는 네트워크 트래픽, Access Log는 서비스로 들어온 요청 기록이다.

S3는 로그 장기 보관에 자주 쓰이고, CloudWatch Logs는 검색/알람/실시간 분석에 자주 쓰인다.

Kinesis Data Firehose는 대량 로그를 S3, Redshift, OpenSearch 등으로 보내는 스트리밍 전달용으로 생각한다.

# Amazon GuardDuty

GuardDuty는 CloudTrail, VPC Flow Logs, DNS Logs 등을 분석해서 AWS 계정의 이상 행위와 위협을 탐지하는 서비스다.

머신러닝, 이상 탐지, 위협 인텔리전스를 사용하며 소프트웨어 설치 없이 활성화할 수 있고, 암호화폐 채굴 공격 탐지에도 자주 언급된다.

탐지 결과는 finding으로 생성되고 EventBridge를 통해 Lambda/SNS 등으로 자동 대응할 수 있으며, AWS Organizations에서는 관리 계정이 멤버 계정을 GuardDuty 위임 관리자로 지정해 조직 전체 GuardDuty를 관리하게 할 수 있다.

## GuardDuty가 분석하는 데이터

| 구분 | 데이터 소스 | 포인트 |
| --- | --- | --- |
| 기본 | CloudTrail Management Events | API 호출, IAM/STS/EC2 같은 control plane 이상 행위 탐지 |
| 기본 | VPC Flow Logs | EC2 네트워크 트래픽, 악성 IP 통신, 포트 스캔 등 탐지 |
| 기본 | Route 53 Resolver DNS Query Logs | EC2가 AWS DNS Resolver를 쓸 때 악성 도메인/DNS 터널링 의심 탐지 |
| 선택 | S3 Protection | S3 CloudTrail Data Events, `GetObject`, `PutObject`, `DeleteObject` 등 객체 수준 이상 행위 탐지 |
| 선택 | EKS Audit Logs / Runtime Monitoring | EKS 제어 plane 감사 로그와 런타임 이벤트 탐지 |
| 선택 | Runtime Monitoring | EKS, ECS Fargate, EC2의 프로세스/파일/네트워크 런타임 이벤트 탐지 |
| 선택 | Malware Protection for EC2 | EC2/EKS on EC2의 EBS 볼륨을 스냅샷 기반으로 악성코드 스캔 |
| 선택 | RDS Protection | 지원 DB의 로그인 활동, brute force나 비정상 로그인 탐지 |
| 선택 | Lambda Protection | Lambda 네트워크 활동 로그 기반 이상 트래픽 탐지 |

GuardDuty는 위 로그를 내 계정의 CloudWatch Logs/S3 로그 설정에서 직접 가져가는 방식이 아니라, 독립적인 이벤트 스트림으로 분석한다. 그래서 GuardDuty 때문에 기존 CloudTrail, VPC Flow Logs 설정이 바뀌지는 않는다.

## GuardDuty에 포함되지 않는 로그

| 로그 | GuardDuty와의 관계 |
| --- | --- |
| ALB/NLB/CLB Access Log | GuardDuty 기본 분석 소스가 아님 |
| CloudFront Access Log | GuardDuty 기본 분석 소스가 아님 |
| S3 Server Access Log | GuardDuty는 이 로그가 아니라 S3 Protection의 CloudTrail S3 Data Events를 봄 |
| WAF Logs | GuardDuty 기본 분석 소스가 아님 |
| AWS Config 기록 | GuardDuty 분석 소스가 아니라 리소스 설정 이력/규정 준수용 |
| 임의의 CloudWatch Application Logs | GuardDuty가 일반 앱 로그를 분석하는 서비스는 아님 |
| 커스텀 DNS Resolver 로그 | EC2가 OpenDNS/Google DNS/자체 DNS를 쓰면 GuardDuty의 Route 53 Resolver DNS 소스로 분석되지 않음 |
| 일반 RDS 엔진 로그 | RDS Protection은 지원 DB의 로그인 활동을 보는 것이지 모든 SQL/엔진 로그를 분석하는 것은 아님 |

## GuardDuty 시험용 요약

기본 데이터 소스는 CloudTrail Management Events, VPC Flow Logs, Route 53 Resolver DNS Query Logs다.

S3, EKS, Runtime Monitoring, Malware Protection, RDS, Lambda는 보호 플랜을 켜서 추가 분석할 수 있다.

GuardDuty는 위협 탐지 서비스이고, Inspector는 취약점 스캔, Security Hub는 finding 통합, Detective는 원인 조사에 가깝다.

## Security Hub와 Detective

| 서비스 | 시험용 핵심 |
| --- | --- |
| AWS Security Hub | GuardDuty, Inspector, Macie, IAM Access Analyzer 같은 보안 finding과 보안 표준 점검 결과를 한곳에 모아 보안 상태를 통합해서 보여준다. |
| Amazon Detective | GuardDuty finding 같은 보안 이벤트를 리소스, API 호출, 네트워크 활동 그래프로 연결해서 원인 조사와 포렌식 분석을 돕는다. |

# IAM 조건

IAM 조건은 정책이 적용되는 상황을 제한하는 조건문이다.

IAM 사용자/Role 정책, 리소스 기반 정책, S3 버킷 정책, VPC Endpoint Policy, SCP 등에서 사용할 수 있다.

## 자주 나오는 조건 키

| 조건 키 | 의미 | 사용 예 |
| --- | --- | --- |
| `aws:SourceIp` | API 호출 출발지 IP 제한 | 회사 네트워크 CIDR에서만 AWS API 허용 |
| `aws:RequestedRegion` | API 호출 대상 리전 제한 | 특정 리전에서 EC2/RDS/DynamoDB 사용 금지 |
| `ec2:ResourceTag/Project` | EC2 리소스 태그 기준 제한 | `Project=DataAnalytics` 인스턴스만 Start/Stop 허용 |
| `aws:PrincipalTag/Department` | IAM principal 태그 기준 제한 | `Department=Data` 사용자/Role만 특정 작업 허용 |
| `aws:MultiFactorAuthPresent` | MFA 여부 기준 제한 | MFA 없으면 EC2 Stop/Terminate 거부 |
| `aws:PrincipalOrgID` | AWS Organizations ID 기준 제한 | 우리 Organization 멤버 계정만 S3 접근 허용 |

## 조건 사용 예시 감각

`aws:SourceIp`는 “어디서 호출했는가”를 본다.

```text
회사 IP 대역이 아니면 Deny
```

`aws:RequestedRegion`은 “어느 리전에 API를 호출하는가”를 본다.

```text
eu-central-1, eu-west-1에서 특정 서비스 사용 Deny
```

`ResourceTag`는 “대상 리소스의 태그”를 본다.

```text
EC2 인스턴스 태그 Project=DataAnalytics이면 Start/Stop 허용
```

`PrincipalTag`는 “요청하는 사용자/Role의 태그”를 본다.

```text
사용자 태그 Department=Data이면 허용
```

`aws:PrincipalOrgID`는 리소스 정책에서 조직 외부 접근을 막을 때 유용하다.

```text
우리 AWS Organization 멤버 계정만 S3 PutObject/GetObject 허용
```

## S3 정책 ARN 주의

S3는 버킷 수준 권한과 객체 수준 권한의 ARN이 다르다.

| 권한 | ARN 형태 | 예 |
| --- | --- | --- |
| 버킷 수준 | `arn:aws:s3:::bucket-name` | `s3:ListBucket` |
| 객체 수준 | `arn:aws:s3:::bucket-name/*` | `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` |

예:

```text
ListBucket
→ arn:aws:s3:::test

GetObject / PutObject / DeleteObject
→ arn:aws:s3:::test/*
```

시험에서 S3 정책이 틀린 이유로 자주 나오는 포인트다.

## 시험용 요약

IAM 조건은 “누가, 어디서, 어떤 리전에, 어떤 리소스/태그 조건으로 요청했는가”를 기준으로 정책 적용을 제한한다.

`aws:`로 시작하는 조건 키는 전역 조건 키이고, `ec2:`처럼 서비스명이 붙으면 해당 서비스 리소스 조건이다.

S3 버킷 정책에서는 버킷 수준 ARN과 객체 수준 ARN을 구분해야 한다.

조직 내부 계정만 리소스에 접근시키려면 리소스 정책에서 `aws:PrincipalOrgID`를 사용할 수 있다.

# EC2 Instance Connect

EC2 Instance Connect는 `SendSSHPublicKey` API로 EC2 인스턴스에 일회성 SSH 공개 키를 밀어 넣고, 그 키를 60초 동안만 유효하게 해서 SSH 접속하게 하는 방식이다.

EC2 콘솔에서 브라우저 기반으로 직접 접속하는 경우에는 22번 포트를 EC2 Instance Connect 서비스 IP 범위에서 허용해야 한다.

내 로컬 SSH 클라이언트나 CLI로 직접 접속하는 경우에는 공개 키 주입은 EC2 Instance Connect API가 처리하지만, 실제 SSH 네트워크 연결은 내 클라이언트에서 인스턴스로 가므로 보안 그룹도 그 경로에 맞게 열려 있어야 한다.

`SendSSHPublicKey` API 호출은 CloudTrail에 기록되어 감사할 수 있다.
