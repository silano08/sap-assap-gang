# SAP VPC

# 큰 그림

VPC 섹션은 네트워크 연결 방식을 고르는 문제가 많다.
시험에서는 "연결은 되지만 보안/확장/중앙 관리/비용 요구사항이 다르다"는 식으로 선택지를 꼬아낸다.

```text
VPC끼리 단순 연결
→ VPC Peering

여러 VPC/온프레미스 허브 연결
→ Transit Gateway

AWS 서비스에 private 연결
→ VPC Endpoint

내 서비스를 다른 계정/VPC에 private하게 제공
→ PrivateLink

온프레미스와 암호화 터널
→ Site-to-Site VPN

개별 사용자의 VPN 접속
→ Client VPN

전용 회선
→ Direct Connect

트래픽 기록
→ VPC Flow Logs

VPC 레벨 방화벽
→ AWS Network Firewall
```

# VPC 기초

VPC는 AWS 안의 격리된 네트워크 공간이다.

기본 구성:

```text
VPC CIDR
→ Subnet
→ Route Table
→ Internet Gateway / NAT Gateway / Endpoint 등
```

시험에서 자주 구분하는 것:

```text
Public subnet
→ Route table에 Internet Gateway로 가는 route가 있음

Private subnet
→ Internet Gateway로 직접 나가는 route 없음
→ outbound internet은 NAT Gateway/Instance 사용
```

Security Group과 NACL:

| 구분 | Security Group | NACL |
| --- | --- | --- |
| 적용 대상 | ENI/인스턴스 단위 | Subnet 단위 |
| 상태 | Stateful | Stateless |
| 규칙 | Allow만 | Allow/Deny |
| 반환 트래픽 | 자동 허용 | 명시 필요 |

시험 감각:

```text
인스턴스 단위 접근 제어
→ Security Group

서브넷 단위 deny 규칙 필요
→ NACL
```

# VPC Peering

VPC Peering은 두 VPC를 직접 연결하는 방식이다.

중요 특징:

- CIDR가 겹치면 안 된다.
- 전이 라우팅이 안 된다.
- Peering을 통과해서 다른 VPC로 넘어갈 수 없다.
- 같은 리전뿐 아니라 cross-region peering도 가능하다.

```text
VPC A ↔ VPC B
VPC B ↔ VPC C

VPC A → VPC C
→ Peering만으로는 불가
```

시험 감각:

```text
두 VPC만 단순히 연결
CIDR 겹치지 않음
전이 라우팅 필요 없음
→ VPC Peering

VPC가 많고 full mesh가 복잡함
중앙 허브가 필요함
→ Transit Gateway
```

# Transit Gateway

Transit Gateway는 여러 VPC와 온프레미스 네트워크를 허브 앤 스포크로 연결하는 서비스다.

```text
VPC A
VPC B
VPC C
On-premises VPN/DX
→ Transit Gateway
```

시험 감각:

```text
수십/수백 개 VPC 연결
VPC Peering full mesh를 피하고 싶음
중앙 라우팅 허브 필요
온프레미스와 여러 VPC를 함께 연결
→ Transit Gateway
```

중요 포인트:

- TGW route table로 네트워크 간 통신 범위를 제어할 수 있다.
- 여러 계정의 VPC 연결은 RAM으로 공유하는 패턴이 나온다.
- Site-to-Site VPN, Direct Connect Gateway와 함께 하이브리드 네트워크 허브로 쓰인다.

# VPC Endpoint

VPC Endpoint는 인터넷/NAT/IGW를 거치지 않고 AWS 서비스에 private하게 접근하게 해준다.

두 종류:

| 종류 | 대상 | 특징 |
| --- | --- | --- |
| Gateway Endpoint | S3, DynamoDB | Route table에 붙음, 비용 효율적 |
| Interface Endpoint | 대부분의 AWS 서비스 | ENI 기반, PrivateLink 사용 |

시험 감각:

```text
Private subnet의 EC2가 S3/DynamoDB에 private하게 접근
NAT Gateway 비용을 줄이고 싶음
→ Gateway Endpoint

Private subnet에서 CloudWatch, SSM, KMS 등 AWS API에 private 접근
→ Interface Endpoint
```

VPC Endpoint Policy는 endpoint를 통해 어떤 리소스/액션에 접근할 수 있는지 제한한다.

```text
Endpoint Policy
→ 이 endpoint를 통해 접근 가능한 AWS API/리소스 제한

IAM Policy / Resource Policy
→ 최종 권한 평가에는 여전히 같이 참여
```

# PrivateLink

PrivateLink는 Interface Endpoint 기반으로, 다른 VPC/계정의 서비스를 private IP로 소비하게 해준다.

핵심 구조:

```text
Service Provider VPC
→ Network Load Balancer
→ Endpoint Service

Consumer VPC
→ Interface Endpoint
→ PrivateLink로 서비스 접근
```

시험 감각:

```text
VPC Peering 없이 서비스만 private하게 노출
CIDR 중복 문제를 피하고 싶다
Consumer가 provider VPC 전체에 접근하면 안 된다
서비스 단위 private 연결이 필요하다
→ AWS PrivateLink
```

PrivateLink와 Peering 차이:

```text
Peering
→ 네트워크끼리 연결
→ 라우팅으로 서로의 CIDR 접근

PrivateLink
→ 특정 서비스 엔드포인트만 연결
→ Provider VPC 전체 접근 불가
```

# Site-to-Site VPN

Site-to-Site VPN은 온프레미스 네트워크와 AWS를 인터넷 기반 IPSec 터널로 연결한다.

구성 요소:

```text
Customer Gateway, CGW
→ 온프레미스 쪽 장비

Virtual Private Gateway, VGW
→ VPC 쪽 게이트웨이

Transit Gateway
→ 여러 VPC 허브로 연결할 때 사용 가능
```

시험 감각:

```text
빠르게 온프레미스와 AWS를 연결
암호화된 터널 필요
전용 회선까지는 필요 없음
→ Site-to-Site VPN
```

라우팅:

```text
Static route
→ 단순 구성

Dynamic route, BGP
→ 경로 자동 교환, 장애 조치에 유리
```

# Client VPN

Client VPN은 개별 사용자가 노트북에서 VPN 클라이언트로 AWS VPC에 접속하는 서비스다.

```text
개별 사용자
→ OpenVPN 기반 Client VPN
→ VPC / on-premises network 접근
```

시험 감각:

```text
재택 근무자가 VPC 내부 리소스에 접속
사용자 단위 인증과 VPN 필요
→ AWS Client VPN
```

Site-to-Site VPN은 네트워크와 네트워크 연결이고, Client VPN은 사용자와 VPC 연결이다.

# Direct Connect

Direct Connect는 온프레미스와 AWS를 전용 회선으로 연결하는 서비스다.

시험 감각:

```text
일관된 대역폭과 낮은 지연 시간
인터넷을 거치지 않는 전용 연결
대규모 데이터 전송
하이브리드 네트워크의 안정적 연결
→ Direct Connect
```

중요 포인트:

- Direct Connect 자체는 암호화가 기본 제공되지 않는다.
- 암호화가 필요하면 VPN over Direct Connect 같은 조합을 고려한다.
- Public VIF는 AWS public service에 접근한다.
- Private VIF는 VPC private resource에 접근한다.
- Transit VIF는 Direct Connect Gateway와 Transit Gateway 연결에 사용한다.

```text
전용 회선 + 암호화 필요
→ Direct Connect + VPN
```

# On-Premise Redundant Connections

하이브리드 연결의 고가용성은 "하나만 연결하지 않는다"가 핵심이다.

패턴:

```text
VPN 2개 터널
→ 기본 VPN HA

Direct Connect 2개 이상
→ 서로 다른 DX location / device 권장

DX + VPN backup
→ DX 장애 시 VPN으로 failover
```

시험 감각:

```text
최고 수준의 하이브리드 연결 가용성
→ 여러 DX connection
→ 서로 다른 location
→ VPN backup까지 고려
```

# VPC Flow Logs

VPC Flow Logs는 ENI, subnet, VPC 레벨의 IP 트래픽 메타데이터를 기록한다.

저장 대상:

```text
CloudWatch Logs
S3
Kinesis Data Firehose
```

시험 감각:

```text
왜 통신이 안 되는지 네트워크 트래픽 확인
허용/거부된 IP 흐름 분석
보안 분석용 네트워크 로그 수집
→ VPC Flow Logs
```

주의:

- Flow Logs는 패킷 내용 전체를 캡처하는 서비스가 아니다.
- 트래픽의 source/destination, port, protocol, accept/reject 같은 메타데이터를 기록한다.

# AWS Network Firewall

AWS Network Firewall은 VPC에 배치하는 관리형 네트워크 방화벽이다.

시험 감각:

```text
VPC outbound/inbound/east-west 트래픽을 중앙에서 검사
도메인 기반 필터링
Suricata 호환 규칙
stateful/stateless 방화벽 필요
침입 탐지/방지 성격의 네트워크 보안
→ AWS Network Firewall
```

보통 중앙 검사 VPC, Transit Gateway와 함께 나오는 문제가 많다.

```text
여러 VPC 트래픽을 중앙 보안 VPC로 모아 검사
→ Transit Gateway + AWS Network Firewall
```
