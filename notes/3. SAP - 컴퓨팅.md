# SAP 컴퓨팅

# HPC, 고성능 컴퓨팅

HPC는 High Performance Computing이다.

쉽게 말하면:

```text
엄청 많은 계산을
짧은 시간 안에
많은 컴퓨팅 리소스로 병렬 처리하는 것
```

AWS에서 HPC가 잘 맞는 이유:

- 필요할 때 대량의 EC2 인스턴스를 빠르게 띄울 수 있다.
- 작업 속도를 높이고 싶으면 리소스를 더 붙이면 된다.
- 사용한 만큼만 비용을 낸다.
- 작업이 끝나면 인프라를 삭제해서 비용을 멈출 수 있다.

시험용 한 줄:

```text
HPC on AWS = 대량 데이터 + 고성능 컴퓨팅 + 빠른 네트워크 + 고성능 스토리지 + 자동화 조합
```

## HPC 사용 사례

- 유전학 분석
- 컴퓨터 화학
- 재무 위험 모델링
- 일기 예보
- 머신 러닝 / 딥 러닝
- 자율주행 시뮬레이션

핵심 감각:

```text
계산량이 크고,
병렬 처리가 가능하고,
짧은 시간에 결과가 필요한 작업
```

## 데이터 이동

HPC는 계산 전에 대량 데이터를 AWS로 옮기는 일이 중요하다.

### Direct Connect

- 온프레미스와 AWS를 전용 네트워크로 연결한다.
- 인터넷을 통하지 않는 private connection이다.
- GBps급 대역폭으로 안정적으로 대량 데이터를 전송할 수 있다.

시험 감각:

```text
온프레미스와 AWS 사이를 지속적으로 고속 연결
→ Direct Connect
```

### Snowball / Snowmobile

- 물리 장비로 데이터를 옮긴다.
- 네트워크로 전송하기 어려운 페타바이트급 데이터에 적합하다.
- 한 번에 대량 데이터를 AWS로 옮길 때 사용한다.

시험 감각:

```text
네트워크로 옮기기엔 너무 큰 데이터
→ Snowball / Snowmobile
```

### DataSync

- 온프레미스 스토리지와 AWS 스토리지 간 데이터 전송 서비스다.
- DataSync agent를 설치해서 사용한다.
- NFS / SMB 같은 온프레미스 파일 시스템에서 S3, EFS, FSx로 전송할 수 있다.

시험 감각:

```text
온프레미스 NFS/SMB → AWS S3/EFS/FSx 반복 전송
→ DataSync
```

## 컴퓨팅과 네트워킹

### EC2 인스턴스

HPC의 기본 컴퓨팅 리소스는 EC2다.

- CPU 최적화 인스턴스:
  - 일반 계산, 시뮬레이션, 수치 연산에 적합.
- GPU 최적화 인스턴스:
  - 머신 러닝, 딥 러닝, 그래픽/병렬 연산에 적합.

비용 최적화:

- Spot Instance / Spot Fleet:
  - 중단 가능하거나 재시도 가능한 HPC 작업 비용을 크게 줄일 수 있다.
- Auto Scaling:
  - 계산량에 따라 EC2 플릿을 늘리거나 줄인다.

### Cluster Placement Group

분산 계산에서 EC2 인스턴스끼리 빠르게 통신해야 하면 클러스터 배치 그룹을 쓴다.

- 동일 AZ 안에 인스턴스를 가깝게 배치한다.
- 낮은 지연 시간과 높은 네트워크 성능을 얻는다.
- HPC처럼 노드 간 통신이 많은 워크로드에 적합하다.

시험 감각:

```text
EC2끼리 아주 빠르게 통신해야 함
→ Cluster Placement Group
```

주의:

```text
Cluster Placement Group = 고성능 네트워크 배치 전략
Multi-AZ 고가용성 전략이 아님
```

## EC2 향상된 네트워킹

EC2 향상된 네트워킹은 SR-IOV 기반으로 더 높은 대역폭, 높은 PPS, 낮은 지연 시간을 제공한다.

```text
SR-IOV = 가상화 오버헤드를 줄여 네트워크 성능을 높이는 기술
```

### ENA, Elastic Network Adapter

- 최신 EC2 향상된 네트워킹 방식이다.
- 최대 100Gbps급 네트워킹을 지원한다.
- 높은 대역폭, 높은 PPS, 낮은 지연 시간이 핵심이다.

시험 감각:

```text
EC2 enhanced networking
→ ENA
```

### Intel 82599 VF

- 예전 방식의 향상된 네트워킹 옵션이다.
- 최대 10Gbps 수준.
- ENA보다 레거시 옵션으로 보면 된다.

시험에서는 이름이 나오면:

```text
Intel 82599 VF = 구형 enhanced networking
ENA = 최신 enhanced networking
```

### EFA, Elastic Fabric Adapter

EFA는 HPC 전용에 가까운 고성능 네트워크 어댑터다.

- ENA보다 HPC에 더 특화된 옵션이다.
- Linux에서만 사용한다.
- 노드 간 통신이 많은 tightly coupled workload에 적합하다.
- MPI(Message Passing Interface)를 사용하는 분산 계산에 적합하다.
- OS를 우회하는 방식으로 더 낮은 지연 시간과 안정적인 전송을 제공한다.

시험 감각:

```text
HPC + Linux + MPI + 노드 간 초저지연 통신
→ EFA
```

ENA / EFA / ENI 차이:

```text
ENI = EC2에 붙는 가상 네트워크 인터페이스
ENA = EC2 enhanced networking용 어댑터
EFA = HPC/MPI용 초저지연 네트워크 어댑터
```

## 스토리지

HPC는 계산 성능만큼 스토리지 성능도 중요하다.

### EBS

- EC2에 붙는 블록 스토리지다.
- `io2 Block Express`를 사용하면 매우 높은 IOPS를 제공한다.
- 강한 내구성과 일관된 성능이 필요할 때 사용한다.

시험 감각:

```text
고성능 블록 스토리지
→ EBS io2 Block Express
```

### Instance Store

- EC2 호스트에 직접 붙은 로컬 스토리지다.
- 매우 낮은 지연 시간과 높은 IOPS를 제공한다.
- 수백만 IOPS 수준까지 가능하다.
- 단, 인스턴스가 종료/손실되면 데이터도 사라질 수 있다.

시험 감각:

```text
가장 빠른 임시 로컬 스토리지
→ Instance Store

영구 저장 필요
→ EBS/S3/EFS/FSx 고려
```

### S3

- 대량 객체 저장소다.
- 파일 시스템이 아니라 object storage다.
- HPC 입력/출력 데이터, 원본 데이터, 결과물 저장에 자주 사용한다.

### EFS

- 여러 EC2에서 공유할 수 있는 Linux 파일 시스템이다.
- 파일 시스템 전체 규모에 따라 성능이 확장된다.
- Provisioned Throughput / Provisioned IOPS 계열 옵션으로 성능을 높일 수 있다.

### FSx for Lustre

HPC에서 가장 시험 포인트가 되는 파일 시스템이다.

- Lustre는 Linux와 HPC 클러스터에 많이 쓰이는 고성능 파일 시스템이다.
- 수백만 IOPS를 제공할 수 있다.
- S3와 연동해서 대량 데이터를 고성능 파일 시스템처럼 처리할 수 있다.

시험 감각:

```text
HPC 전용 고성능 파일 시스템
→ FSx for Lustre
```

S3와 FSx for Lustre 감각:

```text
S3 = 대량 데이터 저장소
FSx for Lustre = 계산 중 빠르게 읽고 쓰는 고성능 파일 시스템
```

## 자동화와 오케스트레이션

### AWS Batch

- 대량 배치 작업을 실행하고 스케줄링하는 서비스다.
- EC2 인스턴스 생성과 작업 실행을 AWS Batch가 관리한다.
- 다중 노드 병렬 작업을 실행할 수 있다.
- HPC 작업을 비교적 쉽게 실행할 때 적합하다.

시험 감각:

```text
대량 계산 작업을 큐에 넣고 EC2에서 자동 실행
→ AWS Batch
```

### AWS ParallelCluster

- AWS에서 HPC 클러스터를 배포하기 위한 오픈 소스 클러스터 관리 도구다.
- 텍스트 설정 파일로 클러스터를 정의한다.
- VPC, 서브넷, 인스턴스 유형, 클러스터 구성을 자동화할 수 있다.
- HPC 클러스터를 직접 구성해야 하는 경우에 적합하다.

시험 감각:

```text
AWS에 HPC 클러스터를 구성/관리하는 도구
→ AWS ParallelCluster
```

Batch와 ParallelCluster 차이:

```text
AWS Batch
= 작업 큐/스케줄링 중심
= 배치 작업을 AWS가 관리해서 실행

AWS ParallelCluster
= HPC 클러스터 구성 도구
= 클러스터 자체를 만들고 운영하는 느낌
```

```text
대량 데이터 전송

고성능 계산
→ CPU/GPU EC2, Spot Fleet, Auto Scaling

노드 간 빠른 통신
→ Cluster Placement Group

EC2 네트워크 성능 향상
→ ENA

HPC/MPI 초저지연 네트워크
→ EFA

고성능 로컬 임시 스토리지
→ Instance Store

고성능 블록 스토리지
→ EBS io2 Block Express

HPC 파일 시스템
→ FSx for Lustre

작업 큐 기반 실행
→ AWS Batch

HPC 클러스터 구성
→ AWS ParallelCluster
```

## 헷갈리기 쉬운 포인트

- HPC는 단일 AWS 서비스가 아니다.
  - 여러 서비스 조합으로 계산 성능을 극대화하는 아키텍처다.

- Cluster Placement Group은 고가용성보다 성능이 목적이다.
  - 같은 AZ에 가깝게 배치해서 지연 시간을 줄인다.

- ENA와 EFA를 구분해야 한다.
  - ENA = 일반 EC2 향상된 네트워킹.
  - EFA = HPC/MPI용 초저지연 네트워킹.

- Instance Store는 빠르지만 휘발성이다.
  - 인스턴스 장애/종료 시 데이터 손실 가능.

- FSx for Lustre는 HPC 파일 시스템으로 기억한다.
  - S3와 연동 가능하고 대량 파일 처리에 강하다.

# Elastic Load Balancing

Elastic Load Balancing은 들어오는 트래픽을 여러 대상에 분산하고, 정상 대상에만 요청을 보내도록 health check를 수행하는 AWS 관리형 로드 밸런서 서비스다.

시험에서는 어떤 로드 밸런서가 어느 계층에서 동작하고, 어떤 프로토콜/라우팅/인증서 기능을 지원하는지 구분하는 게 중요하다.

## 로드 밸런서 종류

| 종류 | 계층 | 주요 프로토콜 | 핵심 사용처 |
| --- | --- | --- | --- |
| Classic Load Balancer, CLB | L4/L7 구세대 | HTTP, HTTPS, TCP, SSL | 레거시 워크로드 |
| Application Load Balancer, ALB | L7 | HTTP, HTTPS, WebSocket, HTTP/2 | 웹 앱, 경로/호스트 기반 라우팅, ECS |
| Network Load Balancer, NLB | L4 | TCP, TLS, UDP | 초고성능, 낮은 지연 시간, 고정 IP |
| Gateway Load Balancer, GWLB | L3 | IP, GENEVE 6081 | 방화벽/IDS/IPS 같은 네트워크 가상 appliance 삽입 |

가능하면 CLB보다 ALB/NLB/GWLB 같은 현재 세대 로드 밸런서를 우선 고려한다.

로드 밸런서는 외부 공개용 internet-facing으로 만들 수도 있고, VPC 내부용 internal로 만들 수도 있다.

## SSL/TLS 인증서 감각

SSL/TLS 인증서는 서버가 “나는 이 도메인의 진짜 서버다”라고 증명하는 신분증이다.

```text
사용자 → https://api.example.com 접속
서버/로드밸런서 → api.example.com 인증서 제시
브라우저 → 도메인명과 CA 서명을 확인
```

### SAN

SAN은 Subject Alternative Name이다.

인증서 하나가 유효한 도메인 이름 목록이라고 보면 된다.

```text
인증서 1개
SAN:
- www.example.com
- api.example.com
- admin.example.com
```

단점은 도메인을 추가/삭제할 때 SAN이 들어간 인증서를 다시 발급하거나 업데이트해야 한다는 점이다.

### SNI

SNI는 Server Name Indication이다.

클라이언트가 TLS handshake 초반에 “나는 이 도메인으로 접속하려고 한다”라고 알려주는 기능이다.

```text
클라이언트: api.example.com 접속할래
ALB: 그럼 api.example.com 인증서를 보여줄게
```

SNI를 지원하면 로드 밸런서 하나에 여러 인증서를 붙이고, 요청 도메인에 맞는 인증서를 선택할 수 있다.

```text
SAN = 인증서 안의 도메인 목록
SNI = 클라이언트가 접속하려는 도메인을 알려줘서 서버가 인증서를 고르게 하는 기능
```

## Classic Load Balancer

CLB는 이전 세대 로드 밸런서다.

특징:

- HTTP/HTTPS/TCP/SSL을 지원한다.
- Health check는 HTTP 또는 TCP 수준에서 가능하다.
- SSL/TLS 인증서는 기본적으로 리스너당 하나를 사용한다.
- SNI를 지원하지 않는다.
- 여러 도메인을 하나의 인증서로 처리하려면 SAN 또는 wildcard 인증서가 필요하다.
- 도메인별로 별도 인증서가 필요하면 CLB를 여러 개 두는 구조가 필요할 수 있다.

### CLB와 SAN/SNI 문제

CLB는 SNI로 여러 인증서 중 하나를 골라주는 기능이 없다.

그래서 여러 도메인을 하나의 CLB로 처리하려면 인증서 하나에 SAN을 많이 넣어야 한다.

```text
CLB 1개
→ 인증서 1개
→ SAN에 여러 도메인 포함
```

하지만 도메인이 늘거나 줄 때마다 인증서를 갱신해야 해서 운영이 불편하다.

그래서 여러 인증서를 유연하게 붙여야 하면 SNI를 지원하는 ALB/NLB/CloudFront가 더 적합하다.

### CLB에서 TCP 대 TCP와 양방향 SSL

TCP 대 TCP는 CLB가 TLS/SSL을 풀지 않고 TCP 연결을 EC2로 그대로 넘기는 구조다.

```text
Client --TLS over TCP--> CLB --TCP pass-through--> EC2
EC2의 Nginx/Apache가 TLS handshake 처리
```

이때 “SSL 인증이 EC2 수준에서 이루어진다”는 말은 인증서 제시, TLS 종료, 클라이언트 인증서 검증 같은 작업을 CLB가 아니라 EC2 안의 웹서버가 직접 한다는 뜻이다.

양방향 SSL, 즉 mTLS는 서버도 클라이언트 인증서를 검증해야 한다.

CLB가 TLS를 종료해버리면 EC2가 클라이언트 인증서를 직접 보기 어렵기 때문에, CLB에서 mTLS를 구현하려면 TCP pass-through로 EC2까지 TLS를 통과시키고 EC2에서 인증서를 검증하는 구조를 사용한다.

```text
CLB에서 TLS 종료
→ CLB가 인증서 처리
→ EC2는 이미 풀린 요청을 받음

TCP pass-through
→ EC2가 TLS 처리
→ EC2가 클라이언트 인증서까지 검증 가능
```

## Application Load Balancer

ALB는 Layer 7 HTTP/HTTPS 로드 밸런서다.

특징:

- HTTP, HTTPS, WebSocket, HTTP/2를 지원한다.
- 경로 기반 라우팅을 할 수 있다.
- 호스트 기반 라우팅을 할 수 있다.
- HTTP header, query string 기반 라우팅도 가능하다.
- HTTP를 HTTPS로 리디렉션할 수 있다.
- SNI를 지원해 여러 SSL/TLS 인증서를 사용할 수 있다.
- Target Group 단위로 health check를 한다.
- ECS dynamic port mapping과 잘 맞는다.

라우팅 예:

```text
/user   → User Target Group
/search → Search Target Group

api.example.com   → API Target Group
admin.example.com → Admin Target Group
```

### ALB Target Group

| Target type | 설명 |
| --- | --- |
| EC2 Instance | 일반 EC2/Auto Scaling Group 대상 |
| IP address | Private IP를 직접 등록, 온프레미스/다른 VPC 패턴에 사용 |
| Lambda | HTTP 요청을 Lambda 이벤트로 변환 |
| ECS Task | 컨테이너/동적 포트 매핑에 적합 |

## TLS 종료

TLS 종료는 HTTPS 암호화 연결을 어디서 복호화하느냐를 말한다.

ALB에 ACM 인증서를 붙이면 보통 ALB에서 TLS를 종료한다.

```text
Client --HTTPS--> ALB --HTTP--> EC2
```

이 구조에서는 EC2가 인증서 관리나 TLS 복호화 CPU 비용을 덜 수 있다.

내부 구간까지 암호화해야 하면 ALB에서 EC2로도 HTTPS를 설정할 수 있다.

```text
Client --HTTPS--> ALB --HTTPS--> EC2
```

## Network Load Balancer

NLB는 Layer 4 로드 밸런서다.

특징:

- TCP, TLS, UDP 트래픽에 적합하다.
- 매우 높은 처리량과 낮은 지연 시간이 필요할 때 사용한다.
- AZ마다 고정 IP를 제공한다.
- Internet-facing NLB에는 Elastic IP를 붙일 수 있다.
- TLS listener를 사용하면 NLB에서 TLS 종료가 가능하다.
- 보안 그룹을 연결할 수 있다. 단, 만들 때 보안 그룹 없이 생성한 NLB에는 나중에 보안 그룹을 붙일 수 없으므로 생성 시 고려해야 한다.

사용 사례:

```text
TCP/UDP 고성능
고정 IP 필요
Elastic IP 필요
PrivateLink와 연계
ALB 기능도 쓰고 싶지만 고정 IP가 필요
```

### NLB Target Group

| Target type | 설명 |
| --- | --- |
| EC2 Instance | 인스턴스를 직접 대상 등록 |
| IP address | Private IP 등록, 온프레미스 대상도 가능 |
| ALB | NLB의 고정 IP와 ALB의 Layer 7 라우팅을 같이 쓰는 패턴 |

### NLB DNS 이름

NLB의 기본 DNS 이름을 조회하면 활성화된 모든 AZ의 NLB 노드 IP가 반환될 수 있다.

```text
regional NLB DNS
→ AZ별 NLB 노드 IP 여러 개 반환
```

NLB는 AZ별 zone DNS name도 제공한다.

```text
us-east-1a의 zone DNS
→ us-east-1a NLB 노드 IP
```

애플리케이션이 자기 AZ의 NLB 노드와 통신하도록 만들면 AZ 간 데이터 전송 비용과 지연 시간을 줄일 수 있다.

단, 이건 애플리케이션이 자신의 AZ를 알고 적절한 zone DNS를 조회하는 로직이 필요하다.

## Gateway Load Balancer

GWLB는 네트워크 가상 appliance를 배포하고 확장하기 위한 로드 밸런서다.

Layer 3 IP 패킷 수준에서 동작하고, GENEVE 프로토콜 6081번 포트를 사용한다.

사용 사례:

- 방화벽
- IDS/IPS
- Deep Packet Inspection
- 트래픽 검사/필터링 appliance
- 패킷 조작/보안 검사

구조:

```text
사용자 트래픽
→ Route Table로 GWLB Endpoint에 전달
→ Gateway Load Balancer
→ 보안 appliance Target Group
→ 검사 후 다시 GWLB
→ 애플리케이션
```

GWLB는 투명 네트워크 게이트웨이 역할과 로드 밸런서 역할을 동시에 한다.

Target Group은 EC2 인스턴스나 Private IP가 될 수 있다.

## 시험용 비교

| 요구사항 | 선택 |
| --- | --- |
| HTTP/HTTPS 경로 기반 라우팅 | ALB |
| Host 기반 라우팅, SNI, 여러 인증서 | ALB |
| ECS dynamic port mapping | ALB |
| WebSocket / HTTP/2 | ALB |
| TCP/UDP 초고성능 | NLB |
| 고정 IP / Elastic IP | NLB |
| NLB 고정 IP + ALB L7 기능 | NLB target으로 ALB |
| 방화벽/IDS/IPS appliance 삽입 | GWLB |
| 레거시 HTTP/TCP 로드 밸런싱 | CLB |
| CLB에서 여러 도메인 하나의 인증서 | SAN 또는 wildcard 인증서 |
| CLB에서 도메인별 별도 인증서 | 여러 CLB 또는 ALB/NLB/CloudFront로 전환 |
| CLB에서 mTLS | TCP pass-through 후 EC2에서 TLS 인증 |

## 시험용 요약

ALB는 Layer 7 웹 라우팅, NLB는 Layer 4 고성능/고정 IP, GWLB는 네트워크 보안 appliance 삽입, CLB는 레거시로 기억한다.

SAN은 인증서 안의 도메인 목록이고, SNI는 클라이언트가 접속하려는 도메인을 알려줘서 로드 밸런서가 맞는 인증서를 고르게 하는 기능이다.

CLB는 SNI를 지원하지 않으므로 여러 인증서를 유연하게 쓰기 어렵고, 여러 도메인은 SAN/wildcard 또는 여러 CLB로 처리해야 한다.

CLB에서 TCP pass-through를 쓰면 TLS 인증은 EC2 수준에서 이루어지며, mTLS처럼 EC2가 클라이언트 인증서를 직접 검증해야 할 때 사용한다.

# Auto Scaling Group, ASG

ASG는 EC2 인스턴스 수를 자동으로 늘리고 줄이는 서비스다.

쉽게 말하면:

```text
트래픽/부하가 늘면 EC2 추가
트래픽/부하가 줄면 EC2 제거
비정상 인스턴스는 교체
```

시험에서 ASG는 보통 다음 포인트로 나온다.

- 어떤 스케일링 정책을 쓸 것인가.
- 어떤 지표로 스케일링할 것인가.
- Spot/On-Demand를 어떻게 섞을 것인가.
- AMI 업데이트를 어떻게 롤링할 것인가.
- Health Check를 어떻게 설계할 것인가.

## 동적 스케일링 정책

### Target Tracking Scaling

대상 추적 스케일링은 가장 단순하고 많이 쓰는 방식이다.

```text
평균 CPU 40%를 유지해줘
```

처럼 목표값 하나를 정하면 ASG가 알아서 늘리고 줄인다.

예:

```text
ASG 평균 CPU > 40%
→ 인스턴스 추가

ASG 평균 CPU < 40%
→ 인스턴스 제거
```

시험 감각:

```text
가장 간단한 ASG 스케일링
→ Target Tracking
```

### Step Scaling

단계 스케일링은 CloudWatch Alarm을 기준으로 직접 규칙을 만든다.

예:

```text
CPU > 70%
→ 인스턴스 2대 추가

CPU < 30%
→ 인스턴스 1대 제거
```

Target Tracking보다 직접 제어가 가능하지만 설정이 더 복잡하다.

시험 감각:

```text
CloudWatch Alarm 기반으로 단계별 증감 규칙 설정
→ Step Scaling
```

### Scheduled Actions

예약된 작업은 특정 시간에 미리 용량을 바꾸는 방식이다.

예:

```text
매주 금요일 17시 할인 이벤트
→ 최소 용량을 10대로 증가
```

트래픽이 언제 늘어날지 이미 알고 있을 때 쓴다.

시험 감각:

```text
미리 아는 일정에 맞춰 ASG 용량 변경
→ Scheduled Actions
```

### Predictive Scaling

예측 스케일링은 AWS가 과거 부하 패턴을 분석해서 미래 부하를 예측하고 미리 스케일링한다.

적합한 경우:

- 매일 비슷한 시간에 트래픽 증가.
- 매주 반복되는 트래픽 패턴.
- 주기적인 업무 피크.

시험 감각:

```text
반복 패턴을 AWS가 분석해서 미리 스케일링
→ Predictive Scaling
```

## ASG 스케일링에 적합한 지표

### CPUUtilization

가장 대표적인 지표다.

```text
CPU 부하가 높으면 인스턴스 추가
CPU 부하가 낮으면 인스턴스 제거
```

CPU 중심 웹 서버나 계산 작업에 적합하다.

### RequestCountPerTarget

ALB Target Group 기준 지표다.

```text
대상 EC2 한 대당 처리하는 요청 수
```

예를 들어 인스턴스 한 대당 요청 수를 일정 수준 이하로 유지하고 싶을 때 쓴다.

시험 감각:

```text
ALB 뒤 EC2에 요청 수를 균등하게 유지
→ RequestCountPerTarget
```

### Average Network In / Out

네트워크 입출력이 많은 애플리케이션에 적합하다.

예:

- 동영상 업로드/다운로드.
- 대용량 파일 전송.
- 네트워크 처리량이 병목인 앱.

### Custom Metric

CloudWatch에 직접 올린 사용자 지정 지표로도 ASG를 스케일링할 수 있다.

예:

- 큐 길이.
- 동시 접속자 수.
- 처리 대기 작업 수.
- 애플리케이션 내부 지표.

## Spot Fleet / Mixed Instances

ASG에서는 Spot과 On-Demand를 섞어서 사용할 수 있다.

```text
기본 안정성은 On-Demand
비용 절감은 Spot
```

Spot은 저렴하지만 AWS가 회수할 수 있으므로, 중단되어도 재시도 가능한 워크로드에 적합하다.

### Spot Instance vs Spot Fleet

| 구분 | Spot Instance | Spot Fleet |
|---|---|---|
| 느낌 | 싼 EC2 인스턴스 하나를 직접 쓰는 것 | 여러 Spot pool에서 목표 용량을 맞추는 묶음 |
| 목적 | 비용 절감 | 비용 절감 + 용량 확보 + 중단 위험 분산 |
| 관리 | 내가 직접 어떤 인스턴스를 쓸지 정함 | AWS가 전략에 따라 여러 풀에서 인스턴스를 가져옴 |
| 안정성 | 해당 Spot이 회수되면 바로 영향 | 여러 풀로 분산하면 중단 위험을 줄일 수 있음 |
| 시험 감각 | 단순히 저렴한 임시 EC2 | 여러 AZ/인스턴스 타입을 섞어 목표 용량 유지 |

Spot pool은 특정 조건의 Spot 용량 묶음이다.

```text
Spot pool
= instance type + AZ + OS/network platform 조합

예:
c5.large in ap-northeast-2a
m5.large in ap-northeast-2c
```

### Spot Fleet allocation strategy

Spot Fleet은 어떤 Spot pool에서 인스턴스를 가져올지 전략을 고를 수 있다.

| 전략 | 의미 | 시험 감각 |
|---|---|---|
| lowestPrice | 가장 싼 풀부터 사용 | 비용 최우선. 대신 싼 풀에 몰리면 중단 위험이 커질 수 있음 |
| diversified | 여러 풀에 분산해서 사용 | 한 풀에서 회수돼도 전체 영향 줄임 |
| capacityOptimized | 여유 용량이 많은 풀 우선 사용 | 중단 위험을 줄이는 쪽 |
| priceCapacityOptimized | 가격과 가용 용량을 함께 고려 | 비용과 안정성 균형. 요즘 권장 감각 |

한 줄 감각:

```text
Spot Instance
= 싸게 빌린 EC2 한 대

Spot Fleet
= 여러 Spot pool에서 목표 용량을 채우는 관리자
```

시험 감각:

```text
ASG + Spot/On-Demand 혼합
→ 비용 절감 + 일정 수준 안정성
```

## Lifecycle Hook

Lifecycle Hook은 인스턴스가 시작되거나 종료되기 전후에 중간 작업을 할 수 있게 해준다.

예:

- 인스턴스 시작 전 앱 설치/설정.
- 서비스 투입 전 추가 health check.
- 종료 전 로그 수집.
- 종료 전 연결 drain.
- 종료 전 임시 데이터 백업.

흐름:

```text
ASG가 인스턴스 시작/종료 시도
→ Lifecycle Hook에서 대기
→ 필요한 작업 수행
→ 완료 신호
→ ASG가 다음 단계 진행
```

시험 감각:

```text
인스턴스 시작/종료 사이에 커스텀 작업 필요
→ Lifecycle Hook
```

## AMI 업데이트와 Instance Refresh

ASG 안의 EC2를 새 AMI로 바꾸려면 먼저 Launch Template 또는 Launch Configuration을 업데이트해야 한다.

그 다음 기존 인스턴스를 새 템플릿 기반 인스턴스로 교체한다.

방법:

- 기존 인스턴스를 수동 종료해서 ASG가 새 인스턴스를 만들게 한다.
- EC2 Instance Refresh를 사용해 자동 롤링 교체한다.

### EC2 Instance Refresh

Instance Refresh는 ASG 인스턴스를 최신 Launch Template 기준으로 순차 교체하는 기능이다.

흐름:

```text
새 AMI로 Launch Template 업데이트
→ StartInstanceRefresh API 호출
→ ASG가 기존 인스턴스를 조금씩 종료
→ 새 Launch Template으로 새 인스턴스 생성
→ 전체 인스턴스를 점진적으로 교체
```

중요 설정:

- Minimum healthy percentage:
  - 교체 중에도 정상 인스턴스를 최소 몇 % 유지할지 정한다.
  - 예: 60%를 유지하면 전체를 한 번에 날리지 않는다.
- Warm-up time:
  - 새 인스턴스가 준비될 시간을 준다.
  - 앱 부팅, 설정 로딩, health check 통과 시간을 고려한다.

시험 감각:

```text
ASG의 기존 인스턴스를 새 AMI/Launch Template 기준으로 롤링 교체
→ EC2 Instance Refresh
```

## ASG 프로세스

ASG 내부에는 여러 프로세스가 있고, 필요하면 일시 중단할 수 있다.

대표 프로세스:

- Launch:
  - EC2 인스턴스를 추가해서 용량을 늘린다.
- Terminate:
  - EC2 인스턴스를 제거해서 용량을 줄인다.
- HealthCheck:
  - 인스턴스 상태를 확인한다.
- ReplaceUnhealthy:
  - 비정상 인스턴스를 종료하고 새로 만든다.
- AZRebalance:
  - 여러 AZ에 인스턴스 수를 균등하게 맞춘다.
- AlarmNotification:
  - CloudWatch Alarm 기반 스케일링 알림을 받는다.
- ScheduledActions:
  - 예약된 스케일링 작업을 실행한다.
- AddToLoadBalancer:
  - 인스턴스를 Load Balancer 또는 Target Group에 등록한다.
- InstanceRefresh:
  - 인스턴스 새로고침을 수행한다.

시험 감각:

```text
ASG가 비정상 인스턴스를 계속 교체해서 디버깅이 어려움
→ ReplaceUnhealthy 프로세스 일시 중단
```

## Health Check

ASG는 인스턴스가 정상인지 확인하고, 비정상이면 종료 후 새 인스턴스를 만든다.

Health Check 종류:

- EC2 Status Check:
  - EC2 자체 상태 확인.
- ELB Health Check:
  - ALB/NLB/CLB 앞에 있을 때 로드 밸런서 기준으로 상태 확인.
  - HTTP endpoint 기반으로 확인할 수 있다.

흐름:

```text
EC2 또는 ELB Health Check 실패
→ ASG가 인스턴스를 unhealthy로 판단
→ 인스턴스 종료
→ 새 인스턴스 시작
```

### 좋은 Health Check

가볍고 정확해야 한다.

예:

```text
/health-server
→ 서버 프로세스가 살아 있고 기본 응답 가능하면 OK
```

좋은 health check는 앱이 “살아 있는지”를 빠르게 확인한다.

### 나쁜 Health Check

무겁거나 외부 의존성이 강하면 위험하다.

예:

```text
/number-customers
→ DB 호출
→ 전체 고객 수 계산
→ DB가 느리면 응답 지연
→ ASG가 EC2를 unhealthy로 오판
→ 정상 인스턴스까지 종료될 수 있음
```

Health Check에 DB, 외부 API, 무거운 계산을 넣으면 DB 장애 때문에 EC2가 계속 교체되는 상황이 생길 수 있다.

시험 감각:

```text
Health Check는 가볍고 빠르고 정확해야 한다.
무거운 DB 조회나 외부 의존 작업을 넣으면 안 된다.
```

## ASG 시험용 한 번에 정리

```text
가장 쉬운 스케일링
→ Target Tracking

CloudWatch Alarm 기반 단계별 증감
→ Step Scaling

미리 아는 일정
→ Scheduled Actions

반복 패턴 예측
→ Predictive Scaling

ALB 뒤 대상당 요청 수 기준
→ RequestCountPerTarget

시작/종료 전후 커스텀 작업
→ Lifecycle Hook

새 AMI로 ASG 인스턴스 순차 교체
→ Instance Refresh

비정상 인스턴스 교체 중지하고 디버깅
→ Suspend ReplaceUnhealthy

ASG 인스턴스를 Target Group에 등록
→ AddToLoadBalancer

좋은 Health Check
→ 가벼운 /health endpoint

나쁜 Health Check
→ DB 전체 조회 같은 무거운 endpoint
```

# Amazon ECS

ECS는 AWS의 컨테이너 관리 서비스다. 시험에서는 Docker 자체보다 **ECS 구성요소와 실행 방식**을 구분하는 게 중요하다.

```text
ECS = 컨테이너를 어디에 몇 개 실행할지 관리
EKS = Kubernetes 기반 컨테이너 관리
Fargate = EC2 관리 없는 서버리스 컨테이너 실행 방식
```

## ECS 핵심 구성요소

```text
ECS Cluster
= Task가 실행될 논리적 공간

Task Definition
= 컨테이너 실행 설계도
= image, CPU, memory, port, log, IAM role 등 정의

Task
= Task Definition으로 실제 실행된 컨테이너 묶음

Service
= 원하는 개수의 Task를 계속 유지
```

한 줄 감각:

```text
Task Definition = 설계도
Task = 실제 실행본
Service = Task 개수 유지 관리자
```

## ECS 실행 방식

```text
ECS on EC2
= 내가 EC2 인스턴스를 준비하고 관리
= Task가 EC2 위에 배치됨
= Task 수가 늘면 EC2 ASG 용량도 신경 써야 함

ECS on Fargate
= EC2를 직접 관리하지 않음
= Task별 CPU/RAM만 지정
= 서버리스 컨테이너 실행
```

시험 감각:

```text
서버까지 직접 관리
→ ECS on EC2

컨테이너만 실행하고 서버 관리는 AWS에 맡김
→ ECS on Fargate
```

## ECS IAM Role

```text
EC2 Instance Profile
= ECS Cluster의 EC2 인스턴스에 붙음
= ECS 등록, ECR pull, CloudWatch Logs 전송

Task IAM Role
= 개별 Task에 붙음
= 컨테이너 앱이 S3, DynamoDB 같은 AWS API 호출
```

## 시험에 잘 나오는 ECS 포인트

```text
ALB Dynamic Port Mapping
= 한 EC2 안에 같은 Task 여러 개 실행
= 각 Task가 다른 임시 port를 사용
= ALB가 올바른 Task port로 라우팅

awsvpc network mode
= Task마다 ENI와 private IP 부여
= Fargate 기본 네트워크 모드

ECS Service Auto Scaling
= Task 개수를 자동 증감
= Target Tracking / Step Scaling / Scheduled Scaling

ECS on EC2에서 용량 부족
= Task만 늘려도 EC2 공간이 없으면 배치 불가
= EC2 ASG도 같이 고려

FARGATE_SPOT
= 저렴하지만 중단 가능

ECR
= Docker image 저장소
= ECR repository는 리전 서비스
= pull 권한 문제는 IAM 확인
```

## ECS 시험용 한 줄 정리

```text
ECS = AWS native 컨테이너 관리
EKS = Kubernetes managed service
Fargate = 서버리스 컨테이너 실행
Task Definition = 설계도
Task = 실행된 컨테이너 묶음
Service = Task 개수 유지
Task IAM Role = 컨테이너 앱 권한
EC2 Instance Profile = ECS용 EC2 인스턴스 권한
Dynamic Port Mapping = ALB가 Task별 다른 port로 라우팅
awsvpc = Task마다 ENI/private IP
ECR = 컨테이너 이미지 저장소, regional
```

# Amazon EKS

EKS, Elastic Kubernetes Service는 AWS에서 Kubernetes 클러스터를 관리형으로 실행하는 서비스다.

시험에서는 Kubernetes 자체 문법보다 **ECS와의 차이, Pod/Node 용어, 실행 모드, 스토리지 연동**을 구분하는 게 중요하다.

```text
ECS
= AWS native 컨테이너 오케스트레이션

EKS
= Kubernetes 기반 컨테이너 오케스트레이션
= Kubernetes API, kubectl, Helm 생태계 사용

Kubernetes
= 컨테이너 배포/스케일링/관리를 위한 오픈소스 표준
```

## EKS를 고르는 경우

```text
이미 온프레미스/다른 클라우드에서 Kubernetes 사용 중
Kubernetes API와 생태계가 필요함
멀티 클라우드/마이그레이션 이식성이 중요함
AWS가 Kubernetes control plane을 관리해주길 원함
```

시험 감각:

```text
AWS native 간단 운영
→ ECS

Kubernetes 표준/이식성 필요
→ EKS
```

## EKS 기본 구조

```text
EKS Cluster
= Kubernetes control plane은 AWS가 관리

Node
= Pod가 실행되는 워커 머신
= 보통 EC2 인스턴스

Pod
= Kubernetes에서 컨테이너 실행 단위
= ECS Task와 비슷한 감각

Service
= Pod를 네트워크로 노출
= public/private Load Balancer와 연결 가능
```

한 줄 감각:

```text
ECS Task 비슷한 것
→ EKS Pod

ECS Container Instance 비슷한 것
→ EKS Node
```

## EKS 실행 모드 / 노드 유형

```text
Managed Node Group
= AWS가 EC2 worker node와 ASG를 관리
= On-Demand / Spot 지원

Self-managed Node
= 사용자가 EC2 node를 직접 생성/등록/관리
= EKS Optimized AMI 사용 가능
= 더 많은 제어가 필요할 때

EKS on Fargate
= worker node를 직접 관리하지 않음
= 서버리스로 Pod 실행
```

시험 감각:

```text
노드 관리도 AWS에 맡김
→ Managed Node Group

노드 설정을 직접 강하게 제어
→ Self-managed Node

노드 자체를 관리하고 싶지 않음
→ EKS on Fargate
```

## EKS 스토리지

EKS에서 볼륨을 쓰려면 Kubernetes의 `StorageClass`와 CSI driver를 사용한다.

```text
CSI
= Container Storage Interface
= Kubernetes가 외부 스토리지를 붙이기 위한 표준 인터페이스
```

시험에 나올 만한 EKS 스토리지:

```text
Amazon EBS
Amazon EFS
Amazon FSx for Lustre
Amazon FSx for NetApp ONTAP
```

주의:

```text
EKS Fargate와 함께 쓰는 대표 스토리지
→ EFS
```

## EKS 시험용 한 줄 정리

```text
EKS = AWS managed Kubernetes
Kubernetes = 오픈소스 컨테이너 오케스트레이션 표준
Pod = Kubernetes 컨테이너 실행 단위, ECS Task 비슷
Node = Pod가 실행되는 워커 머신, 보통 EC2
Managed Node Group = AWS가 EC2 node/ASG 관리
Self-managed Node = 사용자가 node 직접 관리
EKS on Fargate = node 없이 서버리스로 Pod 실행
Service = Pod를 외부/내부 Load Balancer로 노출
StorageClass + CSI driver = EKS 스토리지 연결
EFS = EKS Fargate와 함께 쓰는 대표 스토리지
```

# AWS App Runner

App Runner는 웹 애플리케이션과 API를 빠르게 배포하기 위한 완전관리형 서비스다.

컨테이너 인프라, 로드 밸런서, HTTPS, 확장 같은 세부 운영을 많이 숨겨준다.

```text
소스 코드 또는 Docker image
→ App Runner 서비스 생성
→ vCPU / memory / auto scaling / health check 설정
→ URL로 웹앱/API 접근
```

## App Runner 특징

```text
완전관리형 웹앱/API 배포
컨테이너 이미지 또는 소스 코드에서 시작 가능
자동 확장
고가용성
로드 밸런싱
암호화/HTTPS
Health check
VPC 접근 가능, DB/cache/message queue 연결
```

시험 감각:

```text
컨테이너 인프라를 거의 모르고 웹앱/API를 빠르게 배포
→ App Runner

ECS/EKS까지 직접 설계하기보다 더 단순한 완전관리형 배포
→ App Runner
```

## App Runner 멀티 리전 패턴

App Runner 자체는 한 리전에 배포되므로 멀티 리전 구성이 필요하면 주변 서비스를 같이 쓴다.

```text
ECR cross-region replication
→ 같은 container image를 여러 리전에 복제

DynamoDB Global Tables
→ 데이터도 여러 리전에 복제

각 리전에 App Runner 서비스 배포
→ 같은 이미지와 데이터 소스 사용

Route 53 latency-based routing
→ 사용자에게 가까운 App Runner endpoint로 라우팅
```

## App Runner 시험용 한 줄 정리

```text
App Runner = 웹앱/API를 빠르게 배포하는 완전관리형 서비스
입력 = source code 또는 container image
운영 = autoscaling, HA, load balancing, HTTPS, health check 자동화
VPC 접근 = DB/cache/queue 연결 가능
멀티 리전 = ECR replication + DynamoDB Global Tables + Route 53 latency routing
ECS/EKS보다 더 추상화된 간단 배포 서비스
```

# ECS Anywhere / EKS Anywhere

AWS 컨테이너 서비스를 온프레미스와 연결하는 방식이다.

시험에서는 이름이 비슷해서 헷갈리기 쉬우므로 **ECS control plane으로 외부 서버를 관리하는지**, **온프레미스에 Kubernetes 클러스터를 직접 만드는지**를 구분한다.

## ECS Anywhere

ECS Anywhere는 온프레미스 서버나 VM 같은 고객 관리 인프라에서 ECS Task를 실행하게 해준다.

```text
온프레미스 서버/VM
→ ECS Container Agent 설치
→ SSM Agent 설치
→ ECS Cluster에 external instance로 등록
→ launch type = EXTERNAL
→ AWS ECS control plane에서 Task 배포/관리
```

필요한 것:

```text
ECS Container Agent
SSM Agent
AWS 리전과 안정적인 네트워크 연결
EXTERNAL launch type
```

사용 사례:

```text
컴플라이언스 때문에 데이터센터에서 실행
낮은 지연시간 때문에 현장 가까이 실행
온프레미스 ML / 영상 처리 / 데이터 처리
ECS 운영 모델을 온프레미스로 확장
```

## EKS Anywhere

EKS Anywhere는 AWS 외부, 예를 들면 온프레미스 데이터센터에 Kubernetes 클러스터를 생성하고 운영하는 방식이다.

```text
온프레미스 환경
→ EKS Anywhere installer 사용
→ Amazon EKS Distro 기반 Kubernetes 설치
→ 온프레미스 Kubernetes 클러스터 운영
```

ECS Anywhere와 달리, EKS Anywhere는 AWS 연결 없이도 동작할 수 있다.

```text
connected mode
= EKS Connector로 AWS 콘솔에서 온프레미스 클러스터 확인/관리

disconnected mode
= AWS 연결 없이 온프레미스에서 EKS Distro와 오픈소스 도구로 관리
```

## ECS Anywhere vs EKS Anywhere

| 구분 | ECS Anywhere | EKS Anywhere |
|---|---|---|
| 핵심 | ECS Task를 온프레미스 서버에서 실행 | 온프레미스에 Kubernetes 클러스터 운영 |
| 기반 | ECS control plane | EKS Distro / Kubernetes |
| 설치 | ECS Agent + SSM Agent | EKS Anywhere installer |
| AWS 연결 | AWS 리전에 안정적으로 연결 필요 | 연결 모드/비연결 모드 가능 |
| 실행 단위 | ECS Task | Kubernetes Pod |
| 시험 감각 | ECS를 데이터센터 서버까지 확장 | Kubernetes/EKS 운영 방식을 데이터센터로 가져옴 |

## 시험용 한 줄 정리

```text
온프레미스 서버에 ECS Task 실행
→ ECS Anywhere

필요한 에이전트
→ ECS Container Agent + SSM Agent

ECS Anywhere launch type
→ EXTERNAL

온프레미스에 Kubernetes 클러스터 구축
→ EKS Anywhere

EKS Anywhere 기반 배포판
→ Amazon EKS Distro

AWS 콘솔에서 온프레미스 EKS 클러스터 연결/확인
→ EKS Connector

AWS 연결 없이도 온프레미스 Kubernetes 운영
→ EKS Anywhere disconnected mode
```

# AWS Systems Manager, SSM

SSM은 EC2, 온프레미스 서버, VM 같은 관리 대상 인스턴스를 중앙에서 운영하고 자동화하는 서비스다.

시험에서는 **SSH 없이 접속, 명령 일괄 실행, 패치, 자동화, 설정값 저장, 하이브리드 관리**를 기억하면 된다.

## SSM으로 할 수 있는 일

```text
Session Manager
= SSH key / bastion 없이 EC2 접속
= private subnet EC2도 접속 가능

Run Command
= 여러 인스턴스에 명령/script 일괄 실행

Patch Manager
= OS 보안 패치 자동화

Automation
= 반복 운영 작업 runbook 자동화
= AMI 생성, 재시작, 장애 대응 등

Inventory
= OS, 패키지, 애플리케이션 정보 수집

Maintenance Windows
= 정해진 시간에 패치/명령/자동화 실행

Parameter Store
= 설정값 저장
= SecureString으로 암호화된 값 저장 가능

Hybrid Activations
= 온프레미스 서버도 SSM 관리 대상으로 등록
```

## SSM 사용 조건

```text
SSM Agent 설치/실행
인스턴스 IAM Role 필요
예: AmazonSSMManagedInstanceCore
SSM 서비스 엔드포인트와 통신 가능
```

private subnet에서 인터넷 없이 SSM을 쓰려면 VPC endpoint를 고려한다.

```text
com.amazonaws.region.ssm
com.amazonaws.region.ssmmessages
com.amazonaws.region.ec2messages
```

## 시험용 한 줄 정리

```text
SSH 없이 EC2 접속
→ Session Manager

여러 인스턴스에 명령 실행
→ Run Command

OS 패치 자동화
→ Patch Manager

운영 runbook 자동화
→ Automation

앱 설정값/비밀값 저장
→ Parameter Store

온프레미스 서버까지 관리
→ Hybrid Activations

private subnet EC2에 SSM 접속
→ SSM Agent + IAM Role + VPC endpoints
```

# AWS Lambda

Lambda는 서버를 직접 관리하지 않고 코드를 실행하는 서버리스 컴퓨팅 서비스다.

시험에서는 **Lambda가 좋은 경우와 아닌 경우**, **한계값**, **동시성/스로틀링**, **배포 전략**, **모니터링**을 구분하는 게 중요하다.

## Lambda 실행 방식

```text
지원 런타임
= Node.js, Python, Java, .NET, Ruby, PowerShell 등

Custom Runtime API
= 기본 지원 외 언어도 직접 런타임을 만들어 실행 가능

Container image
= Lambda Runtime API를 구현한 container image 실행 가능
= 최대 image 크기 10 GB
```

시험 감각:

```text
일반 서버리스 함수
→ Lambda

Docker container 자체를 오래/복잡하게 실행
→ ECS / EKS / Fargate 쪽을 먼저 고려
```

## Lambda 주요 한계

공식 문서 기준 핵심 한계는 다음과 같다.

```text
최대 timeout
= 15분

memory
= 128 MB ~ 10,240 MB
= CPU는 memory에 비례

/tmp ephemeral storage
= 512 MB ~ 10,240 MB

deployment package
= 50 MB zipped
= 250 MB unzipped, layer 포함

container image
= 10 GB

동시 실행 기본 quota
= 리전당 1,000, 증가 요청 가능

동기 호출 payload
= 6 MB

비동기 호출 payload
= 1 MB
```

시험 감각:

```text
15분 넘는 긴 작업
→ Lambda 부적합
→ ECS / Batch / Step Functions 등 고려

큰 container workload
→ Lambda container image 가능은 하지만
→ 시험 감각으로는 ECS/EKS/Fargate 선호
```

## Lambda와 VPC

기본 Lambda는 AWS가 관리하는 Lambda VPC에서 실행되고, 인터넷과 퍼블릭 AWS API에 접근할 수 있다.

하지만 VPC 안의 private RDS 같은 리소스에는 바로 접근할 수 없다.

```text
Lambda 기본 실행
→ 인터넷 접근 가능
→ DynamoDB 같은 public AWS API 접근 가능
→ 내 VPC private subnet의 RDS 접근 불가

Lambda에 VPC 설정 추가
→ 지정한 VPC subnet/security group에 연결
→ private RDS 같은 VPC 내부 리소스 접근 가능
→ 대신 인터넷 접근은 VPC 라우팅에 따라 달라짐
```

시험 함정:

```text
Lambda를 public subnet에 넣음
→ 인터넷 접근 가능 X

Lambda를 private subnet에 넣고 NAT Gateway/NAT Instance 사용
→ 인터넷 접근 가능
```

구조:

```text
Lambda in private subnet
→ private route table: 0.0.0.0/0 to NAT Gateway
→ NAT Gateway in public subnet
→ Internet Gateway
→ Internet / public API
```

DynamoDB 같은 AWS public API 접근은 두 가지 방식이 있다.

```text
방법 1
Lambda private subnet
→ NAT Gateway
→ Internet Gateway
→ DynamoDB public endpoint

방법 2
Lambda private subnet
→ DynamoDB VPC endpoint
→ AWS 내부망으로 접근
```

시험 감각:

```text
private RDS 접근 필요
→ Lambda VPC 연결

VPC Lambda가 인터넷 접근 필요
→ private subnet + NAT Gateway/NAT Instance

AWS public service를 내부 경로로 접근
→ VPC endpoint
```

## Lambda 고정 outbound IP

기본 Lambda가 외부 API를 호출하면 고정된 public IP를 보장하기 어렵다.

외부 API에서 allowlist할 고정 IP가 필요하면 Lambda를 private subnet에 두고 NAT Gateway를 거치게 한다.

```text
Lambda in private subnet
→ NAT Gateway
→ Elastic IP
→ 외부 API
```

외부 API 입장에서는 NAT Gateway의 Elastic IP에서 온 요청으로 보인다.

시험 감각:

```text
Lambda outbound IP 고정 필요
→ Lambda in private subnet + NAT Gateway + Elastic IP
```

## Lambda 호출 방식

### 동기 호출

동기 호출은 호출자가 Lambda 응답을 기다리는 방식이다.

```text
CLI / SDK / API Gateway / ALB
→ Lambda 호출
→ 응답 받을 때까지 대기
```

오류 처리와 재시도는 보통 클라이언트 쪽 책임이다.

```text
client retry
exponential backoff
timeout handling
```

### 비동기 호출

비동기 호출은 이벤트를 Lambda에 전달하고 바로 끝나는 방식이다.

예:

```text
S3 event
SNS
EventBridge
```

Lambda 함수 오류가 나면 기본적으로 추가 재시도를 한다.

```text
비동기 호출 함수 오류
→ 기본적으로 추가 2회 재시도
→ 총 최대 3번 실행될 수 있음
```

그래서 Lambda 코드는 중복 실행을 견디도록 만들어야 한다.

```text
idempotency
= 같은 이벤트가 여러 번 처리되어도 결과가 망가지지 않게 설계
```

실패 이벤트는 DLQ나 destination으로 보낼 수 있다.

```text
DLQ
→ SQS 또는 SNS

on-failure destination
→ 실패 invocation 기록 처리
```

## SNS 직접 호출 vs SQS 버퍼링

S3 이벤트를 처리하는 두 구조는 비슷해 보여도 성격이 다르다.

### S3 → SNS → Lambda

```text
S3 event
→ SNS
→ Lambda 즉시 호출
```

특징:

```text
빠르게 처리 시작
동시 실행이 크게 튈 수 있음
Lambda throttling 가능
실패 시 DLQ/destination 설계 필요
```

### S3 → SNS → SQS → Lambda

```text
S3 event
→ SNS
→ SQS
→ Lambda가 queue를 poll
→ batch 단위 처리
```

특징:

```text
SQS가 버퍼 역할
폭증 트래픽을 흡수
처리 지연은 생길 수 있음
Lambda가 batch 단위로 효율적으로 처리
실패한 메시지는 queue에 남아 재처리 가능
```

시험 감각:

```text
즉시 처리와 높은 병렬성
→ SNS → Lambda

트래픽 폭증 흡수, 안정적 재처리, 버퍼링
→ SQS → Lambda

중복 처리 가능성 있음
→ Lambda 코드는 idempotent 해야 함
```

## Lambda 동시성 / Throttling

Lambda는 동시에 실행할 수 있는 개수에 한도가 있다.

```text
요청 증가
→ Lambda execution environment 증가
→ 동시 실행 한도 초과
→ throttling
```

Reserved concurrency는 특정 함수에 동시 실행 용량을 예약하거나 제한한다.

```text
Reserved concurrency 설정
= 특정 Lambda 함수에 최소/최대 실행 여지를 보장
= 다른 함수가 concurrency를 독점하는 것 방지
```

예:

```text
인기 있는 ALB 연동 Lambda가 concurrency 1,000을 모두 사용
→ API Gateway 뒤 Lambda도 throttling 발생 가능

중요 함수에 reserved concurrency 설정
→ 필요한 실행 용량을 보호
```

해결 감각:

```text
reserved concurrency 조정
account concurrency quota 증가 요청
SQS로 요청 버퍼링
처리 시간 최적화
이벤트 발생량 조절
```

## Lambda 배포, CodeDeploy

Lambda는 version과 alias를 사용해서 배포할 수 있다.

CodeDeploy는 alias가 가리키는 Lambda version 사이에서 트래픽을 점진적으로 옮긴다.

```text
prod alias
→ v1 100%
→ v2 0%

CodeDeploy 배포
→ v1 90% / v2 10%
→ v1 80% / v2 20%
→ ...
→ v2 100%
```

배포 전략:

```text
All-at-once
= 한 번에 새 버전으로 전환

Linear
= 일정 시간마다 일정 비율씩 증가
= 예: 3분마다 10%

Canary
= 소량 트래픽을 먼저 새 버전에 보냄
= 안정적이면 전체 전환
```

Pre-traffic hook / Post-traffic hook으로 배포 전후 검증도 가능하다.

시험 감각:

```text
Lambda version 간 점진 배포
→ CodeDeploy + Alias

소량 트래픽으로 먼저 검증
→ Canary deployment
```

## Lambda 모니터링

# Route 53, Hybrid DNS, Global Accelerator

이 묶음은 컴퓨팅 워크로드를 전 세계 사용자나 하이브리드 네트워크에 어떻게 연결할지에 대한 내용이다.
시험에서는 Route 53 라우팅 정책, private DNS, health check, Global Accelerator와 CloudFront 차이를 자주 묻는다.

## Route 53 기본

Route 53은 AWS의 관리형 DNS 서비스다.
도메인 이름을 IP나 AWS 리소스로 보내고, health check를 붙여 DNS failover도 만들 수 있다.

대표 record:

| 타입 | 의미 | 시험 포인트 |
| --- | --- | --- |
| `A` | hostname을 IPv4로 매핑 | `example.com -> 1.2.3.4` |
| `AAAA` | hostname을 IPv6로 매핑 | IPv6용 |
| `CNAME` | hostname을 다른 hostname으로 매핑 | zone apex에는 사용 불가 |
| `NS` | hosted zone의 name server | 도메인을 어떤 DNS 서버가 관리하는지 지정 |

`CNAME`은 `www.example.com` 같은 하위 도메인에는 가능하지만, `example.com` 같은 root domain에는 불가능하다.
AWS 리소스를 root domain에 연결할 때는 `Alias record`를 쓴다.

## CNAME vs Alias

| 구분 | CNAME | Alias |
| --- | --- | --- |
| 대상 | 다른 hostname | AWS 리소스 hostname |
| root domain | 불가 | 가능 |
| 비용 | 일반 DNS 쿼리 비용 | AWS 리소스 대상이면 무료인 경우 많음 |
| health check | 별도 구성 | AWS 리소스와 네이티브 연동 가능 |

Alias target 대표 예시:

- Elastic Load Balancer
- CloudFront distribution
- API Gateway
- Elastic Beanstalk
- S3 static website
- VPC interface endpoint
- Global Accelerator
- 같은 hosted zone 안의 다른 Route 53 record

주의: EC2의 public DNS name 자체에는 Alias record를 직접 걸 수 없다.

## TTL

TTL은 DNS 응답을 얼마나 오래 캐싱할지 정하는 값이다.

```text
TTL 높음
= Route 53 쿼리 적음
= 변경 반영 느림

TTL 낮음
= 변경 반영 빠름
= Route 53 쿼리 많음
```

Alias record를 제외한 일반 DNS record에는 TTL이 필요하다.

## Route 53 Routing Policy

| 정책 | 의미 | 시험 감각 |
| --- | --- | --- |
| Simple | 하나 또는 여러 값을 단순 반환 | health check 연결 불가 |
| Weighted | 비율로 트래픽 분산 | blue/green, canary, 버전 테스트 |
| Latency-based | 가장 지연 시간이 낮은 리전으로 라우팅 | 성능 최적화 |
| Failover | primary/secondary active-passive 구성 | DR, 장애 조치 |
| Geolocation | 사용자 위치 기준 라우팅 | 대륙/국가/미국 주, default record 필요 |
| Geoproximity | 사용자와 리소스 거리 + bias 기준 | Traffic Flow 필요 |
| Multi-value answer | 여러 healthy record 반환 | DNS 수준 분산, LB 대체 아님 |
| IP-based | 클라이언트 IP CIDR 기준 라우팅 | ISP/네트워크별 최적화 |

시험 포인트:

- Simple routing은 health check와 연결할 수 없는 예외다.
- Weighted는 새 버전 일부 노출이나 blue/green/canary 감각으로 나온다.
- Latency-based는 사용자 위치 자체가 아니라 사용자와 AWS 리전 사이 latency 기준이다.
- Geolocation은 위치 자체 기준이고, 매칭 안 될 때를 대비해 default record가 필요하다.
- Geoproximity는 bias로 특정 리소스가 담당하는 지리 범위를 넓히거나 줄인다.
- Multi-value는 쿼리당 최대 8개의 healthy record를 반환하지만 로드 밸런서를 대체하지 않는다.

## Hosted Zone

Hosted zone은 DNS record를 담는 컨테이너다.

| 종류 | 어디서 해석됨 | 대표 대상 |
| --- | --- | --- |
| Public hosted zone | 인터넷 전체 | public EC2 IP, public ALB, CloudFront, S3 website |
| Private hosted zone | 연결된 VPC 내부 | private EC2 IP, internal ALB, RDS private endpoint |

Private hosted zone을 쓰려면 VPC에서 아래 설정이 켜져 있어야 한다.

```text
enableDnsSupport
enableDnsHostnames
```

## DNSSEC

DNSSEC는 DNS 응답의 무결성과 출처를 검증하는 보안 기능이다.
DNS 응답 위조나 중간자 공격을 줄이는 데 사용한다.

- Route 53은 domain registration용 DNSSEC와 DNSSEC signing을 지원한다.
- Public hosted zone에서 사용한다.
- Private hosted zone용 기능으로 외우면 안 된다.

## Route 53 Health Check

Route 53 health check는 DNS record와 연결해서 비정상 endpoint로 트래픽을 보내지 않게 한다.

| 타입 | 의미 | 시험 포인트 |
| --- | --- | --- |
| Endpoint health check | HTTP/HTTPS/TCP endpoint 직접 확인 | public endpoint 필요 |
| Calculated health check | 여러 health check를 AND/OR/NOT으로 조합 | 최대 256 child check |
| CloudWatch alarm health check | CloudWatch alarm 상태를 health check로 사용 | private resource 우회에 유용 |

Endpoint health check는 전 세계 health checker가 endpoint로 접근하므로 public endpoint가 필요하다.
HTTP/HTTPS는 보통 `2xx`, `3xx` 응답이면 healthy로 본다.
응답 첫 `5,120 bytes` 안에 특정 문자열이 있는지도 검사할 수 있다.

Private VPC 리소스에는 Route 53 health checker가 직접 붙을 수 없다.
internal ALB, private RDS endpoint, private IP, 온프레미스 내부 주소는 CloudWatch alarm으로 우회한다.

```text
Private resource 상태 측정
→ CloudWatch metric/alarm 생성
→ Route 53 health check가 CloudWatch alarm 감시
→ DNS failover에 사용
```

## RDS Multi-Region Failover 감각

Primary RDS가 다른 리전 read replica로 비동기 복제 중인 경우:

```text
Primary DB 상태 감시
→ CloudWatch alarm 또는 /health-db endpoint
→ Route 53 health check 실패
→ SNS/EventBridge
→ Lambda 실행
→ read replica promote
→ Route 53 DNS record를 새 DB endpoint로 변경
```

private resource는 CloudWatch alarm 기반 health check가 더 깔끔한 선택지로 나온다.

## Hybrid DNS

Hybrid DNS는 VPC와 외부 네트워크 사이에서 private DNS 이름을 서로 해석하게 만드는 구성이다.
외부 네트워크는 peered VPC일 수도 있고, VPN/Direct Connect로 연결된 온프레미스 데이터센터일 수도 있다.

VPC 안의 Route 53 Resolver는 기본적으로 아래 이름을 해석할 수 있다.

- EC2 인스턴스의 내부 DNS 이름
- Private hosted zone record
- Public hosted zone 또는 인터넷 public DNS 이름

하지만 온프레미스 DNS 이름과 AWS private hosted zone 이름을 서로 주고받으려면 Resolver endpoint가 필요하다.

| 종류 | 방향 | 의미 |
| --- | --- | --- |
| Inbound endpoint | On-premise DNS -> AWS Route 53 Resolver | 외부에서 AWS private DNS 이름을 물어볼 때 |
| Outbound endpoint | AWS Route 53 Resolver -> On-premise DNS | AWS에서 온프레미스 DNS 이름을 물어볼 때 |

```text
Inbound endpoint
= 온프레미스가 AWS private DNS를 물어볼 때 들어오는 문

Outbound endpoint
= AWS가 온프레미스 DNS를 물어볼 때 나가는 문
```

Resolver endpoint는 고가용성을 위해 보통 2개 AZ에 만든다.
각 endpoint는 ENI와 private IP를 가지며, IP 하나당 초당 약 10,000 DNS query를 처리한다.

Inbound 예시:

```text
온프레미스 서버
→ app.aws.private 조회
→ 온프레미스 DNS resolver
→ aws.private 도메인은 Route 53 inbound endpoint IP로 forwarding
→ Route 53 Resolver
→ Private hosted zone에서 응답
```

Outbound 예시:

```text
EC2 instance
→ web.onprem.private 조회
→ Route 53 Resolver
→ Resolver rule 확인
→ outbound endpoint
→ 온프레미스 DNS resolver
→ onprem.private record 응답
```

Outbound endpoint는 resolver rule과 같이 쓴다.
Resolver rule은 특정 도메인 질의를 어디로 보낼지 정한다.

- Forwarding rule: `onprem.private` -> 온프레미스 DNS resolver IP.
- System rule: 특정 도메인에 대해 forwarding rule을 쓰지 않도록 오버라이드.
- 자동 system rule: AWS 내부 도메인이나 private hosted zone처럼 Route 53 Resolver가 이미 아는 이름.

여러 rule이 동시에 매칭되면 가장 구체적인 도메인 rule이 이긴다.

Resolver rule은 AWS RAM으로 다른 계정/VPC에 공유할 수 있다.
중앙 네트워크 계정에서 DNS forwarding rule을 만들고 여러 VPC가 재사용하는 패턴이다.

## AWS Global Accelerator

Global Accelerator는 AWS 글로벌 네트워크를 이용해서 애플리케이션 endpoint까지 빠르고 안정적으로 트래픽을 보내는 서비스다.
애플리케이션마다 2개의 static Anycast IP가 생성된다.

흐름:

```text
Client
→ 가장 가까운 AWS Edge location의 Anycast IP
→ AWS backbone network
→ ALB/NLB/EC2/EIP endpoint
```

대상 endpoint:

- Elastic IP
- EC2 instance
- ALB
- NLB

Public endpoint와 private endpoint 모두 가능하다.
단, Elastic IP endpoint를 제외하면 client IP preservation을 지원한다.

## Global Accelerator 장점

- 2개의 static Anycast IP를 제공한다.
- IP가 고정이라 client DNS cache 문제를 줄인다.
- AWS 내부 네트워크를 사용해 latency와 jitter를 줄인다.
- 가장 낮은 지연 시간 기준으로 endpoint에 라우팅한다.
- health check 기반으로 보통 1분 이내 빠른 regional failover가 가능하다.
- 외부 firewall allowlist에는 Anycast IP 2개만 넣으면 된다.
- AWS Shield와 통합되어 DDoS 보호를 받는다.

## CloudFront vs Global Accelerator

둘 다 AWS edge location과 AWS 글로벌 네트워크를 사용하고, Shield와 통합된다.
하지만 목적이 다르다.

| 구분 | CloudFront | Global Accelerator |
| --- | --- | --- |
| 주 목적 | 콘텐츠 전송/CDN | 애플리케이션 트래픽 가속 |
| 프로토콜 | HTTP/HTTPS 중심 | TCP/UDP 지원 |
| 캐싱 | edge에서 캐싱 가능 | 캐싱 없음 |
| 대상 | S3, ALB, custom origin 등 | ALB, NLB, EC2, EIP |
| 대표 사용 | 이미지/비디오/API/동적 웹 가속 | 게임, IoT, VoIP, static IP, 빠른 failover |

시험 감각:

```text
정적/동적 웹 콘텐츠를 edge에서 캐싱/전송
→ CloudFront

TCP/UDP 애플리케이션을 AWS 글로벌 네트워크로 가속
→ Global Accelerator

고정 IP 2개가 필요
→ Global Accelerator

빠른 regional failover와 DNS cache 회피
→ Global Accelerator

게임 UDP, MQTT IoT, VoIP
→ Global Accelerator
```

## Route 53 vs Global Accelerator

둘 다 글로벌 라우팅에 쓰일 수 있지만 동작 방식이 다르다.

| 구분 | Route 53 | Global Accelerator |
| --- | --- | --- |
| 계층 | DNS | Network edge proxy |
| 변경 반영 | TTL/DNS cache 영향 | static Anycast IP 유지 |
| 장애 조치 | DNS 응답 변경 | edge에서 endpoint 전환 |
| 프로토콜 | DNS routing | TCP/UDP |
| 장점 | 다양한 DNS routing policy | 빠른 failover, 고정 IP, AWS backbone |

한 줄로:

```text
Route 53
= DNS 응답을 어디로 줄지 정함

Global Accelerator
= 고정 Anycast IP로 받은 트래픽을 AWS 글로벌 네트워크로 endpoint에 프록시함
```

## 네트워킹/엣지 시험용 한 줄 정리

```text
루트 도메인에 AWS 리소스 연결
→ Route 53 Alias

비율 기반 트래픽 분산
→ Weighted routing

가장 낮은 지연 시간 리전으로 DNS 라우팅
→ Latency-based routing

사용자 위치 기준 라우팅
→ Geolocation

거리+bias 기반 라우팅
→ Geoproximity + Traffic Flow

private endpoint health check
→ CloudWatch alarm health check

온프레미스가 AWS private DNS 질의
→ Route 53 Resolver inbound endpoint

AWS가 온프레미스 DNS 질의
→ Route 53 Resolver outbound endpoint + resolver rule

Resolver rule 계정 간 공유
→ AWS RAM

고정 Anycast IP 2개 + TCP/UDP 가속 + 빠른 failover
→ Global Accelerator

콘텐츠 캐싱/CDN
→ CloudFront
```
