# SAP 서비스 통신

# Step Functions

Step Functions는 여러 AWS 서비스 작업을 순서, 조건, 병렬, 대기, 재시도, 실패 처리까지 포함해서 묶는 서버리스 워크플로 서비스다.
시험에서는 "Lambda 여러 개를 순서대로 호출" 정도보다, **AWS 서비스들을 오케스트레이션하는 상태 머신**으로 이해하는 게 중요하다.

```text
여러 단계의 비즈니스 프로세스
긴 실행 시간
분기/병렬/대기/재시도/오류 처리
사람 승인 같은 장기 워크플로
→ Step Functions
```

## 핵심 감각

- JSON 기반 상태 머신을 만들고, 콘솔에서 시각적으로 실행 흐름을 볼 수 있다.
- 각 실행은 성공, 실패, 취소, 진행 중 같은 상태를 가진다.
- 순차 실행, 병렬 실행, 조건 분기, Wait, timeout, retry, catch 같은 흐름 제어가 가능하다.
- 단순한 Lambda 호출기가 아니라 Lambda, ECS/Fargate, Batch, DynamoDB, SQS, SNS, EMR, Glue, SageMaker 등과 직접 통합된다.
- AWS SDK 통합으로 200개 이상의 AWS 서비스 API를 상태 머신에서 직접 호출할 수 있다.

시험 감각:

```text
Lambda A → Lambda B → Lambda C를 직접 호출
→ 코드 안에 흐름 제어가 숨어서 복잡해짐

Step Functions
→ 흐름, 재시도, 분기, 실패 처리를 상태 머신에 드러냄
```

## 직접 서비스 통합

Step Functions는 많은 작업을 Lambda 없이 직접 할 수 있다.

```text
DynamoDB에 item 쓰기
SQS에 message 보내기
SNS publish
ECS/Fargate task 실행
AWS Batch job 실행
Glue/SageMaker job 시작
다른 Step Functions workflow 시작
```

따라서 시험에서 "중간 Lambda를 최소화", "운영 부담 최소화", "서비스 간 워크플로 조정"이 나오면 Step Functions 직접 통합을 의심한다.

```text
나쁨
Step Functions → Lambda → DynamoDB

가능하면 더 좋음
Step Functions → DynamoDB 직접 호출
```

## Task 종류

| Task | 의미 | 시험 감각 |
| --- | --- | --- |
| Lambda Task | Lambda 함수 호출 | 일반적인 서버리스 단계 |
| Service Task | AWS 서비스 직접 호출 | ECS, Fargate, Batch, DynamoDB, SQS, SNS 등 |
| Activity Task | 외부 worker가 작업을 가져가서 수행 | EC2, 모바일, 온프레미스 worker 등 서버리스 아님 |
| Wait Task | 특정 시간 또는 timestamp까지 대기 | 지연, 승인 대기, 장기 프로세스 |

Activity Task는 Step Functions가 외부 worker에게 일을 "밀어주는" 게 아니라, worker가 Step Functions에 물어보고 작업을 가져가는 방식으로 이해하면 된다.

## Standard vs Express

| 구분 | Standard Workflow | Express Workflow |
| --- | --- | --- |
| 최대 실행 시간 | 최대 1년 | 최대 5분 |
| 사용 상황 | 장기 워크플로, 승인, 감사 추적 | 짧고 대량의 고속 처리 |
| 실행 기록 | 상세 실행 기록 제공 | 실행 기록 대신 CloudWatch Logs 중심 |
| 처리량 | 상대적으로 낮음 | 매우 높음 |
| 과금 | 상태 전환 수 기준 | 실행 수, 기간, 메모리 기준 |
| 실행 보장 | 정확히 한 번 실행에 가까운 장기 처리 감각 | 적어도 한 번 실행 감각 |

시험에서 장기 실행, 사람 승인, 전체 실행 이력 확인이 중요하면 Standard.
짧고 대량의 이벤트 처리, 초고속 워크플로면 Express.

```text
사람 승인/며칠 걸리는 주문 프로세스
→ Standard

초당 대량 요청/짧은 마이크로서비스 오케스트레이션
→ Express
```

## Express: 동기 vs 비동기

Express Workflow는 동기/비동기 호출 감각도 중요하다.

```text
Synchronous Express
→ 실행 결과가 나올 때까지 기다림
→ API Gateway 뒤에서 결과를 바로 반환해야 할 때

Asynchronous Express
→ 워크플로 시작만 확인하고 바로 응답
→ 결과를 즉시 돌려줄 필요 없는 이벤트 처리
```

API Gateway와 붙을 때:

```text
사용자 요청 → API Gateway → Synchronous Express
→ 워크플로 결과를 사용자에게 반환

사용자 요청 → API Gateway → Asynchronous Express
→ "시작됨"만 반환, 처리는 뒤에서 진행
```

## 오류 처리

Step Functions의 큰 장점은 오류 처리를 워크플로 안에 명시할 수 있다는 점이다.

- Retry: 실패한 task를 다시 시도.
- Catch: 실패 시 다른 경로로 분기.
- timeout: 너무 오래 걸리는 task 제어.
- EventBridge: 실행 실패 이벤트를 감지.
- SNS: 실패 알림 발송.

시험 감각:

```text
Lambda가 가끔 실패함
→ Step Functions Retry로 재시도
→ 그래도 실패하면 Catch 또는 EventBridge + SNS 알림
```

## Trigger 방법

Step Functions는 여러 방식으로 시작할 수 있다.

```text
Console
AWS SDK / CLI
Lambda
API Gateway
EventBridge
CodePipeline via EventBridge
다른 Step Functions
```

API 요청으로 복잡한 백엔드 프로세스를 시작해야 하면 API Gateway + Step Functions 조합이 자주 나온다.

## Mechanical Turk 함정

시험에서 Mechanical Turk가 나오면 Step Functions와 자동 통합된다고 생각하면 안 된다.
Mechanical Turk와 사람 작업 기반 워크플로가 강조되면 예전 서비스인 SWF가 더 자연스러운 선택지로 나올 수 있다.

```text
Mechanical Turk 직접 통합
→ Step Functions 아님
→ SWF 쪽 함정 가능
```

## 언제 Step Functions가 답인가

```text
여러 Lambda/서비스 호출을 순서대로 조정
분기/병렬/대기/재시도/실패 처리 필요
장기 실행 워크플로
사람 승인 단계
상태와 실행 이력을 보고 싶음
서비스 간 직접 통합으로 Lambda glue code를 줄이고 싶음
→ Step Functions
```

반대로 단순 메시지 버퍼링이면 SQS, 이벤트 라우팅이면 EventBridge, 실시간 스트리밍이면 Kinesis를 먼저 본다.

```text
순서 있는 workflow 제어
→ Step Functions

비동기 queue로 decoupling
→ SQS

이벤트 소스와 타겟 라우팅
→ EventBridge

대량 실시간 데이터 스트림
→ Kinesis
```

# SQS

SQS는 서버리스 관리형 메시지 큐다.
시험에서는 세부 API보다 **서비스를 분리해서 독립적으로 확장하고, 작업을 비동기 처리하는 큐**로 이해하면 된다.

```text
Producer와 Consumer를 분리
작업을 비동기로 처리
Consumer 장애/일시적 트래픽 폭증을 흡수
작업이 적어도 한 번은 처리되게 함
→ SQS
```

## 핵심 감각

- 서버리스, 완전관리형 queue.
- IAM과 통합된다.
- 메시지 최대 크기는 256KB.
- 큰 메시지는 S3에 저장하고, SQS에는 S3 object key만 넣는다.
- Consumer는 EC2, ECS, Lambda 등으로 만들 수 있다.
- Standard Queue는 높은 처리량과 at-least-once 처리를 제공한다.
- FIFO Queue는 순서 보장과 중복 제거가 필요할 때 사용한다.

큰 메시지 패턴:

```text
큰 payload
→ S3에 저장
→ SQS에는 S3 key/reference 전송
→ Consumer가 S3에서 원본 조회
```

## 왜 SQS를 쓰는가

SQS의 핵심은 decoupling이다.

```text
Producer가 바로 Consumer를 호출
→ Consumer가 느리거나 죽으면 전체 흐름 영향

Producer → SQS → Consumer
→ Producer와 Consumer가 독립적으로 확장/장애 처리
```

사용 사례:

```text
주문 요청을 큐에 넣고 worker가 처리
이미지 처리 작업을 큐에 넣고 EC2/ECS가 처리
DynamoDB 쓰기 폭주를 SQS로 완충
요청 queue / 응답 queue로 비동기 작업 처리
```

## DynamoDB 쓰기 버퍼

DynamoDB에 쓰기 요청이 한 번에 몰리면 throttle이 날 수 있다.
이때 바로 DynamoDB에 쓰지 않고 SQS에 먼저 넣고, 별도 worker가 천천히 DynamoDB에 쓰게 만들 수 있다.

```text
Client
→ SQS
→ Worker
→ DynamoDB
```

시험 감각:

```text
쓰기 폭주를 완충하고 싶다
Consumer를 수평 확장하고 싶다
DynamoDB throttle을 줄이고 싶다
→ SQS buffer
```

## Visibility Timeout

Consumer가 메시지를 읽으면 그 메시지는 잠깐 다른 Consumer에게 안 보인다.
이 시간을 visibility timeout이라고 한다.

```text
Consumer가 메시지 수신
→ visibility timeout 동안 메시지 숨김
→ 처리 성공 후 DeleteMessage
→ 삭제하지 못하면 timeout 후 다시 queue에 나타남
```

따라서 SQS는 기본적으로 **at-least-once** 처리 감각이다.
같은 메시지가 두 번 처리될 수 있으므로 Consumer는 멱등성이 있어야 한다.

```text
멱등성
= 같은 메시지를 여러 번 처리해도 최종 결과가 중복되지 않게 설계
```

DynamoDB 예시:

```text
나쁨
같은 메시지를 받을 때마다 새 row insert
→ 중복 데이터 발생

좋음
messageId를 key로 upsert/conditional write
→ 두 번 처리해도 결과는 하나
```

## Dead Letter Queue

DLQ는 계속 실패하는 메시지를 따로 빼두는 queue다.
메시지가 여러 번 처리 실패하면 source queue에 계속 돌아오며 실패 루프를 만들 수 있다.
이때 max receive count를 넘으면 DLQ로 보낸다.

```text
Source Queue
→ Consumer 처리 실패
→ 다시 Source Queue
→ 여러 번 실패
→ DLQ로 이동
```

DLQ의 목적:

- 문제 메시지 격리.
- Consumer 코드 디버깅.
- 실패 메시지를 나중에 재처리.
- 정상 메시지 처리를 막는 poison pill 방지.

시험 포인트:

```text
Standard Queue의 DLQ는 Standard Queue
FIFO Queue의 DLQ는 FIFO Queue
DLQ 보존 기간은 충분히 길게, 예: 최대 14일
```

DLQ redrive를 사용하면 DLQ의 메시지를 원래 source queue로 다시 보낼 수 있다.
단, 이 경우에도 Consumer 멱등성이 중요하다.

## Lambda와 SQS

Lambda는 event source mapping으로 SQS를 읽는다.
Lambda가 SQS에 의해 직접 "푸시"되는 느낌이 아니라, 이벤트 소스 매핑이 SQS를 long polling으로 읽고 Lambda를 호출한다고 이해하면 된다.

```text
SQS
→ Event Source Mapping이 long polling
→ 메시지 batch로 Lambda 호출
```

중요한 설정:

- batch size를 조절할 수 있다.
- 빠른 처리면 작은 batch, 효율이면 큰 batch.
- visibility timeout은 Lambda timeout보다 충분히 길어야 한다.
- AWS 권장 감각은 Lambda timeout의 약 6배.

DLQ 주의:

```text
SQS → Lambda 구조에서 실패 메시지 관리
→ Lambda DLQ가 아니라 SQS queue의 DLQ를 설정

Lambda DLQ
→ 비동기 Lambda 호출용
```

이 차이가 시험 함정으로 나온다.

## Standard Queue vs FIFO Queue

| 구분 | Standard Queue | FIFO Queue |
| --- | --- | --- |
| 순서 | best-effort ordering | 순서 보장 |
| 처리 보장 | at-least-once | exactly-once processing 감각, 중복 제거 |
| 처리량 | 매우 높음 | 제한 있음 |
| 사용 상황 | 일반적인 비동기 decoupling | 순서/중복 제거가 중요한 작업 |

FIFO 처리량 감각:

```text
batching 없음
→ 초당 약 300 message

batching 사용
→ 초당 약 3,000 message
```

숫자는 시험에서 가끔 감으로 묻는다.
고처리량이 가장 중요하면 Standard, 순서와 중복 제거가 중요하면 FIFO를 본다.

## Request Queue / Response Queue 패턴

긴 작업을 동기 요청으로 기다리지 않고 큐로 분리할 수 있다.

```text
Client
→ Request Queue
→ Worker 처리
→ Response Queue
→ Client가 결과 확인
```

이 구조의 장점:

- 양쪽을 독립적으로 확장.
- worker 장애 시 다른 worker가 처리 가능.
- 요청을 수평 분산.
- 시스템 전체 fault tolerance 증가.

## 언제 SQS가 답인가

```text
서비스 간 결합도를 낮추고 싶다
Consumer가 느리거나 일시적으로 죽어도 요청을 잃고 싶지 않다
작업을 비동기로 처리하고 싶다
트래픽 폭증을 buffer로 흡수하고 싶다
적어도 한 번 처리하면 된다
실패 메시지를 DLQ로 격리하고 싶다
→ SQS
```

반대로:

```text
복잡한 순서/분기/재시도 workflow
→ Step Functions

이벤트를 여러 타겟으로 라우팅
→ EventBridge

실시간 데이터 스트리밍/분석 파이프라인
→ Kinesis

pub/sub fanout
→ SNS
```

# Amazon MQ

Amazon MQ는 RabbitMQ와 ActiveMQ를 AWS에서 관리형으로 제공하는 메시지 브로커 서비스다.
SQS/SNS는 AWS 네이티브 API를 쓰지만, Amazon MQ는 기존 온프레미스 애플리케이션이 쓰던 오픈 프로토콜을 유지하고 싶을 때 쓴다.

```text
기존 애플리케이션이 MQTT / AMQP / STOMP / OpenWire / WSS 사용
애플리케이션을 SQS/SNS API로 재작성하고 싶지 않음
기존 RabbitMQ / ActiveMQ / IBM MQ / TIBCO EMS 계열을 AWS로 마이그레이션
→ Amazon MQ
```

시험 감각:

```text
클라우드 네이티브 신규 설계
→ SQS / SNS

기존 메시지 브로커 호환성 유지, lift-and-shift 마이그레이션
→ Amazon MQ
```

주의할 점:

- SQS/SNS처럼 거의 무한 확장되는 서버리스 서비스는 아니다.
- 브로커 서버 기반이므로 용량과 가용성 고려가 필요하다.
- 고가용성이 필요하면 Multi-AZ 장애 조치 구성을 사용한다.
- queue와 topic 기능을 모두 제공할 수 있다.

# SNS

SNS는 Pub/Sub 방식의 서버리스 알림/메시지 fanout 서비스다.
Producer는 SNS Topic 하나에 메시지를 publish하고, SNS가 여러 subscriber에게 같은 메시지를 뿌린다.

```text
하나의 이벤트를 여러 수신자에게 동시에 알림
Email/SMS/mobile push/HTTP endpoint/Lambda/SQS/Firehose 등으로 fanout
→ SNS
```

## SQS와 SNS의 차이

| 구분 | SQS | SNS |
| --- | --- | --- |
| 핵심 패턴 | Queue | Pub/Sub Topic |
| 목적 | 작업을 쌓아두고 Consumer가 가져가 처리 | 하나의 메시지를 여러 Subscriber에게 즉시 전달 |
| 수신 방식 | Consumer가 queue에서 poll | SNS가 subscriber로 push |
| 메시지 보관 | queue에 보관됨 | subscriber로 전달 중심 |
| 대표 사용 | 비동기 작업 처리, 버퍼링, worker decoupling | 알림, fanout, 이벤트 브로드캐스트 |
| 장애 감각 | Consumer가 죽어도 메시지가 queue에 남음 | 각 subscriber 전달 성공/실패 관리가 중요 |

시험 감각:

```text
작업을 쌓아두고 worker가 하나씩 처리
트래픽 폭증을 buffer로 흡수
Consumer가 늦어도 메시지를 보관
→ SQS

이벤트 하나를 여러 시스템에 동시에 알림
Email, Lambda, SQS 여러 곳으로 fanout
구독자가 각자 같은 메시지를 받음
→ SNS
```

## SNS Fanout 패턴

SNS는 SQS와 같이 쓰면 강력하다.
SNS Topic 하나에 publish하고, 여러 SQS queue를 subscribe시키면 각 서비스가 자기 queue에서 독립적으로 처리할 수 있다.

```text
Order Service
→ SNS Topic
→ Payment Queue
→ Shipping Queue
→ Fraud Check Queue
→ Email Notification
```

이 구조의 장점:

- Producer는 SNS Topic 하나만 알면 된다.
- 구독자를 추가해도 Producer 코드를 덜 바꾼다.
- 각 consumer는 자기 SQS queue를 통해 독립적으로 확장한다.
- 한 consumer 장애가 다른 consumer에 영향을 덜 준다.

시험에서 "하나의 이벤트를 여러 SQS queue로 복제", "fanout", "여러 시스템이 같은 이벤트를 받아야 함"이 나오면 SNS + SQS 조합을 본다.

## Fan Out 패턴이 정확히 뭔가

Fan Out은 **하나의 입력 이벤트를 여러 대상에게 복제해서 뿌리는 구조**다.

```text
1개 이벤트
→ 여러 consumer에게 퍼짐
```

직접 보내면 Producer가 모든 대상과 연결되어야 한다.

```text
Buying Service
→ Fraud Queue
→ Shipping Queue
→ Email Service
→ Analytics Queue
```

이러면 대상이 늘어날 때마다 Producer 코드를 바꾸거나 연결을 추가해야 한다.
중간에 한 대상 전송이 실패하면 처리도 지저분해진다.

Fan Out은 Producer가 SNS Topic 하나에만 보낸다.

```text
Buying Service
→ SNS Topic
→ Fraud Queue
→ Shipping Queue
→ Email Service
→ Analytics Queue
```

핵심은 이거다.

```text
Producer는 한 번만 publish
SNS가 여러 subscriber에게 복제 전달
각 subscriber는 독립적으로 처리
```

SQS queue를 subscriber로 붙이면 메시지 내구성, 지연 처리, 재시도, DLQ까지 가져갈 수 있다.

시험 감각:

```text
하나의 이벤트를 여러 SQS queue에 안전하게 전달
각 consumer가 독립적으로 확장/재시도
나중에 consumer를 추가해도 producer 변경 최소화
→ SNS + SQS Fan Out
```

## S3 Event Fan Out

S3 이벤트 알림은 같은 이벤트 조건을 여러 목적지로 마음대로 중복 설정하기 어렵다.
예를 들어 `ObjectCreated` + prefix `images/` 조건으로 여러 queue에 보내고 싶으면 SNS를 중간에 둔다.

```text
S3 ObjectCreated
→ SNS Topic
→ Image Resize Queue
→ Metadata Extract Queue
→ Security Scan Queue
→ Lambda / Email 등
```

시험에서 "S3 이벤트 하나를 여러 SQS queue 또는 여러 대상으로 보내야 함"이 나오면 SNS Fan Out을 본다.

## Cross-Region Fan Out

SNS Topic은 다른 리전의 SQS queue로도 메시지를 보낼 수 있다.
단, 접근 정책과 권한이 허용되어야 한다.

```text
SNS Topic, us-east-1
→ SQS Queue, us-west-2
```

## Queue Access Policy

SNS가 SQS queue에 메시지를 넣으려면 SQS queue policy가 SNS topic의 `SendMessage`를 허용해야 한다.

```text
SNS Topic이 SQS Queue에 쓸 수 있도록
SQS Queue access policy 필요
```

시험에서 SNS + SQS 구성이 안 되는 이유를 묻는다면 queue policy를 의심한다.

## SNS to Firehose

SNS는 Amazon Data Firehose로도 메시지를 보낼 수 있다.
Firehose는 받은 데이터를 S3, Redshift, OpenSearch 같은 목적지로 적재할 수 있다.

```text
Application
→ SNS Topic
→ Data Firehose
→ S3 / Redshift / OpenSearch
```

SNS 메시지를 장기 저장하거나 분석 목적지로 흘려보내고 싶을 때 쓴다.

## SNS FIFO + SQS FIFO

순서 보장과 중복 제거가 필요한 fan out이면 SNS FIFO Topic과 SQS FIFO Queue를 조합한다.

```text
Producer
→ SNS FIFO Topic
→ SQS FIFO Queue A
→ SQS FIFO Queue B
```

SNS FIFO 특징:

- message group ID 기준으로 순서 보장.
- deduplication ID 또는 content-based deduplication으로 중복 제거.
- FIFO fan out을 위해 사용.
- 처리량 제한은 SQS FIFO 감각과 비슷하게 본다.

시험 감각:

```text
여러 consumer에게 같은 이벤트를 전달해야 함
그런데 순서도 보장해야 함
중복 제거도 필요함
→ SNS FIFO + SQS FIFO
```

주의:

```text
일반 fan out
→ SNS Standard + SQS Standard

순서/중복 제거가 중요한 fan out
→ SNS FIFO + SQS FIFO
```

## Subscriber 종류

SNS Topic은 여러 종류의 subscriber를 가질 수 있다.

```text
SQS
Lambda
HTTP/HTTPS endpoint
Email
SMS
Mobile push
Amazon Data Firehose
```

Firehose로 보내면 S3, Redshift, OpenSearch 같은 곳으로 적재하는 파이프라인을 만들 수 있다.

## Event Source로서 SNS

AWS 서비스들은 알림을 SNS Topic으로 보낼 수 있다.
시험에서 "알림", "운영 이벤트 통지"가 나오면 SNS가 자주 등장한다.

예:

```text
CloudWatch Alarm
Auto Scaling Group notification
CloudFormation event
AWS Budgets
S3 event
DMS event
Lambda
DynamoDB
RDS event
→ SNS Topic
```

전부 외우기보다, AWS 서비스에서 발생한 이벤트를 사람이나 다른 시스템에 알리는 대표 서비스가 SNS라고 잡으면 된다.

## Message Filtering

SNS subscriber는 filter policy를 사용할 수 있다.
기본적으로 topic에 publish된 메시지는 모든 subscriber에게 가지만, filter를 걸면 필요한 메시지만 받을 수 있다.

```text
SNS Topic: order-events

Payment Queue
→ eventType = payment

Shipping Queue
→ eventType = shipping
```

시험 감각:

```text
같은 SNS Topic을 쓰되 subscriber마다 필요한 메시지만 받고 싶다
→ SNS message filtering
```

예시:

```text
SNS Topic: order-events

발주 Queue
→ status = "placed"만 수신

취소 Queue
→ status = "cancelled"만 수신

전체 감사 Queue
→ filter 없음, 모든 메시지 수신
```

Fan Out과 filtering을 같이 쓰면 하나의 topic으로 여러 업무 흐름을 깔끔하게 분리할 수 있다.

## 보안

- 전송 중 암호화 지원.
- 저장 시 암호화는 KMS key 사용.
- SNS API 권한은 IAM 정책으로 제어.
- SNS topic access policy는 S3 bucket policy처럼 리소스 기반 정책 감각으로 사용한다.
- 다른 계정이나 AWS 서비스가 특정 topic에 publish하도록 허용할 때 topic policy가 중요하다.

```text
S3 event가 SNS Topic에 publish해야 함
다른 AWS 계정이 SNS Topic에 publish/subscribe해야 함
→ SNS topic access policy 확인
```

## SNS Delivery Retry와 DLQ

SNS가 subscriber에게 메시지를 전달하지 못하면 delivery policy에 따라 재시도한다.
특히 AWS 관리형 endpoint인 SQS, Lambda, Data Firehose 같은 대상은 SNS가 꽤 오래 재시도한다.

```text
SNS Topic
→ Subscriber 전달 실패
→ delivery policy에 따라 retry
→ 그래도 실패하면 DLQ 또는 discard
```

AWS Managed endpoint:

```text
SNS → SQS
SNS → Lambda
SNS → Data Firehose
```

이런 AWS 관리형 대상은 기본 재시도 정책이 매우 길다.

```text
immediate retry: 즉시 3회
pre-backoff: 1초 간격 2회
backoff: 1~20초 지수 백오프 10회
post-backoff: 20초 간격으로 대량 재시도
→ 최대 약 23일 / 총 100,015회 재시도
```

즉 AWS 서비스 대상은 잠깐 장애가 났다고 바로 메시지를 버리지 않는다.

시험에서 중요한 감각:

```text
SNS DLQ는 Topic에 붙는 게 아니라 Subscription에 붙는다
```

예를 들어 하나의 SNS Topic에 이메일 구독과 HTTP 구독이 있으면, 각각의 구독에 별도 DLQ를 둘 수 있다.

```text
SNS Topic
→ Email Subscription → Email용 DLQ
→ HTTP Subscription  → HTTP용 DLQ
```

DLQ를 설정하지 않았고 재시도도 모두 실패하면 메시지는 폐기될 수 있다.
SNS DLQ는 SQS queue를 사용한다.
SNS FIFO Topic의 DLQ는 SQS FIFO Queue를 사용해야 한다.

HTTP/S endpoint는 사용자 지정 delivery policy를 지원한다.
즉 재시도 횟수, 최소/최대 지연, backoff, throttling 같은 재시도 방식을 조절할 수 있다.

```text
HTTP/S subscriber의 backend를 과부하시키고 싶지 않음
재시도 간격/횟수를 직접 제어하고 싶음
→ SNS custom delivery policy
```

SQS와 비교:

```text
SQS DLQ
→ Consumer가 메시지를 여러 번 처리 실패하면 DLQ로 이동

SNS DLQ
→ SNS가 특정 subscription으로 배달 실패하면 DLQ로 이동
```

## 언제 SNS가 답인가

```text
하나의 메시지를 여러 대상으로 보내야 함
pub/sub fanout
알림, 이메일, SMS, 모바일 push
여러 SQS queue에 같은 이벤트 전달
subscriber별 메시지 필터링
AWS 서비스 이벤트를 알림으로 전송
→ SNS
```

반대로:

```text
메시지를 쌓아두고 worker가 처리
→ SQS

복잡한 순서/조건/재시도 workflow
→ Step Functions

대량 실시간 스트리밍
→ Kinesis

기존 RabbitMQ/ActiveMQ 프로토콜 유지
→ Amazon MQ
```

# SQS / SNS / Kinesis Data Streams 구분

셋 다 메시지나 이벤트를 다루지만, 목적이 다르다.

```text
SQS = 작업 대기줄
SNS = 알림 방송
Kinesis Data Streams = 이벤트 녹화본 / 실시간 로그
```

| 서비스 | 한 줄 정의 | 언제 쓰는가 | 익숙한 비유 |
|---|---|---|---|
| SQS | 메시지를 queue에 쌓고 worker가 꺼내 처리 | 비동기 작업 처리, decoupling, retry, DLQ | RabbitMQ queue, Celery broker, Redis List 작업 큐 |
| SNS | topic에 publish하면 여러 subscriber에게 fanout | 알림, pub/sub, 한 이벤트를 여러 시스템에 전파 | 이벤트 방송국, push notification |
| Kinesis Data Streams | 이벤트를 시간순 로그처럼 저장하고 consumer가 읽음 | 대량 실시간 이벤트, replay, 순서 보장, 실시간 분석 | Kafka, Redis Stream |

## 판단 기준

### SQS가 답인 경우

```text
작업을 줄 세워두고 worker가 처리
consumer가 처리 후 삭제
처리 실패 시 retry / DLQ
traffic spike를 queue로 완충
visibility timeout
→ SQS
```

예:

```text
이미지 리사이징 요청
이메일 발송 작업
결제 후 영수증 생성
Lambda/ECS worker가 하나씩 처리할 작업
```

### SNS가 답인 경우

```text
하나의 이벤트를 여러 곳으로 동시에 전달
pub/sub
fanout
Email / SMS / Lambda / SQS / HTTP endpoint로 push
subscriber별 filter policy
→ SNS
```

예:

```text
주문 생성 이벤트를 결제/배송/마케팅 서비스에 모두 알림
CloudWatch Alarm을 이메일이나 Lambda로 전달
여러 SQS queue에 같은 이벤트 복제
```

### Kinesis Data Streams가 답인 경우

```text
대량의 이벤트가 계속 들어옴
streaming data
real-time analytics
consumer가 같은 데이터를 각자 읽음
보존 기간 안에서 replay
partition key / shard / ordered records
→ Kinesis Data Streams
```

예:

```text
클릭스트림
애플리케이션 로그
게임 이벤트
IoT 센서 데이터
실시간 거래 이벤트 분석
```

### SQS FIFO vs Kinesis 순서 보장

둘 다 순서를 다룰 수 있어서 헷갈린다.

| 요구사항 | 더 자연스러운 답 |
|---|---|
| worker에게 작업을 맡기고 처리 후 삭제 | SQS FIFO |
| 중복 제거, DLQ, queue 기반 작업 처리 | SQS FIFO |
| MessageGroupId 기준으로 순서 유지 | SQS FIFO |
| 이벤트를 스트림으로 받아 고객별 순서 유지하며 대량 처리 | Kinesis Data Streams |
| partition key 기준으로 순서 유지 | Kinesis Data Streams |
| 재처리, 여러 consumer, 실시간 분석 가능성 | Kinesis Data Streams |

예를 들어 문제에서 "수만 개의 주문을 처리하고, 각 고객이 주문한 순서대로 처리"라고 하면 전역으로 모든 주문을 한 줄로 세우는 것이 아니다.
고객별 순서를 유지하라는 뜻에 가깝다.

```text
customerId = partition key
→ 같은 고객의 주문은 같은 shard로 들어감
→ shard 안에서 순서 유지
→ Kinesis Data Streams
```

SQS FIFO도 `MessageGroupId = customerId`로 고객별 순서 보장이 가능하다.
하지만 시험에서 "수만 개", "streaming", "여러 consumer", "replay", "실시간 분석" 느낌이 강하면 Kinesis를 먼저 본다.

## 자주 나오는 조합

### SNS + SQS

가장 흔한 fanout 패턴이다.

```text
주문 생성
→ SNS Topic
  → 결제 서비스 SQS
  → 배송 서비스 SQS
  → 마케팅 서비스 SQS
```

SNS는 이벤트를 방송하고, 각 서비스는 자기 SQS queue에 쌓인 메시지를 자기 속도로 처리한다.
한 서비스가 느리거나 장애가 나도 다른 서비스는 영향을 덜 받는다.

시험 감각:

```text
하나의 이벤트를 여러 consumer에게 보내야 함
각 consumer가 독립적으로 retry/DLQ/처리 속도를 가져야 함
→ SNS + SQS
```

## Kafka / Redis Stream과 비교

- Kafka와 가장 가까운 AWS 서비스는 Amazon MSK이고, AWS 네이티브로는 Kinesis Data Streams가 가깝다.
- Redis Stream도 SQS보다는 Kinesis/Kafka 쪽에 더 가깝다. append-only 로그, consumer group, ID 기반 읽기 감각이 있기 때문이다.
- SQS는 Redis Stream보다는 Redis List 기반 작업 큐, Celery queue, RabbitMQ queue에 더 가깝다.

짧게 기억:

```text
일을 맡긴다 → SQS
소식을 뿌린다 → SNS
이벤트 흐름을 쌓고 읽는다 → Kinesis Data Streams
```
