# EBS, Instance Store, EFS 선택 기준

스토리지 문제는 먼저 "무엇을 저장하느냐"보다 "어떻게 접근하느냐"를 봐야 한다.

```text
EC2 한 대에 붙는 고성능 디스크
→ EBS

EC2 호스트에 붙은 초고속 임시 로컬 디스크
→ Instance Store

여러 Linux 인스턴스가 동시에 공유하는 파일 시스템
→ EFS

HPC용 고성능 공유 파일 시스템
→ FSx for Lustre

객체 저장소, 파일 시스템 아님
→ S3
```

## 스토리지 비용 순위 감각

시험에서 "가장 저렴한 스토리지"를 고르라고 나오면 먼저 사용 사례가 맞는지 보고, 그 다음 비용 순서를 본다.
S3, EBS, EFS는 서로 용도가 다르기 때문에 단순 가격만 보고 바꾸면 안 된다.

```text
비싼 쪽

EBS io1 / io2
  ↓
EFS Standard / EFS One Zone
  ↓
EBS gp2 / gp3
  ↓
EBS st1
  ↓
EFS Standard-IA ≈ S3 Standard
  ↓
EBS sc1
  ↓
EFS One Zone-IA
  ↓
S3 Standard-IA 이하, Glacier 계열

싼 쪽
```

대략적인 시험 감각:

| 가격대 | 서비스/클래스 | 기억할 포인트 |
| --- | --- | --- |
| 매우 비쌈 | EBS io1/io2 | 프로비저닝 IOPS 비용 때문에 가장 비싼 축. DB, SAP HANA, 지연 민감 워크로드 |
| 비쌈 | EFS Standard, EFS One Zone | 관리형 NFS 파일 시스템. 여러 EC2 공유 가능하지만 EBS gp보다 비싼 편 |
| 중간 | EBS gp2/gp3 | 일반 EC2 범용 블록 스토리지 |
| 저렴 | EBS st1 | HDD 처리량 최적화. 순차 읽기/쓰기, 로그, 빅데이터 |
| 저렴 | EFS Standard-IA, S3 Standard | EFS IA는 자주 안 보는 파일을 싸게 보관. 접근하면 검색 비용 발생 가능 |
| 더 저렴 | EBS sc1 | HDD 콜드 스토리지. 자주 접근하지 않는 블록 데이터 |
| EFS 중 최저 | EFS One Zone-IA | 가장 저렴한 EFS 계열. 단일 AZ 손실 위험과 검색 비용 고려 |
| S3 최저권 | S3 IA / Glacier 계열 | 객체 저장소. 장기 보관/아카이브일수록 저렴하지만 검색 지연/검색 비용 고려 |

시각적으로 외우기:

```text
EBS io1/io2 ─ EFS Std/OneZone ─ EBS gp2/gp3 ─ EBS st1 ─ EFS Std-IA/S3 Std ─ EBS sc1 ─ EFS OneZone-IA ─ S3 IA/Glacier
   $$$$             $$$              $$            $            $                 $          $              cheapest
```

시험에서 걸러내는 법:

```text
최고 IOPS / DB / 지연 민감
→ EBS io1/io2가 맞을 수 있음. 단, 비쌈.

여러 Linux EC2가 같은 파일 공유
→ EFS. 비용만 보고 EBS로 바꾸면 오답 가능.

단일 EC2의 일반 디스크
→ gp3 우선 감각.

순차 처리용 저렴한 HDD
→ st1.

콜드 블록 스토리지
→ sc1.

정적 객체 / 아카이브 / 가장 저렴한 장기 보관
→ S3 IA 또는 Glacier 계열.

EFS를 써야 하는데 가장 저렴해야 함
→ EFS One Zone-IA. 단일 AZ 위험 감수.
```

핵심:

```text
가격만 보면 S3 Glacier 계열이 싸다.
하지만 파일 시스템이 필요하면 S3는 대체재가 아니다.

EFS 범위 안에서 최저 비용
→ EFS One Zone-IA

EBS/EFS 전체에서 가장 비싼 축
→ EBS io1/io2
```

## EBS 핵심 감각

EBS는 EC2에 붙이는 네트워크 블록 스토리지다.

- 특정 AZ에 속한다.
- 일반적으로 한 번에 하나의 EC2에 붙인다.
- 다른 AZ로 옮기려면 snapshot을 만들고 대상 AZ에서 volume으로 복원한다.
- OS boot volume으로 쓸 수 있다.
- 데이터베이스처럼 낮은 지연 시간과 일관된 IOPS가 필요할 때 적합하다.

시험 감각:

```text
단일 EC2용 영구 블록 스토리지
→ EBS

고성능 DB, SAP HANA, Oracle, SQL Server 같은 IOPS 민감 워크로드
→ io1 / io2 / io2 Block Express

대부분 범용 워크로드
→ gp3
```

## EBS Multi-Attach와 EFS 차이

EBS도 `io1`, `io2`에서 Multi-Attach가 가능하다.
하지만 이것은 EFS와 같은 "일반 공유 파일 시스템"이 아니다.

| 구분 | EBS Multi-Attach | EFS |
| --- | --- | --- |
| 스토리지 유형 | Block storage | File storage, NFS |
| 공유 범위 | 같은 AZ의 여러 EC2 | 여러 AZ의 여러 EC2 |
| 동시 쓰기 | 애플리케이션/클러스터가 직접 제어해야 함 | NFS 공유 파일 시스템으로 설계됨 |
| 일반 파일 공유 | 부적합 | 적합 |
| 대표 사용 | 고가용성 클러스터 앱, 클러스터 파일 시스템 | WordPress, CMS, 공유 파일, 홈 디렉터리 |

중요한 점:

```text
EBS Multi-Attach
= 여러 EC2가 같은 디스크 블록을 볼 수 있게 해줌
= 동시 쓰기 충돌을 EBS가 알아서 해결해주는 것이 아님

EFS
= 여러 서버가 같은 파일/디렉터리를 공유하도록 설계됨
```

시험에서 "여러 EC2가 같은 파일을 읽고 써야 한다"면 보통 EFS다.
EBS Multi-Attach는 특수 클러스터 애플리케이션이나 클러스터 파일 시스템이 전제될 때만 선택한다.

## Instance Store 핵심 감각

Instance Store는 EC2가 실행되는 물리 호스트에 붙은 로컬 디스크다.

- 매우 빠르다.
- 지연 시간이 낮고 IOPS가 높다.
- 인스턴스 stop/terminate/장애 시 데이터 손실 가능성이 있다.
- 영구 데이터 저장소가 아니다.

시험 감각:

```text
가장 빠른 임시 로컬 스토리지
→ Instance Store

캐시, 버퍼, 임시 처리 파일, HPC scratch space
→ Instance Store

영구 저장 필요
→ EBS / EFS / S3
```

# EFS, Elastic File System

EFS는 AWS 관리형 NFS 파일 시스템이다.
여러 Linux EC2, ECS/EKS task, Lambda, 온프레미스 서버가 같은 파일 시스템을 동시에 마운트할 수 있다.

시험에서는 EFS를 "공유 파일 시스템"으로만 외우면 부족하고, 아래 조건들을 같이 봐야 한다.

## POSIX 호환 파일 시스템

POSIX는 Unix/Linux 계열에서 파일을 다루는 표준 규칙이다.

EFS가 POSIX compatible이라는 말은 Linux 애플리케이션이 일반 파일 시스템처럼 쓸 수 있다는 뜻이다.

예:

```text
디렉터리 구조
파일 소유자/그룹
chmod / chown 권한
파일 락
표준 파일 API read/write
```

비교:

```text
POSIX 호환 공유 파일 시스템
→ EFS

객체 저장소, POSIX 파일 시스템 아님
→ S3

Windows 파일 공유
→ FSx for Windows File Server
```

EFS는 Linux 기반 AMI와 잘 맞고, Windows 워크로드용 공유 파일 시스템으로 고르면 안 된다.

## EFS 네트워크 구조

EFS는 파일 시스템 자체에 직접 EC2가 붙는 느낌이 아니라, VPC 안의 mount target을 통해 접근한다.

- EFS는 한 리전에 존재한다.
- 하나의 VPC에 연결된다.
- AZ마다 mount target을 만들 수 있다.
- mount target은 ENI를 가진다.
- EC2는 같은 AZ의 mount target을 통해 EFS에 접근하는 것이 일반적이다.
- NFS 접근은 security group으로 제어한다.

시험 감각:

```text
EFS 접근 제어
→ Security Group에서 NFS 2049 허용

Multi-AZ EC2가 같은 파일 시스템 공유
→ 각 AZ에 EFS mount target
```

## 온프레미스에서 EFS 마운트

온프레미스 서버도 EFS를 마운트할 수 있다.
단, AWS와 네트워크로 연결되어 있어야 한다.

필요한 연결:

- Direct Connect
- Site-to-Site VPN

주의 포인트:

```text
EC2에서 EFS 마운트
→ DNS 이름 사용 가능

온프레미스에서 EFS 마운트
→ mount target ENI의 IP 주소 사용
```

강의에서 "온프레미스는 DNS 대신 ENI IPv4를 사용한다"는 포인트가 나온다.
하이브리드 환경 문제에서 꽤 시험스럽다.

## EFS 성능 모드

EFS 성능 모드는 파일 시스템 생성 시 선택한다.

| 모드 | 특징 | 선택 기준 |
| --- | --- | --- |
| General Purpose | 낮은 지연 시간, 기본값 | 웹 서버, CMS, WordPress |
| Max I/O | 더 높은 처리량/병렬성, 지연 시간 증가 | 빅데이터, 미디어 처리, 대규모 병렬 접근 |

시험 감각:

```text
레이턴시에 민감한 일반 웹/CMS
→ General Purpose

수천 클라이언트, 높은 병렬성, 처리량 중심
→ Max I/O
```

## EFS 처리량 모드

EFS 처리량은 "파일 시스템 크기와 처리량이 연결되어 있느냐"가 핵심이다.

| 모드 | 의미 | 선택 기준 |
| --- | --- | --- |
| Bursting | 저장된 데이터 크기에 따라 기본 처리량이 커짐 | 일반적이고 예측 가능한 워크로드 |
| Provisioned | 저장 용량과 무관하게 처리량을 직접 지정 | 데이터는 적지만 높은 처리량 필요 |
| Elastic | 워크로드에 따라 처리량 자동 확장/축소 | 예측 어려운 워크로드 |

쉽게 보면:

```text
Bursting
= 파일 시스템이 커지면 처리량도 같이 커짐

Provisioned
= 파일은 적어도 처리량만 크게 따로 살 수 있음

Elastic
= 워크로드에 맞춰 AWS가 처리량을 자동 조절
```

시험에서 "작은 EFS인데 높은 처리량이 필요하다"면 Provisioned Throughput을 떠올린다.
"패턴 예측이 어렵다"면 Elastic Throughput을 떠올린다.

## EFS 스토리지 클래스와 수명 주기

EFS는 파일 접근 빈도에 따라 비용을 줄일 수 있다.

| 클래스 | 용도 |
| --- | --- |
| EFS Standard | 자주 접근하는 파일, Multi-AZ |
| EFS Infrequent Access, IA | 자주 접근하지 않는 파일 |
| EFS Archive | 거의 접근하지 않는 장기 보관 파일 |
| EFS One Zone | 단일 AZ, 개발/테스트나 비용 절감 |
| EFS One Zone-IA | 단일 AZ + 드문 접근 |

Lifecycle policy로 일정 기간 접근하지 않은 파일을 IA나 Archive로 자동 이동할 수 있다.
다시 접근하면 검색 비용이 발생할 수 있다.

시험 감각:

```text
프로덕션 Multi-AZ 고가용성
→ EFS Standard

비용 절감 + 단일 AZ 감수 가능
→ EFS One Zone

오래 접근하지 않는 파일 비용 절감
→ Lifecycle policy로 IA / Archive 이동
```

## EFS Access Point

EFS Access Point는 애플리케이션별로 EFS 접근 경로와 POSIX 사용자 정보를 고정하는 기능이다.

할 수 있는 것:

- 특정 root directory로 제한
- POSIX UID/GID 강제
- 애플리케이션별 접근 지점 제공
- IAM으로 access point 사용 권한 제어

예:

```text
App A
→ Access Point /config
→ UID 1001, GID 1001

Analytics App
→ Access Point /data
→ UID 1002, GID 1002
```

시험 감각:

```text
같은 EFS 안에서 앱별로 디렉터리/UID/GID를 분리하고 싶다
→ EFS Access Point
```

## EFS File System Policy

EFS에는 S3 bucket policy와 비슷한 resource-based policy를 붙일 수 있다.

주요 용도:

- 특정 IAM principal만 mount/write 허용
- 특정 access point를 통해서만 접근 허용
- 전송 중 암호화 강제

예시 감각:

```text
aws:SecureTransport = true
→ 암호화된 연결만 허용
```

Security Group은 네트워크 접근 제어이고, EFS file system policy는 IAM 기반 리소스 접근 제어다.

```text
NFS 포트 접근 제어
→ Security Group

누가 어떤 EFS/API/access point를 쓸 수 있는지
→ IAM + EFS file system policy
```

## EFS 암호화

EFS는 암호화를 지원한다.

- 저장 중 암호화: KMS 사용.
- 전송 중 암호화: TLS 사용.
- file system policy에서 `aws:SecureTransport` 조건으로 강제 가능.

시험 감각:

```text
EFS at-rest encryption
→ KMS

EFS in-transit encryption 강제
→ file system policy + aws:SecureTransport
```

## EFS Cross-Region Replication

EFS는 다른 리전으로 복제할 수 있다.

- 새 파일 시스템과 기존 파일 시스템 모두 가능.
- 대상 리전에 읽기 전용 복제본 파일 시스템을 만든다.
- RPO/RTO를 분 단위로 줄이는 DR 용도에 적합하다.
- 복제는 백엔드에서 처리되며 source 파일 시스템의 provisioned throughput을 직접 소비하지 않는다.

시험 감각:

```text
EFS를 다른 리전에 복제해 DR/컴플라이언스 대응
→ EFS Cross-Region Replication
```

# 헷갈린 질문 보강

## NFS가 뭐냐

NFS는 Network File System이다.
네트워크를 통해 다른 서버의 파일 시스템을 내 서버의 디렉터리처럼 마운트해서 쓰는 프로토콜이다.

```text
EC2 A
EC2 B
EC2 C
→ 같은 EFS 파일 시스템을 NFS로 마운트
→ 같은 디렉터리와 파일을 공유
```

AWS에서는 EFS가 관리형 NFS 파일 시스템이다.

```text
여러 Linux 서버가 같은 파일 시스템을 네트워크로 공유
→ NFS

AWS 관리형 NFS
→ EFS
```

S3는 NFS가 아니다.
S3는 파일 시스템처럼 마운트해서 쓰는 서비스가 아니라, API로 객체를 `PUT/GET`하는 객체 스토리지다.

## EFS Bursting, Provisioned, Elastic 쉽게 보기

EFS 처리량 모드는 "저장 용량과 속도가 묶여 있느냐"를 보면 된다.

```text
Bursting
= 저장된 데이터가 많을수록 기본 처리량도 커짐
= 작은 파일 시스템은 기본 처리량이 작고, 필요할 때 burst credit으로 잠깐 더 빠르게 처리

Provisioned Throughput
= 저장 용량과 상관없이 원하는 처리량을 직접 설정
= 파일은 적은데 빠르게 읽고 써야 할 때

Elastic Throughput
= 워크로드에 맞춰 AWS가 처리량을 자동으로 올리고 내림
= 사용량 패턴을 예측하기 어려울 때
```

시험에서 숫자보다 중요한 선택 기준:

```text
파일 시스템 크기만큼 자연스럽게 처리량 증가
→ Bursting

작은 EFS인데 높은 처리량 필요
→ Provisioned Throughput

처리량 패턴 예측 어려움
→ Elastic Throughput
```

## 온프레미스에서 EFS 마운트하는 감각

EFS는 VPC 안에 mount target을 만들고, 이 mount target은 ENI와 private IP를 가진다.

AWS 안의 EC2는 보통 EFS DNS 이름으로 마운트한다.

```text
EC2
→ EFS DNS 이름
→ 같은 AZ의 mount target
→ EFS
```

온프레미스 서버는 AWS VPC 내부 DNS를 바로 쓰기 어려운 경우가 많다.
그래서 Direct Connect나 Site-to-Site VPN으로 VPC와 연결한 뒤, EFS mount target ENI의 private IPv4로 NFS 마운트한다.

```text
온프레미스 서버
→ Direct Connect 또는 VPN
→ EFS mount target ENI private IP
→ EFS
```

강의에서 "온프레미스에서 EBS 볼륨에 액세스"처럼 들리는 부분은 이 문맥에서는 EBS가 아니라 EFS로 보는 것이 맞다.
EBS는 EC2에 붙는 블록 볼륨이고, 온프레미스 서버가 NFS로 직접 마운트하는 서비스가 아니다.

# EFS 시험용 선택 기준

```text
여러 AZ의 여러 Linux EC2가 같은 파일을 공유
→ EFS

WordPress/CMS 업로드 파일을 여러 웹서버가 공유
→ EFS

Windows 파일 공유
→ FSx for Windows File Server

HPC 고성능 병렬 파일 시스템
→ FSx for Lustre

작은 파일 시스템인데 높은 처리량 필요
→ EFS Provisioned Throughput

워크로드 처리량 예측 어려움
→ EFS Elastic Throughput

레이턴시에 민감한 웹/CMS
→ EFS General Purpose

병렬성/처리량이 더 중요
→ EFS Max I/O

파일 접근 빈도 낮아 비용 절감 필요
→ EFS Lifecycle policy + IA/Archive

비용 절감 가능하지만 단일 AZ 감수
→ EFS One Zone

앱별 디렉터리/UID/GID 분리
→ EFS Access Point

EFS를 온프레미스에서 마운트
→ Direct Connect/VPN + mount target IP

EFS DR을 위해 다른 리전 복제
→ EFS Cross-Region Replication
```

# Amazon FSx

Amazon FSx는 AWS에서 서드파티/특수 목적 파일 시스템을 완전관리형으로 실행하는 서비스다.
RDS가 MySQL/PostgreSQL 같은 DB 엔진을 관리형으로 제공하는 것처럼, FSx는 Windows File Server, Lustre, NetApp ONTAP, OpenZFS 같은 파일 시스템 엔진을 관리형으로 제공한다.

시험에서 FSx는 "EFS보다 좋은 파일 시스템"이 아니라, **워크로드가 요구하는 파일 시스템 종류가 정해져 있을 때 고르는 서비스**로 봐야 한다.

```text
Linux 범용 NFS 공유
→ EFS

Windows SMB / Active Directory / NTFS
→ FSx for Windows File Server

HPC / ML / 빅데이터 / S3 연동 초고성능 파일 시스템
→ FSx for Lustre

기존 NetApp ONTAP/NAS 워크로드 이전
→ FSx for NetApp ONTAP

기존 ZFS 워크로드 이전, snapshot/clone/저지연
→ FSx for OpenZFS
```

## FSx for Windows File Server

완전관리형 Windows 파일 공유 서비스다.
Windows 환경에서 쓰던 공유 드라이브를 AWS로 가져오는 느낌이다.

핵심 키워드:

- SMB protocol
- Windows NTFS
- Microsoft Active Directory 통합
- ACL, user quota
- Multi-AZ 구성 가능
- 온프레미스에서 private connectivity로 접근 가능
- 매일 S3에 자동 백업
- Linux EC2에서도 마운트 가능

시험 감각:

```text
Windows 파일 공유
→ FSx for Windows File Server

SMB / NTFS / AD / ACL
→ FSx for Windows File Server

온프레미스 Windows File Server와 AWS 파일 서버를 묶고 싶음
→ DFS, Distributed File System
```

성능/스토리지 선택:

```text
짧은 지연 시간, DB/미디어 처리/데이터 분석
→ SSD

홈 디렉터리, CMS, 비용 민감
→ HDD
```

헷갈리는 포인트:

```text
EFS
= Linux/NFS/POSIX 공유 파일 시스템

FSx for Windows File Server
= Windows/SMB/NTFS/AD 공유 파일 시스템
```

## FSx for Lustre

Lustre는 Linux + cluster에서 온 이름이고, 대규모 병렬 컴퓨팅용 분산 파일 시스템이다.
FSx for Lustre는 HPC, ML, 빅데이터 같은 초고성능 파일 처리에 쓴다.

대표 키워드:

- HPC
- Machine Learning
- 빅데이터
- 영상 처리
- 재무 모델링
- 전자 설계 자동화, EDA
- 수백 GB/s 처리량
- 수백만 IOPS
- sub-millisecond latency

시험 감각:

```text
HPC/ML/빅데이터에서 많은 EC2가 파일을 초고속 병렬 처리
→ FSx for Lustre
```

### FSx for Lustre와 S3 연동

FSx for Lustre는 S3와 연동할 수 있다.
S3에 있는 데이터를 Lustre 파일 시스템처럼 빠르게 읽고, 계산 결과를 다시 S3에 쓸 수 있다.

```text
S3 원본 데이터
→ FSx for Lustre로 고성능 파일 처리
→ EC2/HPC 클러스터가 병렬 계산
→ 결과를 다시 S3에 저장
```

시험에서 `S3 data lake`와 `HPC 고성능 파일 시스템`이 같이 나오면 FSx for Lustre를 떠올린다.

### FSx for Lustre 스토리지 옵션

```text
SSD
= 낮은 지연 시간
= IOPS 집약적
= 작고 랜덤한 파일 작업

HDD
= 처리량 집약적
= 대규모 순차 파일 작업
= 더 저렴
```

### Scratch vs Persistent

FSx for Lustre 배포 옵션은 scratch와 persistent가 중요하다.

| 구분 | Scratch | Persistent |
| --- | --- | --- |
| 목적 | 임시 고성능 작업 공간 | 장기 사용 파일 시스템 |
| 데이터 복제 | 없음 | 같은 AZ 내 복제 |
| 장애 시 | 서버 장애 시 데이터 손실 가능 | 장애 시 몇 분 내 투명하게 대체 |
| 성능 | 더 높은 burst 성능 | 내구성/장기 처리 중심 |
| 비용 | 더 저렴한 편 | 더 비쌈 |
| 사용 사례 | 단기 처리, 재생성 가능한 데이터 | 장기 처리, 민감한 데이터 |

Scratch file system은 계산 중 잠깐 쓰는 초고속 임시 작업 공간이다.

```text
S3에 원본 데이터 저장
→ FSx for Lustre Scratch로 가져와 빠르게 계산
→ 결과를 S3에 저장
→ scratch 파일 시스템은 지워도 됨
```

시험 감각:

```text
재생성 가능한 데이터, 단기 처리, 비용 최적화
→ FSx for Lustre Scratch

장기 처리, 데이터 내구성 중요
→ FSx for Lustre Persistent
```

주의:

```text
FSx for Lustre Persistent는 같은 AZ 내에서 복제한다.
Multi-AZ 파일 시스템으로 외우면 안 된다.
```

## FSx for NetApp ONTAP

AWS에서 NetApp ONTAP 파일 시스템을 관리형으로 쓰는 서비스다.
기존 온프레미스 NetApp/NAS 워크로드를 AWS로 옮길 때 강한 힌트가 된다.

지원 프로토콜:

- NFS
- SMB
- iSCSI

호환 대상:

- Linux
- Windows
- macOS
- VMware Cloud on AWS
- WorkSpaces
- AppStream
- EC2
- ECS
- EKS

주요 기능:

- 자동 확장/축소
- snapshot
- replication
- compression
- deduplication
- point-in-time clone

시험 감각:

```text
기존 NetApp ONTAP/NAS를 AWS로 마이그레이션
→ FSx for NetApp ONTAP

NFS/SMB/iSCSI를 모두 원함
→ FSx for NetApp ONTAP

압축/중복 제거/복제/스냅샷/빠른 클론
→ FSx for NetApp ONTAP
```

Point-in-time clone은 새 워크로드 테스트나 스테이징 환경을 빠르게 만들 때 유용하다.

```text
운영 파일 시스템을 빠르게 클론
→ 스테이징/테스트 파일 시스템 생성
```

## FSx for OpenZFS

AWS에서 OpenZFS 파일 시스템을 관리형으로 쓰는 서비스다.
기존 ZFS 워크로드를 AWS로 옮길 때 선택한다.

특징:

- NFS 프로토콜 계열 지원
- Linux, macOS, Windows 클라이언트 호환
- 낮은 지연 시간
- 높은 IOPS
- snapshot
- compression
- point-in-time clone
- deduplication은 지원하지 않음

시험 감각:

```text
기존 ZFS 워크로드를 AWS로 이전
→ FSx for OpenZFS

낮은 지연 시간 + snapshot/clone
→ FSx for OpenZFS

NetApp처럼 deduplication 필요
→ FSx for NetApp ONTAP
```

## FSx 선택 기준

```text
Windows 파일 공유, SMB, NTFS, AD 통합
→ FSx for Windows File Server

HPC/ML/빅데이터, S3 연동, 초고성능 병렬 파일 처리
→ FSx for Lustre

단기 HPC scratch space
→ FSx for Lustre Scratch

장기 Lustre 파일 시스템
→ FSx for Lustre Persistent

기존 NetApp ONTAP/NAS 마이그레이션
→ FSx for NetApp ONTAP

NFS + SMB + iSCSI 모두 필요
→ FSx for NetApp ONTAP

기존 ZFS 워크로드 마이그레이션
→ FSx for OpenZFS

Linux 범용 공유 파일 시스템
→ EFS
```

# S3 시험 포인트

S3는 서버리스 객체 스토리지다.
SAP에서는 "S3가 좋다"보다 "언제 S3가 틀린 선택인가"와 "성능/복제/이벤트 옵션을 언제 고르는가"가 중요하다.

## S3 안티패턴

S3는 파일 시스템이 아니다.
객체를 key로 저장하고 `PUT/GET` API로 접근한다.

S3가 어울리지 않는 경우:

- POSIX 파일 시스템이 필요함.
- 파일 lock이 필요함.
- EC2에 일반 디스크처럼 마운트해야 함.
- 작은 파일이 너무 많고 파일 시스템 작업이 잦음.
- 빠르게 변하는 데이터.
- 검색/쿼리/인덱싱이 본질적으로 필요한 데이터.
- 동적 웹 애플리케이션의 파일 시스템 대체.

시험 감각:

```text
객체 저장소, 정적 콘텐츠, 대량 파일 저장
→ S3

여러 Linux 서버가 파일 시스템처럼 공유
→ EFS

POSIX / file lock / chmod / chown
→ EFS 또는 FSx

검색/쿼리/인덱싱
→ DynamoDB, OpenSearch, Athena, RDS 등 다른 서비스 고려
```

## S3 Storage Class와 Lifecycle

스토리지 클래스 이름을 전부 깊게 외우기보다, 접근 빈도와 복구 시간 기준으로 고른다.

| 클래스 | 선택 감각 |
| --- | --- |
| Standard | 자주 접근, 기본 |
| Intelligent-Tiering | 접근 패턴을 모를 때 자동 티어링 |
| Standard-IA | 드물게 접근하지만 필요하면 빠르게 접근 |
| One Zone-IA | 단일 AZ 감수하고 비용 절감 |
| Glacier Instant Retrieval | 아카이브지만 즉시 검색 필요 |
| Glacier Flexible Retrieval | 몇 분~몇 시간 검색 허용 |
| Glacier Deep Archive | 가장 저렴한 장기 보관, 검색 느림 |

Lifecycle policy로 객체를 다른 storage class로 이동하거나 삭제할 수 있다.

시험 감각:

```text
접근 패턴 모름
→ Intelligent-Tiering

오래된 객체를 자동으로 저렴한 티어로 이동
→ Lifecycle policy

장기 보관 + 거의 접근 안 함
→ Glacier Deep Archive
```

S3 Analytics는 객체 접근 패턴을 분석해서 Standard-IA 등으로 옮길 lifecycle 정책을 잡는 데 도움을 주는 기능 정도로만 기억한다.

## S3 Storage Lens 무료 vs 유료

S3 Storage Lens는 S3 사용량과 활동을 조직/계정/리전/버킷/prefix 관점으로 보는 분석 대시보드다.
S3 Analytics가 "특정 객체를 IA로 옮길지"에 더 가깝다면, Storage Lens는 "전체 S3 사용 상태와 비용/보안/성능 best practice를 보는 관측 도구"에 가깝다.

시험에서 기억할 기본 감각:

- 기본 대시보드도 여러 계정과 여러 리전에 걸친 S3 사용량을 보여줄 수 있다.
- Storage Lens는 객체 스토리지인 S3를 대상으로 한다.
- 객체 수, 스토리지 사용량, prefix 증가 추세 같은 사용량 지표를 볼 수 있다.
- 암호화된 객체 비율, versioning/replication/lifecycle 적용 여부 같은 보안/보호 상태도 확인할 수 있다.
- 예: "얼마나 많은 객체가 암호화되어 있는가?" 같은 질문은 Storage Lens 지표로 볼 수 있다.

| 구분 | Free metrics | Advanced metrics, 유료 |
| --- | --- | --- |
| 목적 | 전체 S3 사용량/비용/보안 상태 기본 가시성 | 더 세밀한 분석과 운영 모니터링 |
| 지표 | summary, cost optimization, data protection, access management, performance, event metrics | 추가 cost optimization/data protection, activity metrics, detailed status-code metrics |
| Prefix 분석 | 기본 report에서 주요 prefix 중심 | prefix-level aggregation, expanded prefixes metrics report |
| 추천 | 기본적인 cost/data protection recommendation | contextual recommendations 제공 |
| CloudWatch | 없음 | CloudWatch publishing 가능 |
| 조회 가능 기간 | 14일 | 15개월 |
| 시험 감각 | "대략적인 S3 현황과 비용 최적화 확인" | "prefix/activity/status code까지 보고 CloudWatch 알람/운영 분석" |

시험용 한 줄:

```text
S3 Storage Lens Free
= S3 전체 사용량/비용/보안 상태 기본 대시보드

S3 Storage Lens Advanced
= prefix/activity/status-code까지 자세히 보고 CloudWatch로 publish하는 유료 분석
```

## S3 Replication

S3 replication을 쓰려면 source/target bucket 모두 versioning이 필요하다.

| 복제 | 의미 | 사용 사례 |
| --- | --- | --- |
| CRR | Cross-Region Replication | DR, compliance, latency 개선 |
| SRR | Same-Region Replication | 같은 리전 내 계정 분리, 로그 집계, 데이터 복사 |

주의:

- Replication은 기존 객체가 아니라 새로 들어오는 객체 중심으로 동작한다.
- 대상 bucket의 storage class/lifecycle은 대상 bucket에서 별도로 관리한다.
- Source bucket lifecycle이 target bucket lifecycle까지 자동으로 대신 정리해주는 느낌으로 외우면 안 된다.

## S3 RTC, Replication Time Control

S3 RTC는 복제 시간을 예측 가능하게 만들고 싶을 때 사용한다.

핵심:

```text
대부분의 객체는 몇 초 내 복제
99.99% 객체를 15분 내 복제하도록 SLA 제공
15분 임계값 초과 시 CloudWatch metric/alarm으로 감시 가능
```

시험 감각:

```text
컴플라이언스/DR 때문에 15분 내 복제를 보장해야 함
→ S3 RTC
```

## S3 Event Notification

S3 bucket 이벤트에 반응해서 다른 서비스를 트리거한다.

대표 이벤트:

- `S3:ObjectCreated`
- `S3:ObjectRemoved`
- `S3:ObjectRestore`
- `S3:Replication`

기본 대상:

- SNS
- SQS
- Lambda

시험 감각:

```text
이미지 업로드 시 썸네일 생성
→ S3 Event Notification → Lambda

객체 생성/삭제 이벤트를 큐에 넣어 처리
→ S3 Event Notification → SQS
```

일반 Event Notification은 보통 수 초 내 전달되지만 1분 이상 걸릴 수 있다.

## S3 EventBridge 연동

S3 이벤트를 EventBridge로 보내면 더 복잡한 라우팅과 필터링이 가능하다.

EventBridge를 쓰면 좋은 경우:

- JSON rule 기반 고급 필터링 필요.
- 객체 크기, metadata, event detail 기반 필터링 필요.
- 하나의 이벤트를 여러 서비스로 보내야 함.
- Step Functions, Kinesis Data Streams, Firehose 등 다양한 대상으로 연결.
- 이벤트 archive/replay가 필요.

시험 감각:

```text
S3 이벤트를 단순히 Lambda/SQS/SNS로 보냄
→ S3 Event Notification

S3 이벤트를 복잡하게 필터링하거나 여러 AWS 서비스로 라우팅
→ EventBridge
```

## S3 성능과 Prefix

S3는 자동으로 높은 요청률까지 확장된다.
성능 문제에서 prefix가 나오면 "접두사별 요청률"을 떠올린다.

객체 key:

```text
bucket/folder1/sub1/file.jpg
```

prefix:

```text
/folder1/sub1/
```

시험 감각:

```text
S3 요청률을 더 높이고 싶다
→ 여러 prefix로 key를 분산
```

숫자는 깊게 외우기보다 "prefix를 늘리면 병렬 요청 처리량을 키울 수 있다"는 감각이 중요하다.

## Multipart Upload

큰 객체를 여러 part로 나눠 병렬 업로드하는 방식이다.

- 100MB 이상이면 권장.
- 5GB 이상이면 필수.
- 업로드 실패 시 전체 파일이 아니라 실패한 part만 재시도 가능.
- 대역폭을 더 잘 써서 업로드 속도를 높인다.

시험 감각:

```text
큰 파일 업로드 성능 개선
→ Multipart Upload
```

불완전한 multipart upload가 남으면 비용이 낭비된다.
Lifecycle policy로 일정 기간 지난 incomplete multipart upload를 정리할 수 있다.

```text
중단된 multipart upload part 정리
→ Lifecycle rule: abort incomplete multipart upload
```

## S3 Transfer Acceleration

Transfer Acceleration은 클라이언트가 가까운 AWS edge location으로 업로드하고,
이후 AWS backbone network로 대상 리전 S3 bucket까지 전송하는 방식이다.

```text
Client
→ 가까운 Edge location
→ AWS private network
→ 먼 리전의 S3 bucket
```

시험 감각:

```text
멀리 떨어진 사용자들이 S3로 빠르게 업로드
→ S3 Transfer Acceleration

큰 파일 업로드 + 전송 가속
→ Multipart Upload + Transfer Acceleration 같이 사용 가능
```

## Byte-Range Fetch

S3 Byte-Range Fetch는 객체의 특정 바이트 범위만 가져오는 방식이다.

사용 사례:

- 큰 파일 다운로드를 여러 range로 나눠 병렬화.
- 실패한 range만 재시도.
- 파일 전체가 아니라 header 같은 일부 데이터만 읽기.

시험 감각:

```text
큰 파일 다운로드 성능 개선
→ Byte-Range Fetch로 병렬 GET

파일 일부만 필요
→ Byte-Range Fetch
```

## S3 Select / Glacier Select

S3 Select는 객체 전체를 다운로드하지 않고 S3 쪽에서 SQL 비슷한 조건으로 필요한 행/열만 필터링해 가져온다.

장점:

- 네트워크 전송량 감소.
- 클라이언트 CPU 사용 감소.
- 비용 절감.
- CSV/JSON/Parquet 같은 파일에서 일부 row/column만 필요할 때 유용.

시험 감각:

```text
S3 객체 전체 다운로드 후 클라이언트 필터링
→ 비효율

S3 객체에서 필요한 행/열만 서버 측 필터링
→ S3 Select

Glacier 아카이브 객체에서 필요한 일부 데이터만 필터링
→ Glacier Select
```

# S3 시험용 선택 기준

```text
정적 콘텐츠/객체 저장/무제한 서버리스 스토리지
→ S3

파일 시스템처럼 마운트, POSIX, file lock 필요
→ EFS/FSx

접근 패턴 모름
→ S3 Intelligent-Tiering

오래된 객체 비용 최적화
→ Lifecycle policy

리전 간 복제
→ CRR

같은 리전 내 복제
→ SRR

15분 내 복제 SLA 필요
→ S3 RTC

객체 이벤트로 Lambda/SQS/SNS 트리거
→ S3 Event Notification

S3 이벤트 고급 필터링/여러 대상/archive/replay
→ EventBridge

큰 파일 업로드
→ Multipart Upload

멀리서 S3 업로드 가속
→ Transfer Acceleration

큰 파일 다운로드 병렬화 또는 일부만 읽기
→ Byte-Range Fetch

객체 안 일부 row/column만 가져오기
→ S3 Select / Glacier Select
```

# AWS DataSync

DataSync는 대규모 데이터를 온프레미스, 다른 클라우드, AWS 스토리지 서비스 사이에서 옮기고 동기화하는 서비스다.
시험에서는 "무엇이든 실시간 복제"가 아니라 **예약 기반 데이터 이동 서비스**로 기억해야 한다.

## DataSync가 이동할 수 있는 대상

소스/대상으로 자주 나오는 것:

- 온프레미스 NFS
- 온프레미스 SMB
- HDFS
- 다른 클라우드 스토리지
- Amazon S3
- Amazon EFS
- Amazon FSx

S3로 보낼 때는 Standard뿐 아니라 Glacier 계열을 포함한 storage class도 대상으로 쓸 수 있다.

## Agent 필요 여부

DataSync는 위치에 따라 agent 필요 여부가 다르다.

| 이동 경로 | Agent 필요 여부 |
| --- | --- |
| 온프레미스 NFS/SMB/HDFS -> AWS | 필요 |
| 다른 클라우드 -> AWS | 필요 |
| AWS storage service -> AWS storage service | 불필요 |

시험 감각:

```text
온프레미스 파일 서버에서 S3/EFS/FSx로 동기화
→ DataSync agent 필요

S3 ↔ EFS ↔ FSx 같은 AWS 서비스 간 동기화
→ DataSync agent 필요 없음
```

## 지속 복제가 아니라 예약 태스크

DataSync는 파일 시스템 변경을 실시간으로 계속 복제하는 서비스가 아니다.
태스크를 만들고, 수동 실행하거나 일정에 따라 반복 실행한다.

예:

```text
매시간
매일
매주
```

따라서 약간의 지연이 있어도 되는 데이터 이동/동기화에 적합하다.

시험 감각:

```text
지속적 실시간 복제
→ DataSync 아님

예약 기반 대규모 데이터 동기화
→ DataSync
```

## 메타데이터와 권한 보존

DataSync의 중요한 시험 포인트는 파일 메타데이터와 권한을 보존할 수 있다는 점이다.

보존 가능한 것:

- 파일 권한
- 파일 소유권
- timestamp
- POSIX metadata
- SMB ACL

시험 감각:

```text
NFS POSIX 권한이나 SMB 권한을 유지하면서 AWS로 마이그레이션
→ DataSync
```

단순히 파일만 복사하는 도구가 아니라, 파일 시스템 의미를 최대한 유지하며 옮기는 서비스로 봐야 한다.

## 성능과 대역폭 제어

DataSync는 대량 데이터 전송에 맞춰 설계되어 있다.

- 하나의 task가 높은 처리량으로 데이터를 이동할 수 있다.
- 네트워크를 다 쓰면 곤란한 경우 bandwidth limit을 설정할 수 있다.
- 전송은 암호화된다.

시험 감각:

```text
대규모 파일 전송 + 네트워크 대역폭 제한 필요
→ DataSync bandwidth limit
```

## 방향성

DataSync는 한 방향만 고정된 서비스가 아니다.

```text
온프레미스 -> AWS
AWS -> 온프레미스
다른 클라우드 -> AWS
AWS storage -> AWS storage
```

다만 task 자체는 설정한 방향으로 실행된다.

## 네트워크가 부족하면 Snowcone

온프레미스에서 AWS로 DataSync를 쓰고 싶은데 네트워크 용량이 부족하면 Snowcone이 시험 포인트다.
Snowcone에는 DataSync agent가 미리 설치되어 있다.

감각:

```text
온프레미스 데이터
→ Snowcone에 수집
→ Snowcone의 DataSync agent 사용
→ AWS로 전송
→ S3/EFS/FSx에 동기화
```

시험 감각:

```text
DataSync를 쓰고 싶은데 네트워크 대역폭이 부족
→ AWS Snowcone with DataSync agent
```

## DataSync vs 다른 선택지

```text
온프레미스 NFS/SMB를 S3/EFS/FSx로 반복 동기화
→ DataSync

페타바이트급 오프라인 이전
→ Snowball/Snowmobile

S3 bucket 간 복제
→ S3 Replication

DB 마이그레이션
→ AWS DMS

OS/서버 자체 마이그레이션
→ AWS Application Migration Service
```

## DataSync 시험용 한 줄 정리

```text
대규모 파일/객체 데이터를 AWS로 동기화
→ DataSync

온프레미스/타 클라우드 소스
→ DataSync agent 필요

AWS 서비스 간 S3/EFS/FSx 동기화
→ agent 불필요

실시간 지속 복제 아님
→ 예약 태스크, hourly/daily/weekly

파일 권한/metadata 보존
→ DataSync 핵심 포인트

네트워크 부족한 온프레미스
→ Snowcone + DataSync agent
```

# AWS Transfer Family

AWS Transfer Family는 S3나 EFS를 백엔드 저장소로 두고, FTP 계열 프로토콜로 파일을 업로드/다운로드하게 해주는 완전관리형 서비스다.

핵심 감각:

```text
S3 API나 EFS/NFS를 직접 쓰기 어려운 외부 사용자/레거시 시스템
→ FTP/SFTP/FTPS 인터페이스 제공
→ 내부적으로 S3 또는 EFS에 저장
```

## 지원 프로토콜

| 프로토콜 | 의미 | 암호화 |
| --- | --- | --- |
| FTP | 전통적인 File Transfer Protocol | 전송 중 암호화 없음 |
| FTPS | FTP + TLS/SSL | 전송 중 암호화 |
| SFTP | SSH File Transfer Protocol | 전송 중 암호화 |

시험 감각:

```text
FTP
= 암호화 없음

FTPS / SFTP
= 전송 중 암호화

SFTP는 FTP의 보안 버전이 아니라 SSH 기반 별도 프로토콜
```

## 백엔드와 권한

Transfer Family는 사용자가 FTP/SFTP/FTPS로 접속하게 하고, 실제 파일은 S3나 EFS에 저장한다.

```text
User
→ Transfer Family endpoint
→ IAM role
→ S3 bucket 또는 EFS file system
```

시험 감각:

```text
외부 파트너가 SFTP로 파일 업로드
→ Transfer Family + S3

FTP 인터페이스로 EFS 파일 시스템 접근
→ Transfer Family + EFS
```

Transfer Family는 S3/EFS 접근을 위해 IAM role을 사용한다.
사용자별 홈 디렉터리나 prefix 제한 같은 패턴도 자주 나온다.

## 인증 연동

Transfer Family는 사용자 인증을 직접 관리하거나 기존 인증 시스템과 연동할 수 있다.

연동 예:

- Microsoft Active Directory
- LDAP
- Okta
- Amazon Cognito
- custom identity provider

시험 감각:

```text
기존 기업 사용자 인증 시스템으로 SFTP 로그인
→ Transfer Family identity provider 연동
```

## 요금 감각

세부 숫자보다 과금 축만 기억한다.

```text
프로비저닝된 endpoint 시간
+ 전송된 데이터 GB
```

## Endpoint 유형

Transfer Family는 endpoint 유형별 네트워크 보안 특성이 중요하다.

| 유형 | 접근 | IP/보안 감각 |
| --- | --- | --- |
| Public endpoint | 인터넷에서 접근 | public DNS 사용 권장, AWS 관리 public IP, IP가 바뀔 수 있음 |
| VPC endpoint, internal | VPC 내부/온프레미스에서 private 접근 | private IP, Security Group/NACL 사용 가능 |
| VPC endpoint, internet-facing | VPC 기반이지만 인터넷 접근 가능 | Elastic IP 연결 가능, SG/NACL로 접근 제한 가능 |

## Public Endpoint

Public endpoint는 인터넷에서 바로 접근할 수 있다.

주의:

- public IP는 AWS가 관리한다.
- 시간이 지나며 IP가 바뀔 수 있다.
- 그래서 public DNS 이름 사용이 권장된다.
- 특정 source IP만 네트워크 레벨에서 허용하는 구성에는 한계가 있다.

시험 감각:

```text
간단히 인터넷에서 SFTP/FTPS/FTP 접근
→ Public endpoint

고정 public IP allowlist 필요
→ Public endpoint는 부적합
```

## VPC Endpoint, Internal

VPC 내부에서만 접근하는 private endpoint다.

접근 경로:

```text
EC2 in VPC
→ Transfer Family VPC endpoint

온프레미스
→ VPN / Direct Connect
→ Transfer Family VPC endpoint
```

특징:

- private IP 사용.
- Security Group 사용 가능.
- Network ACL 사용 가능.
- 온프레미스에서 private하게 접근 가능.

시험 감각:

```text
내부 시스템이나 온프레미스에서만 SFTP 접근
→ VPC endpoint internal

VPN/DX를 통해 private하게 접근
→ VPC endpoint internal
```

## VPC Endpoint, Internet-facing

VPC 안에 endpoint를 만들지만 인터넷에서도 접근 가능하게 하는 하이브리드 형태다.

특징:

- Elastic IP를 붙일 수 있다.
- 고정 public IP를 직접 통제할 수 있다.
- Security Group으로 인터넷 사용자 접근 제한 가능.
- VPC 내부 EC2나 온프레미스도 private하게 접근 가능.

시험 감각:

```text
인터넷 사용자가 SFTP로 접근해야 함
+ 고정 public IP allowlist 필요
+ Security Group으로 접근 제한 필요
→ Internet-facing VPC endpoint + Elastic IP
```

## Transfer Family vs DataSync

```text
파트너/사용자가 FTP/SFTP/FTPS로 파일을 주고받아야 함
→ AWS Transfer Family

온프레미스 파일 서버와 AWS 스토리지를 대량 동기화
→ AWS DataSync

S3에 직접 제한된 시간 업로드/다운로드
→ Pre-signed URL
```

## Transfer Family 시험용 한 줄 정리

```text
SFTP/FTPS/FTP로 S3/EFS에 파일 전송
→ AWS Transfer Family

FTP
→ 암호화 없음

FTPS/SFTP
→ 전송 중 암호화

백엔드 저장소
→ S3 또는 EFS

S3/EFS 접근 권한
→ IAM role

기존 AD/LDAP/Okta/Cognito 인증 연동
→ Transfer Family identity provider

간단한 인터넷 접근
→ Public endpoint

private 접근, VPN/DX, SG/NACL
→ VPC endpoint internal

고정 public IP + 인터넷 접근 제한
→ Internet-facing VPC endpoint + Elastic IP
```

# S3 솔루션 아키텍처

S3 아키텍처 문제는 "정적 객체를 어떻게 제공할 것인가", "S3에 검색 기능을 어떻게 붙일 것인가", "정적/동적 콘텐츠를 어떻게 분리할 것인가"로 자주 나온다.

## 정적 객체 제공 방식

정적 파일을 사용자에게 제공하는 방법은 여러 가지가 있지만, 확장성과 가용성 관점에서 선호도가 다르다.

| 아키텍처 | 장점 | 한계 | 시험 감각 |
| --- | --- | --- | --- |
| EC2 + EBS/Instance Store | 단순함 | 확장성/가용성 낮음 | 가능은 하지만 좋은 선택 아님 |
| CloudFront + EC2 + EBS | 엣지 캐싱 가능 | 원본 EC2 장애 시 캐시 miss면 실패 | 단일 EC2 원본은 여전히 약함 |
| CloudFront + ALB + ASG + EFS | EC2 확장성 + 공유 파일 가능 | EFS 비용, 운영 복잡도 | 앱 서버가 파일 시스템을 공유해야 할 때 |
| CloudFront + S3 | 서버리스, 확장성 좋음, 정적 객체 제공에 적합 | 자주 바뀌는 동적 콘텐츠에는 부적합 | 정적 콘텐츠 제공의 선호 패턴 |

시험 선택 기준:

```text
자주 업데이트되지 않는 큰 정적 객체를 글로벌 사용자에게 제공
→ CloudFront + S3

EC2 여러 대가 같은 파일 시스템을 공유해야 함
→ ALB + ASG + EFS

CloudFront 앞에 단일 EC2
→ 캐시는 도움 되지만 원본 장애에 취약
```

## S3 검색/인덱싱 패턴

S3는 객체 스토리지이고, 버킷 안 객체를 DB처럼 검색/쿼리하는 인덱싱 기능이 없다.

검색이 필요하면 객체 메타데이터를 별도 저장소에 인덱싱한다.

대표 패턴:

```text
S3에 객체 업로드
→ S3 Event Notification
→ Lambda 실행
→ 객체 일부 또는 metadata 읽기
→ DynamoDB에 metadata 저장
→ API가 DynamoDB를 검색
→ 필요한 S3 객체 key 반환
```

Lambda가 파일 전체를 읽을 필요가 없으면 Byte-Range Fetch로 일부만 읽을 수 있다.

검색 예:

- 날짜별 객체 검색
- 특정 고객이 사용한 총 스토리지 계산
- 특정 속성을 가진 객체 찾기
- 특정 기간에 업로드된 객체 찾기

시험 감각:

```text
S3 안의 객체를 조건으로 검색해야 함
→ S3 자체 검색이 아니라 DynamoDB/OpenSearch/Athena 등으로 인덱싱

객체 업로드 시 metadata 자동 인덱싱
→ S3 Event Notification + Lambda + DynamoDB
```

## 동적 콘텐츠와 정적 콘텐츠 분리

정적 콘텐츠와 동적 콘텐츠를 분리하는 것은 모범 사례다.

정적 콘텐츠:

```text
HTML, 이미지, 영상, 대용량 파일, 자주 안 바뀌는 파일
→ S3
→ CloudFront 캐싱
```

동적 콘텐츠:

```text
REST API, 최신 데이터, 사용자별 응답, 세션성 데이터
→ ALB + EC2/ECS
→ API Gateway + Lambda
→ 데이터 계층 DynamoDB/RDS/ElastiCache 등
```

둘은 이벤트로 연결될 수 있다.

```text
사용자가 동적 API를 통해 파일 업로드 요청
→ S3에 파일 저장
→ S3 Event Notification
→ Lambda
→ DynamoDB에 metadata/index 저장
→ 동적 API에서 검색 가능
```

시험 감각:

```text
정적 콘텐츠
→ S3 + CloudFront

동적 콘텐츠
→ API Gateway/Lambda 또는 ALB/EC2/ECS

정적 파일 업로드 후 검색 가능하게 만들기
→ S3 event + Lambda + DynamoDB index
```

## CloudFront를 반드시 거치게 할지, S3에 직접 접근시킬지

CloudFront + S3를 쓴다고 해서 항상 사용자가 CloudFront만 통해야 하는 것은 아니다.

| 방식 | 의미 | 사용 감각 |
| --- | --- | --- |
| CloudFront + OAI/OAC | S3 bucket을 직접 공개하지 않고 CloudFront만 접근 허용 | 정적 콘텐츠 배포 보안 강화 |
| S3 pre-signed URL | 제한된 시간 동안 S3 객체에 직접 업로드/다운로드 허용 | 앱 서버를 거치지 않는 효율적 전송 |

시험 감각:

```text
사용자가 S3를 직접 못 보고 CloudFront로만 접근
→ CloudFront OAI/OAC + S3 bucket policy

사용자에게 일정 시간만 S3 직접 업로드/다운로드 허용
→ S3 pre-signed URL

대용량 파일을 앱 서버 프록시 없이 직접 업로드
→ pre-signed URL
```

## S3 아키텍처 시험용 한 줄 정리

```text
정적 웹/대용량 정적 객체 글로벌 배포
→ CloudFront + S3

앱 서버들이 같은 업로드 파일을 공유
→ ALB + ASG + EFS

S3 객체 검색 기능 필요
→ S3 event + Lambda + DynamoDB metadata index

동적/정적 콘텐츠 분리
→ 동적은 API/ALB 계층, 정적은 S3/CloudFront

S3 직접 접근 차단하고 CloudFront만 허용
→ OAI/OAC

S3 직접 업로드/다운로드를 안전하게 허용
→ pre-signed URL
```
