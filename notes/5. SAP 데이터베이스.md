# SAP 데이터베이스

# DynamoDB

DynamoDB는 완전관리형, 서버리스 NoSQL key-value/document 데이터베이스다.
시험에서는 세부 API보다 "어떤 조회 패턴에 맞는가", "인덱스가 필요한가", "Global Tables/DAX/Streams를 언제 쓰는가"가 중요하다.

```text
대규모 트래픽
서버리스 NoSQL
고정 스키마가 필요 없는 JSON성 데이터
ms 단위 응답
키 기반 조회
→ DynamoDB
```

## DynamoDB 핵심 감각

- 서버리스, 완전관리형 NoSQL.
- 테이블 용량은 자동 확장 가능.
- item 최대 크기는 400KB.
- 큰 객체는 DynamoDB에 직접 넣지 말고 S3에 저장하고 DynamoDB에는 S3 key/reference를 저장한다.
- CRUD 지원.
- eventually consistent read와 strongly consistent read 지원.
- 트랜잭션으로 ACID 처리 가능.
- PITR, backup 지원.
- 테이블 클래스는 Standard와 Standard-IA가 있다.

시험 감각:

```text
큰 파일/이미지/문서
→ S3 저장
→ DynamoDB에는 metadata/reference 저장

스키마 유연한 고속 key-value 조회
→ DynamoDB

SQL join/복잡한 ad-hoc query
→ DynamoDB보다 RDS/Aurora/OpenSearch/Athena 고려
```

## Capacity Mode

| 모드 | 감각 | 사용 상황 |
| --- | --- | --- |
| Provisioned | RCU/WCU를 정하고 Auto Scaling 가능 | 트래픽 패턴 예측 가능, 비용 최적화 |
| On-demand | 요청당 과금, 용량 계획 거의 없음 | 예측 불가 트래픽, 개발/초기 서비스, 급격한 변동 |

시험에서 "예측 불가능한 워크로드", "운영 부담 최소화"가 나오면 On-demand 쪽을 본다.
"트래픽 패턴이 알려져 있고 비용 최적화"라면 Provisioned + Auto Scaling이 자연스럽다.

## Partition Key와 Partition

DynamoDB의 파티션은 테이블 데이터를 나눠 담는 내부 저장 조각이다.
아이템이 어느 파티션에 들어갈지는 partition key 값의 해시로 결정된다.

```text
partition key
= 데이터를 어떤 내부 파티션에 분산할지 결정하는 값
```

좋은 partition key는 값이 다양하고 요청이 골고루 퍼져야 한다.

```text
좋음
→ userId, orderId, deviceId

나쁨
→ status, gender, region처럼 값 종류가 적은 키
```

특정 partition key에 읽기/쓰기가 몰리면 hot partition이 생기고, throttle이나 성능 병목이 날 수 있다.

시험 감각:

```text
파티션 키는 고르게 분산되어야 함
특정 키에 트래픽 집중
→ hot partition
→ DAX/cache, key 설계 변경, write sharding 고려
```

## Primary Key 설계

DynamoDB 기본 키는 테이블 생성 시 정한다.

| 기본 키 유형 | 구성 | 의미 |
| --- | --- | --- |
| Simple primary key | Partition key만 | partition key 값 하나가 item을 고유하게 식별 |
| Composite primary key | Partition key + Sort key | 두 값의 조합이 item을 고유하게 식별 |

예시:

```text
Users table
PK = userId

UserGame table
PK = userId
SK = gameId

UserActivity table
PK = userId
SK = timestamp
```

Sort key는 같은 partition key 안에서 범위 조회나 정렬 조건을 만들 때 중요하다.

```text
특정 사용자의 최근 활동 조회
→ PK = userId
→ SK = timestamp
```

## DynamoDB Query의 제약

DynamoDB는 RDB처럼 아무 컬럼에나 `WHERE`를 걸어 조회하는 DB가 아니다.
핵심은 기본 키나 인덱스로 설계된 접근 경로로만 효율적으로 Query할 수 있다는 점이다.

```text
Query
= partition key 값을 지정하고
= 필요하면 sort key 조건을 추가해서 조회
```

인덱스가 없는 속성으로는 Query를 시작할 수 없다.
가능한 것은 Scan + FilterExpression인데, 이것은 읽은 뒤 버리는 방식이라 큰 테이블에서 비싸고 느리다.

```text
Query
→ 기본 키 / LSI / GSI 기반 빠른 조회

Scan + Filter
→ 테이블이나 인덱스를 훑고 결과를 걸러냄
→ 큰 테이블에서는 피해야 함
```

시험 감각:

```text
자주 조회할 속성
→ 기본 키나 GSI/LSI로 모델링

인덱스 없는 속성 조건 조회
→ Query가 아니라 Scan
→ 비용/성능 문제
```

## LSI vs GSI

| 구분 | LSI | GSI |
| --- | --- | --- |
| 풀네임 | Local Secondary Index | Global Secondary Index |
| 파티션 키 | 원본 테이블과 같아야 함 | 원본 테이블과 달라도 됨 |
| 정렬 키 | 원본과 다른 sort key 사용 | partition key와 sort key를 새로 설계 가능 |
| 생성 시점 | 테이블 생성 시에만 가능 | 테이블 생성 후에도 추가 가능 |
| 일관성 | Strongly consistent read 가능 | Eventual consistency만 |
| 용도 | 같은 PK 안에서 다른 정렬/범위 조회 | 완전히 다른 조회 패턴 추가 |

한 줄 감각:

```text
LSI
= 같은 partition key, 다른 sort key

GSI
= 다른 partition key로 새로운 조회 패턴
```

예시:

```text
원본 테이블
PK = userId
SK = orderDate

LSI
PK = userId
SK = orderAmount
→ 같은 사용자의 주문을 금액순/금액 범위로 조회

GSI
PK = productId
SK = orderDate
→ 특정 상품의 주문을 날짜순으로 조회
```

시험 함정:

```text
테이블 생성 후 추가해야 함
→ GSI

Strongly consistent read 필요
→ LSI 가능, GSI 불가

원본과 다른 partition key로 조회
→ GSI
```

## TTL

TTL은 특정 시간이 지난 item을 자동 만료시키는 기능이다.

```text
session data
temporary token
cache item
일시적 이벤트 데이터
→ TTL
```

삭제는 정확히 그 시각에 즉시 일어나는 보장은 아니고, 백그라운드에서 비동기적으로 정리된다.

## DynamoDB Streams

DynamoDB Streams는 테이블 item 변경 이벤트를 순서대로 캡처한다.

```text
PutItem / UpdateItem / DeleteItem
→ DynamoDB Streams
→ Lambda / EC2 / downstream consumer
```

핵심:

- item-level 변경을 캡처한다.
- 보존 기간은 24시간.
- Lambda와 자주 연결한다.
- 변경 이벤트 기반 아키텍처에 자주 나온다.

사용 예:

```text
DynamoDB 변경
→ Stream
→ Lambda
→ OpenSearch 색인 업데이트

DynamoDB 변경
→ Stream
→ Lambda
→ downstream system 동기화
```

## Streams vs Kinesis Data Streams 연동

DynamoDB Streams는 24시간 보존이 한계다.
더 긴 보존, 분석 파이프라인, Kinesis 생태계 활용이 필요하면 Kinesis Data Streams로 보낼 수 있다.

```text
DynamoDB 변경
→ Kinesis Data Streams
→ Firehose
→ S3 / Redshift / OpenSearch

DynamoDB 변경
→ Kinesis Data Analytics
→ 실시간 집계/필터링/변환
```

시험 감각:

```text
짧은 변경 이벤트 처리
→ DynamoDB Streams

더 긴 보존, 스트리밍 분석, Firehose 연계
→ Kinesis Data Streams
```

## Global Tables

DynamoDB Global Tables는 멀티 리전 active-active 테이블이다.

```text
Region A read/write 가능
Region B read/write 가능
→ 서로 비동기 복제
```

사용 상황:

- 글로벌 사용자에게 낮은 지연 시간 제공.
- 멀티 리전 재해 복구.
- RTO를 낮추고 싶을 때.
- active-active write가 필요할 때.

중요한 점:

```text
Global Tables
= active-active
= 비동기 복제
= conflict resolution은 last writer wins
```

같은 item을 여러 리전에서 거의 동시에 쓰면 마지막 write가 이긴다.
둘 다 중요한 변경이면 하나가 덮일 수 있으므로 애플리케이션 설계가 필요하다.

충돌 줄이는 설계:

```text
사용자/데이터별 home region 지정
version + conditional write
idempotency key
상태 덮어쓰기보다 append-only event 모델
```

## DAX, DynamoDB Accelerator

DAX는 DynamoDB 전용 인메모리 캐시다.
애플리케이션이 DynamoDB API와 비슷한 방식으로 DAX endpoint를 사용하면, DAX가 read/query 결과를 캐싱한다.

```text
읽기 지연 시간 microsecond 수준
read-heavy workload
hot key 완화
→ DAX
```

특징:

- DynamoDB 전용 캐시.
- read/query/scan 결과 캐싱.
- 기본 TTL은 5분 감각.
- Multi-AZ 구성 가능.
- 프로덕션은 보통 3노드 이상 권장.
- KMS, VPC, IAM, CloudTrail 등 보안 통합.

## DAX vs ElastiCache

| 구분 | DAX | ElastiCache |
| --- | --- | --- |
| 목적 | DynamoDB read/query 캐시 | 범용 애플리케이션 캐시 |
| 캐싱 대상 | item, query/scan 결과 | 앱이 넣는 임의 결과 |
| 사용 감각 | DynamoDB 직접 읽기가 많고 hot key가 있음 | 무거운 계산 결과, 세션, 집계 결과 캐싱 |
| 앱 변경 | DynamoDB client를 DAX endpoint로 향하게 하는 감각 | 앱에서 cache-aside 로직을 직접 설계 |

시험 감각:

```text
DynamoDB 자체 read latency/hot key 완화
→ DAX

DynamoDB에서 읽은 뒤 계산한 결과를 재사용
→ ElastiCache
```

## S3 Metadata Index 패턴

S3는 객체 스토리지라 버킷 안 객체를 DB처럼 검색하는 인덱싱 기능이 없다.
객체 검색 API가 필요하면 DynamoDB에 metadata를 저장하는 패턴이 자주 나온다.

```text
S3 object upload
→ S3 Event Notification
→ Lambda
→ object metadata 추출
→ DynamoDB에 저장
→ API가 DynamoDB를 Query
```

가능해지는 것:

- 날짜별 객체 조회.
- 사용자별 저장 용량 계산.
- 특정 속성을 가진 객체 목록 조회.
- S3 객체에 대한 검색 API 제공.

시험 감각:

```text
S3 자체에서 객체 조건 검색
→ 불가에 가까움

S3 객체 metadata 검색
→ S3 event + Lambda + DynamoDB index
```

# Amazon OpenSearch

Amazon OpenSearch는 예전 Amazon Elasticsearch Service의 새 이름이다.
Elasticsearch가 라이선스를 바꾼 뒤 AWS가 오픈소스 fork로 제공하는 검색/분석 서비스라고 보면 된다.

```text
Elasticsearch
→ OpenSearch

Kibana
→ OpenSearch Dashboards
```

## OpenSearch 핵심 감각

OpenSearch는 원본 데이터베이스라기보다 "검색용 인덱스"에 가깝다.
DynamoDB, RDS, S3 같은 원본 저장소가 있고, 검색이 필요한 필드만 OpenSearch에 복사해서 색인한다.

```text
원본 데이터 저장
→ DynamoDB / RDS / S3

검색 잘 되게 색인
→ OpenSearch
```

왜 굳이 OpenSearch를 쓰는가?

```text
DynamoDB
= key/index 기반 조회에 강함
= 아무 필드나 contains, 전문 검색, 유사 검색은 부적합

OpenSearch
= full-text search
= 로그 분석
= 텍스트 검색
= 필터/집계/대시보드
= 클릭스트림/보안 분석
```

예를 들어 상품 테이블이 DynamoDB에 있다고 해도:

```text
상품명에 "wireless"가 들어간 상품
설명에 "noise cancelling"이 포함된 상품
로그 중 error가 포함된 이벤트
특정 시간대의 API 오류 집계
```

이런 검색은 DynamoDB의 키 기반 Query보다 OpenSearch 쪽이 자연스럽다.

## OpenSearch 아키텍처가 납득되는 흐름

핵심은 "쓰기 원본"과 "검색 인덱스"를 분리하는 것이다.

```text
사용자/애플리케이션
→ DynamoDB에 원본 item 저장
→ DynamoDB Streams에 변경 이벤트 발생
→ Lambda가 변경 내용을 읽음
→ OpenSearch index에 문서 추가/수정/삭제
→ 검색 API는 OpenSearch를 조회
```

즉 사용자가 검색할 때 DynamoDB를 Scan하는 것이 아니라, 미리 색인해둔 OpenSearch를 조회한다.

```text
쓰기 경로
App → DynamoDB

동기화 경로
DynamoDB Streams → Lambda → OpenSearch

검색 경로
App/Search API → OpenSearch
```

중요한 점:

```text
DynamoDB가 source of truth
OpenSearch는 검색용 복사본/index
```

그래서 OpenSearch의 데이터가 잠깐 늦게 반영될 수 있다.
DynamoDB Stream이나 Kinesis를 통해 비동기로 OpenSearch에 반영되기 때문이다.

## DynamoDB에서 OpenSearch로 보내는 방법

대표 패턴:

```text
DynamoDB
→ DynamoDB Streams
→ Lambda
→ OpenSearch
```

대량 스트리밍/분석 파이프라인 감각:

```text
DynamoDB
→ Kinesis Data Streams
→ Kinesis Data Firehose
→ OpenSearch
```

시험에서는 "DynamoDB 테이블에서 full-text search가 필요하다"거나 "검색 기능을 추가해야 한다"가 나오면 OpenSearch가 강한 후보가 된다.

## OpenSearch 사용 사례

- 로그 분석.
- 실시간 애플리케이션 모니터링.
- 보안 분석.
- full-text search.
- 클릭스트림 분석.
- 검색용 인덱싱.
- OpenSearch Dashboards로 시각화.

## OpenSearch 운영 모드

| 모드 | 감각 |
| --- | --- |
| Managed cluster | 인스턴스 타입/노드 수 등을 정해서 클러스터 운영 |
| Serverless | 클러스터 용량 관리를 줄이고 검색/분석 워크로드 실행 |

## OpenSearch vs DynamoDB

| 요구사항 | 선택 |
| --- | --- |
| PK/SK 기반 빠른 조회 | DynamoDB |
| 특정 속성으로 정해진 조회 패턴 | DynamoDB + GSI/LSI |
| 텍스트 검색, contains, 로그 검색 | OpenSearch |
| 검색 결과 랭킹/필터/집계 | OpenSearch |
| 원본 데이터의 강한 저장소 | DynamoDB/RDS/S3 |
| 검색용 복사본/인덱스 | OpenSearch |

시험 감각:

```text
DynamoDB에서 키 기반 Query로 해결 가능
→ DynamoDB/GSI

DynamoDB에 없는 "검색 엔진" 기능 필요
→ OpenSearch

S3/RDS/DynamoDB 데이터를 검색 가능하게 만들기
→ 변경 이벤트/Lambda/Kinesis로 OpenSearch에 색인
```

# RDS

RDS는 관계형 데이터베이스 엔진을 AWS가 관리형으로 운영해주는 서비스다.
서버리스라기보다는 DB 인스턴스 타입을 고르고, AWS가 백업/패치/모니터링 같은 운영 일부를 맡아주는 관리형 DB에 가깝다.

지원 엔진 감각:

```text
PostgreSQL
MySQL
MariaDB
Oracle
Microsoft SQL Server
Db2
```

## RDS 기본 배치

RDS는 보통 VPC의 private subnet에 둔다.
애플리케이션 서버나 Lambda는 RDS와 통신 가능한 네트워크 경로와 보안 그룹을 가져야 한다.

```text
App / Lambda
→ VPC 내부 경로
→ RDS private endpoint
```

Lambda가 private RDS에 접근하려면 Lambda에 VPC config를 설정한다.
정확히는 Lambda가 서버처럼 서브넷에 들어가는 것이 아니라, Lambda-managed ENI가 지정한 subnet/security group에 붙어서 RDS private IP로 통신한다.

```text
Lambda VPC config
→ subnet IDs
→ security group
→ Lambda ENI
→ RDS
```

보안 그룹 감각:

```text
RDS SG inbound
→ Lambda/App SG에서 오는 DB port 허용

Lambda/App SG outbound
→ RDS SG로 나가는 DB port 허용
```

## Storage, Backup, Snapshot

RDS 스토리지는 EBS 기반이다.
스토리지 자동 확장을 켜면 용량 부족 시 볼륨 크기를 자동으로 늘릴 수 있다.

백업 구분:

| 구분 | 감각 | 시험 포인트 |
| --- | --- | --- |
| Automated backup | 자동 백업, PITR 가능 | 보존 기간이 있고 만료됨 |
| Manual snapshot | 사용자가 직접 특정 시점 저장 | 사용자가 삭제할 때까지 유지 가능 |
| Snapshot copy | 다른 리전으로 복사 가능 | DR에 유용 |

```text
특정 시점 복구
→ automated backup / PITR

장기 보관 또는 리전 간 DR
→ manual snapshot copy
```

암호화되지 않은 RDS를 암호화하려면 보통 snapshot을 이용한다.

```text
Unencrypted RDS
→ snapshot 생성
→ snapshot copy 시 KMS 암호화
→ encrypted snapshot에서 새 RDS 복원
```

## RDS Event Notification

RDS는 DB 인스턴스 이벤트를 SNS로 보낼 수 있다.

```text
RDS event
→ SNS topic
→ 운영 알림
```

예:

- 장애.
- 백업 시작/완료.
- failover.
- 유지보수.
- 설정 변경.

주의:

```text
RDS Event Notification
= DB 운영 이벤트 알림

SQL 쿼리 추적
≠ RDS Event Notification
≠ CloudTrail
```

CloudTrail은 RDS API 호출은 추적하지만, DB 내부 SQL 쿼리 로그를 일반적으로 추적하는 용도가 아니다.

## Multi-AZ vs Read Replica

시험에서 가장 자주 헷갈리는 구분이다.

| 구분 | Multi-AZ | Read Replica |
| --- | --- | --- |
| 목적 | 고가용성 / 장애 조치 | 읽기 확장 / DR 보조 |
| 복제 | 동기식 | 비동기식 |
| 앱 접근 | 하나의 RDS endpoint만 사용 | replica endpoint로 읽기 가능 |
| standby 사용 | 앱이 직접 접근하지 않음 | 앱이 SELECT를 보낼 수 있음 |
| failover | 자동 failover | 승격은 별도 작업 필요 |
| cross-region | 일반 Multi-AZ는 같은 리전 | cross-region replica 가능 |

Multi-AZ:

```text
Primary RDS
→ 다른 AZ Standby에 synchronous replication
→ 장애 시 RDS가 자동 failover
→ endpoint는 유지
```

Read Replica:

```text
Primary RDS
→ Read Replica에 asynchronous replication
→ 앱은 읽기 요청을 replica로 보낼 수 있음
→ replication lag 가능
```

한 줄:

```text
장애 대비
→ Multi-AZ

읽기 부하 분산
→ Read Replica
```

## 읽기 전용 DB를 앱에서 쓰는 방식

Read Replica는 보통 애플리케이션이 읽기/쓰기 endpoint를 구분해서 사용한다.

```text
쓰기 요청
→ writer / primary endpoint

읽기 요청
→ read replica endpoint
```

Aurora는 writer endpoint와 reader endpoint를 제공한다.
일반 RDS read replica는 replica별 endpoint가 있고, 앱이나 Route 53 등을 통해 분산할 수 있다.

Spring/JDBC 감각:

```text
writerDataSource
readerDataSource
→ RoutingDataSource
→ readOnly transaction이면 reader
→ write transaction이면 writer
```

주의:

```text
쓰기 직후 최신값을 반드시 읽어야 함
→ writer에서 읽기

조금 늦어도 되는 목록/통계 조회
→ reader에서 읽기
```

## Route 53으로 Read Replica 분산

RDS Read Replica가 여러 개 있을 때 Route 53 weighted record로 읽기 endpoint들을 분산할 수 있다.

```text
read.example.com
→ replica-1 endpoint, weight 25
→ replica-2 endpoint, weight 25
→ replica-3 endpoint, weight 25
→ replica-4 endpoint, weight 25
```

Health check를 붙이면 문제가 있는 replica를 응답에서 제외할 수 있다.

시험 감각:

```text
여러 read replica에 읽기 트래픽 분산
→ Route 53 weighted record + health check
```

단, SQL을 보고 자동으로 읽기/쓰기를 나눠주는 마법 VIP로 이해하면 안 된다.
쓰기/읽기 분리는 앱, 드라이버, 프레임워크, 프록시 계층에서 설계해야 한다.

## RDS 보안

| 기능 | 감각 |
| --- | --- |
| KMS encryption | EBS volume과 snapshot 암호화 |
| SSL/TLS | 전송 중 암호화, 강제 가능 |
| TDE | Oracle / SQL Server의 DB 레벨 투명 데이터 암호화 |
| IAM DB Authentication | MySQL, PostgreSQL, MariaDB에서 지원 |

IAM DB Authentication:

```text
EC2/Lambda IAM role
→ RDS 인증 token 요청
→ token으로 DB 로그인
→ token lifetime 약 15분
```

중요한 점:

```text
IAM은 DB 로그인 인증을 도와줌
DB 안에서 어떤 테이블을 읽고 쓸 수 있는지는 DB 내부 권한으로 관리
```

## Oracle on RDS 시험 포인트

Oracle은 시험에서 1~2문제로 나올 수 있는 특수 포인트가 있다.

### RDS Backup vs RMAN

| 구분 | 의미 | 복원 대상 |
| --- | --- | --- |
| RDS automated backup / snapshot | RDS for Oracle 백업 | RDS for Oracle로 복원 |
| Oracle RMAN | Oracle 자체 Recovery Manager | 외부 Oracle DB로 복원 |

흐름:

```text
RDS for Oracle
→ RDS backup / snapshot
→ RDS for Oracle로 restore
```

```text
RDS for Oracle 또는 Oracle DB
→ RMAN backup
→ S3
→ 외부 Oracle DB, 예: EC2/온프레미스 Oracle로 restore
```

핵심:

```text
RDS로 되돌릴 백업
→ RDS backup / snapshot

Oracle 생태계에서 외부 DB로 옮겨 복원
→ RMAN
```

### Oracle RAC

RAC는 Real Application Clusters다.
여러 Oracle instance가 같은 database storage를 공유하는 Oracle 클러스터 기술이다.

```text
Oracle RAC 필요
→ RDS for Oracle 지원 안 함
→ EC2에 Oracle 직접 설치
```

왜냐하면 RAC는 OS, 스토리지, 네트워크, 클러스터 제어가 깊게 필요하기 때문이다.
RDS는 관리형 서비스라 그 수준의 제어를 제공하지 않는다.

### Oracle TDE와 DMS

```text
Oracle TDE
→ 데이터를 스토리지에 쓰기 전 DB 레벨에서 암호화

온프레미스 Oracle을 AWS로 마이그레이션/복제
→ AWS DMS
```

## RDS for MySQL 이식

RDS MySQL을 외부 MySQL로 옮기는 경우 `mysqldump` 같은 MySQL dump 도구를 사용할 수 있다.

```text
RDS MySQL
→ mysqldump export
→ 온프레미스 MySQL 또는 EC2 MySQL로 import
→ 필요하면 replication으로 동기화
→ cutover
```

시험 감각:

```text
RDS MySQL을 non-RDS MySQL로 이동
→ MySQL native dump/replication 도구 가능
```

## RDS Proxy

RDS Proxy는 애플리케이션과 RDS/Aurora 사이의 관리형 DB connection pool이다.
특히 Lambda처럼 동시에 많이 뜨는 컴퓨트와 RDS를 연결할 때 중요하다.

문제 상황:

```text
Lambda 동시 실행 급증
→ 각 Lambda가 DB connection 생성
→ RDS max connections 초과
→ too many connections
```

해결:

```text
Lambda
→ RDS Proxy
→ connection pooling
→ RDS/Aurora
```

장점:

- 유휴 연결 관리.
- connection pooling.
- IAM 인증 또는 DB 인증 지원.
- 자동 확장.
- 장애 시 애플리케이션 영향 완화.

시험 감각:

```text
Lambda가 RDS에 너무 많은 connection 생성
→ RDS Proxy
```

네트워크 감각:

```text
Private RDS/Aurora
→ 보통 VPC 내부 RDS Proxy
→ Lambda도 VPC 연결해서 접근
```

강의에서 말하는 "public Lambda가 RDS Proxy에 접근" 같은 표현은 시험에서 세부 네트워크보다 RDS Proxy의 목적, 즉 connection 관리에 초점을 두면 된다.

## RDS Cross-Region Failover

RDS cross-region read replica는 DR에 사용할 수 있지만, 장애가 나면 자동으로 writer가 되는 것은 아니다.
보통 감지와 조치를 조합해 자동화한다.

```text
Primary RDS 상태 이상
→ CloudWatch Alarm 또는 custom health check
→ EventBridge
→ Lambda
→ cross-region read replica promote
→ Route 53 DNS record update
```

중요:

```text
CloudWatch
= 감지/알람

EventBridge
= 이벤트로 Lambda 실행

Lambda
= 실제 promote / DNS update 자동화

Route 53
= 애플리케이션 endpoint 전환
```

즉 CloudWatch가 RDS를 직접 전환해주는 것이 아니다.
CloudWatch는 불난 것을 감지하고, Lambda 자동화가 실제 조치를 수행한다.

## RDS 시험용 한 줄 정리

```text
관리형 관계형 DB
→ RDS

고가용성/자동 failover
→ Multi-AZ

읽기 확장
→ Read Replica

Cross-region DR
→ Cross-region Read Replica + promotion + DNS 전환 자동화

RDS 이벤트 알림
→ SNS

SQL 쿼리 추적
→ CloudTrail이 아니라 DB engine log/audit 기능 고려

암호화 안 된 RDS를 암호화
→ snapshot copy with KMS → restore

Lambda connection 폭증
→ RDS Proxy

IAM DB Auth
→ MySQL/PostgreSQL/MariaDB, token으로 로그인, 권한은 DB 내부 관리

Oracle RAC 필요
→ RDS for Oracle 불가, EC2에 Oracle 직접 구성

Oracle RDS를 RDS로 복원
→ RDS backup/snapshot

Oracle 백업을 외부 Oracle로 복원
→ RMAN + S3

온프레미스 Oracle 마이그레이션/복제
→ AWS DMS
```

# Aurora

Aurora는 RDS 계열이지만 일반 RDS보다 클라우드 네이티브에 가깝게 설계된 관계형 데이터베이스다.
시험에서는 Aurora의 스토리지 구조, endpoint, read replica, cross-region DR, 성능 진단을 자주 묻는다.

```text
Aurora
= MySQL / PostgreSQL 호환
= 관리형 관계형 DB
= 스토리지 자동 확장
= 빠른 failover
= read replica와 reader endpoint로 읽기 확장
```

## Aurora vs DynamoDB

| 구분 | Aurora | DynamoDB |
| --- | --- | --- |
| 유형 | 관계형 DB | NoSQL key-value/document |
| 호환성 | MySQL, PostgreSQL | DynamoDB API |
| 조회 | SQL, join, transaction | key/index 기반 Query |
| 확장 감각 | Aurora storage/read replica | partition key/GSI/global table |
| Cross-region 복제 | DB 전체 복제 감각 | 테이블 단위 Global Tables |
| 사용 감각 | 관계형 모델 유지, SQL 필요 | 대규모 key-value, access pattern 명확 |

한 줄:

```text
SQL/관계형 모델 필요
→ Aurora

서버리스 NoSQL, key-value 대규모 처리
→ DynamoDB
```

## Aurora Storage 구조

Aurora의 핵심은 compute와 storage가 분리된 공유 스토리지 구조다.
스토리지는 10GB 단위로 자동 증가하고 최대 128TB까지 확장된다.

```text
Aurora Cluster
→ 3개 AZ에 걸쳐 6개 storage copy
→ 4/6 copy write quorum
→ 3/6 copy read quorum
→ self-healing
→ 자동 확장
```

시험 감각:

```text
Aurora는 기본적으로 여러 AZ에 걸친 고가용성 storage를 가진다.
일반 RDS Multi-AZ처럼 standby 하나만 따로 생각하는 구조와 다르다.
```

스토리지는 수많은 볼륨에 stripe되어 단일 장애점을 줄이고, 손상된 블록은 peer-to-peer 복제로 자가 복구된다.

## Aurora Writer와 Reader

Aurora cluster에는 writer가 하나 있고, reader replica를 최대 15개까지 둘 수 있다.

```text
Writer
→ INSERT / UPDATE / DELETE
→ SELECT도 가능

Reader replicas
→ SELECT
→ 읽기 부하 분산
```

writer 장애 시 Aurora는 빠르게 replica 중 하나를 writer로 승격한다.
강의 기준으로는 failover가 보통 30초 이내 감각이다.

시험 감각:

```text
쓰기
→ writer

읽기 확장
→ Aurora Replicas + reader endpoint

장애 시 빠른 failover
→ Aurora 장점
```

## Aurora Endpoints

Aurora endpoint는 앱이 어느 DB 인스턴스에 붙을지 정해주는 DNS 주소다.

| Endpoint | 연결 대상 | 사용 감각 |
| --- | --- | --- |
| Cluster endpoint, Writer endpoint | 현재 writer instance | 쓰기용 대표 주소 |
| Reader endpoint | Aurora replicas 전체 | 읽기 부하 분산 |
| Custom endpoint | 사용자가 고른 일부 인스턴스 묶음 | 특정 워크로드 분리 |
| Instance endpoint | 특정 DB instance 하나 | 점검/디버깅/특수 연결 |

```text
Cluster endpoint
→ writer로 연결
→ INSERT / UPDATE / DELETE / SELECT 가능

Reader endpoint
→ reader replica 중 하나로 연결
→ SELECT 전용 감각

Custom endpoint
→ 특정 reader subset만 묶음
→ 분석 쿼리를 고성능 replica에만 보내기

Instance endpoint
→ 특정 인스턴스 직통
→ 운영/디버깅/미세 조정
```

예시:

```text
일반 조회
→ reader endpoint

무거운 분석 조회
→ db.r5.2xlarge reader만 묶은 custom endpoint

쓰기/최신 읽기
→ cluster endpoint
```

주의:

```text
Reader endpoint는 연결을 reader들로 분산해주는 주소다.
SQL을 분석해서 읽기/쓰기를 자동 분리하는 마법 주소가 아니다.
앱은 쓰기용 endpoint와 읽기용 endpoint를 구분해서 써야 한다.
```

## Aurora Read Replica와 Cross-Region

Aurora read replica는 읽기 확장과 failover 후보로 사용된다.
reader endpoint를 쓰면 reader replica 위치를 앱이 직접 기억하지 않아도 된다.

Cross-region read replica는 다른 리전에 DB 전체를 복제한다.
DynamoDB처럼 필요한 단일 테이블만 골라 복제하는 감각이 아니라, Aurora database/cluster 복제 감각이다.

```text
다른 리전 read latency 감소
DR 준비
→ Aurora cross-region read replica

리전 장애
→ read replica promote
→ DNS/application endpoint 전환
```

## Aurora와 S3 Import/Export

Aurora는 S3와 직접 데이터를 주고받을 수 있다.
애플리케이션 서버가 중간에서 데이터를 읽고 다시 쓰는 구조보다 비용과 네트워크 사용을 줄일 수 있다.

```text
S3
→ Aurora로 load

Aurora
→ S3로 export
```

시험 감각:

```text
Aurora 데이터를 S3로 내보내거나 S3에서 로드
→ 앱 서버를 경유하지 말고 Aurora-S3 통합 고려
```

## Aurora Backup, Snapshot, Restore

Aurora도 RDS처럼 backup, snapshot, restore를 지원한다.

```text
PITR
snapshot
snapshot copy
restore
```

RDS와 같은 계열로 이해하면 된다.

## Aurora Logs

Aurora에서 생성되는 DB 로그는 다운로드하거나 CloudWatch Logs로 게시할 수 있다.

대표 로그:

- error log.
- slow query log.
- general log.
- audit log.

시험 감각:

```text
DB 내부 로그 확인/분석
→ Aurora logs
→ CloudWatch Logs로 publish 가능
```

CloudTrail은 AWS API 호출 추적이지, SQL 쿼리 분석 도구가 아니다.

## Aurora 성능 문제 진단

성능 문제가 나오면 도구를 구분해야 한다.

| 도구 | 보는 것 |
| --- | --- |
| Performance Insights | DB load, wait, SQL, host, user 기준 병목 |
| CloudWatch Metrics | CPU, memory, swap 등 일반 지표 |
| Enhanced Monitoring | OS/host level 세부 지표, 초 단위 지표, 프로세스 정보 |
| Slow Query Log | 느린 SQL 문 확인 |

시험 감각:

```text
어떤 SQL이 DB 부하를 만드는지
→ Performance Insights / slow query log

CPU, memory 같은 일반 지표
→ CloudWatch Metrics

DB 호스트/OS 수준의 더 자세한 지표
→ Enhanced Monitoring
```

## Aurora Serverless

Aurora Serverless는 Aurora의 서버리스 용량 모델이다.
DB 인스턴스 크기를 직접 오래 잡아두는 대신, 실제 사용량에 따라 자동으로 용량이 늘고 줄어든다.

```text
간헐적 workload
예측하기 어려운 workload
개발/테스트
사용량이 0에 가깝다가 갑자기 튀는 서비스
→ Aurora Serverless
```

핵심 감각:

```text
클라이언트
→ Aurora가 관리하는 endpoint/proxy fleet
→ 뒤에서 capacity 자동 조정
→ 같은 Aurora shared storage 사용
```

장점:

- capacity planning 부담 감소.
- 실제 사용량 기반 자동 확장.
- 초 단위 과금 감각.
- 간헐적/예측 불가 workload에 비용 효율적.

시험 감각:

```text
사용량 예측 어려움 + DB 용량 관리 최소화
→ Aurora Serverless
```

## Aurora Data API

Aurora Serverless에는 Data API를 사용할 수 있다.
JDBC connection을 직접 열고 유지하는 대신, HTTP API로 SQL statement를 실행하는 방식이다.

```text
애플리케이션
→ HTTPS Data API 호출
→ SQL statement 전달
→ Secrets Manager의 DB credential 사용
→ Aurora Serverless 실행
```

중요한 권한:

```text
애플리케이션 IAM 권한
→ Aurora Data API 호출 권한
→ Secrets Manager secret 접근 권한
```

왜 쓰는가?

```text
Lambda 같은 서버리스 앱에서
DB connection 관리가 귀찮거나 부담됨
→ Data API
```

Data API는 "DB 연결을 직접 유지하지 않는 SQL 실행 API"로 기억하면 된다.

## Aurora + RDS Proxy

Aurora에서도 RDS Proxy를 사용할 수 있다.
Data API가 HTTP 기반 SQL 실행이라면, RDS Proxy는 기존 JDBC/DB connection 방식을 유지하면서 connection pooling을 맡기는 방식이다.

```text
Lambda / App
→ RDS Proxy
→ Aurora writer 또는 reader
```

사용 감각:

```text
기존 앱 구조 유지
JDBC/DB connection 사용
Lambda connection 폭증 방지
→ RDS Proxy

JDBC 연결 자체를 덜 다루고 HTTP API로 SQL 실행
→ Data API
```

RDS Proxy에는 read-only endpoint도 만들 수 있다.

```text
쓰기
→ RDS Proxy writer endpoint
→ Aurora primary

읽기
→ RDS Proxy read-only endpoint
→ Aurora read replicas
```

시험 감각:

```text
Lambda가 Aurora에 너무 많은 connection 생성
→ RDS Proxy

서버리스 앱이 SQL을 HTTP API로 실행
→ Aurora Data API
```

## Aurora Global Database

Aurora Global Database는 글로벌 읽기 지연 시간 감소와 재해 복구를 위한 Aurora 구성이다.

```text
Primary region
→ read/write

Secondary regions
→ read-only
→ primary에서 복제
```

특징:

- primary region 1개.
- secondary region 최대 5개 감각.
- secondary region마다 read replica를 둘 수 있다.
- 복제 지연은 보통 1초 미만 감각.
- DR 시 secondary region을 promote 가능.
- RTO는 1분 미만 감각으로 설명된다.

시험 감각:

```text
글로벌 사용자에게 가까운 리전에서 읽기 제공
→ Aurora Global Database

리전 장애 시 빠른 DR
→ secondary region promote
```

## Aurora Global Database Write Forwarding

Write forwarding은 secondary region이 write 요청을 "접수"해서 primary region으로 전달하는 기능이다.
진짜 active-active multi-writer가 아니다.

```text
사용자 / 앱
→ Secondary Aurora에 INSERT/UPDATE 요청
→ Secondary가 primary로 write forwarding
→ Primary에서 실제 write/commit
→ 변경사항이 secondary로 다시 복제
```

핵심:

```text
Secondary region
= write 접수처 역할 가능

Primary region
= 실제 데이터를 변경하는 유일한 writer
```

왜 쓰는가?

```text
각 리전 앱이 자기 리전 Aurora endpoint만 바라보게 하고 싶음
→ 읽기는 secondary에서 처리
→ 쓰기는 primary로 forwarding
→ 앱이 primary endpoint를 따로 관리하는 부담 감소
```

주의:

```text
Aurora Global Database write forwarding
≠ DynamoDB Global Tables active-active write

쓰기 주인은 여전히 primary region 하나
```

시험 감각:

```text
secondary region에 들어온 write를 primary로 전달
→ Aurora Global Database write forwarding

여러 리전에서 각각 직접 write 후 충돌 조정
→ DynamoDB Global Tables 쪽 감각
```

## Aurora Global Database RPO

Aurora PostgreSQL 계열에서는 RPO 설정 관련 내용이 나올 수 있다.
핵심은 DR 상황에서 "얼마나 많은 데이터 손실을 허용할지"를 제어하는 감각이다.

```text
RPO, Recovery Point Objective
= 장애 시점에 잃어도 되는 데이터 시간 범위

RTO, Recovery Time Objective
= 장애 후 복구까지 걸리는 목표 시간
```

시험에서:

```text
Global DB + DR + 데이터 손실 목표
→ RPO

Global DB + 빠른 리전 전환
→ RTO
```

## RDS에서 Aurora로 마이그레이션

RDS MySQL/PostgreSQL 계열을 Aurora로 옮기는 대표 방식은 두 가지다.

| 방식 | 감각 | 장점 | 주의 |
| --- | --- | --- | --- |
| Snapshot restore | RDS snapshot을 Aurora로 복원 | 단순하고 빠름 | 복원 시점 이후 변경분 처리 필요 |
| Aurora read replica 후 promote | RDS의 Aurora read replica 생성 후 복제 지연이 작아지면 승격 | downtime 줄이기 좋음 | 복제 완료/cutover 관리 필요 |

Snapshot 방식:

```text
RDS
→ snapshot
→ Aurora로 restore
→ 앱 endpoint 전환
```

Replica 방식:

```text
RDS primary
→ Aurora read replica 생성
→ replication lag가 거의 0이 될 때까지 대기
→ Aurora replica promote
→ 앱 endpoint 전환
```

시험 감각:

```text
단순한 RDS → Aurora 전환
→ snapshot restore

downtime 최소화
→ Aurora read replica 생성 후 promote
```

## DynamoDB vs MongoDB 감각

둘 다 NoSQL이고 JSON성 데이터를 다룰 수 있지만 조회 철학이 다르다.

```text
MongoDB
= 여러 필드로 find 가능
= 인덱스 없으면 collection scan으로 느려짐

DynamoDB
= Query 자체가 key/index 기반
= 인덱스 없는 속성 조회는 Scan
```

DynamoDB는 "조회 패턴을 먼저 정하고 키/인덱스를 설계하는 DB"에 가깝다.

## DynamoDB 시험용 한 줄 정리

```text
서버리스 NoSQL, 대규모 key-value/document 조회
→ DynamoDB

item 400KB 초과
→ S3에 저장하고 DynamoDB에는 reference

예측 불가 트래픽
→ On-demand

예측 가능하고 비용 최적화
→ Provisioned + Auto Scaling

특정 속성으로 자주 조회
→ GSI/LSI 설계

테이블 생성 후 인덱스 추가
→ GSI

같은 partition key 안의 다른 sort key
→ LSI

item 변경 이벤트 처리
→ DynamoDB Streams + Lambda

Streams 24시간보다 긴 보존/분석
→ Kinesis Data Streams 연동

멀티 리전 active-active
→ Global Tables

Global Tables 충돌
→ last writer wins

DynamoDB read 캐시/hot key 완화
→ DAX

무거운 계산 결과 캐시
→ ElastiCache

S3 객체 검색용 metadata index
→ S3 event + Lambda + DynamoDB
```
