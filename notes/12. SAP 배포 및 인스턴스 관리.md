# SAP 배포 및 인스턴스 관리

# 큰 그림

섹션 12는 "애플리케이션과 인스턴스를 어떻게 배포하고 운영할 것인가"를 묻는 파트다.
시험에서는 직접 EC2에 들어가서 작업하는 방식보다, 관리형 배포/운영 도구를 고르는 문제가 자주 나온다.

```text
애플리케이션 배포 플랫폼
→ Elastic Beanstalk

배포 전략과 트래픽 전환
→ CodeDeploy

인프라를 코드로 관리
→ CloudFormation / CDK / SAM

승인된 템플릿을 셀프서비스로 제공
→ Service Catalog

운영 작업, 패치, 세션 접속, 파라미터 관리
→ Systems Manager

동적 서비스 검색
→ AWS Cloud Map
```

# Elastic Beanstalk

Elastic Beanstalk는 애플리케이션 코드를 올리면, 뒤의 EC2, ASG, ELB, 배포, 모니터링을 대신 구성해 주는 PaaS 성격의 서비스다.

시험 감각:

```text
개발자는 코드만 배포하고 싶다
인프라 세부 구성은 AWS가 관리해줬으면 한다
그래도 EC2/ALB/ASG 같은 리소스는 내 계정에 만들어져야 한다
→ Elastic Beanstalk
```

중요한 점은 Beanstalk가 완전 서버리스는 아니라는 것이다.
내부적으로 EC2, 로드 밸런서, 오토 스케일링 그룹 같은 리소스를 만든다.

배포 정책도 시험 포인트다.

| 배포 방식 | 감각 |
| --- | --- |
| All at once | 가장 빠르지만 장애 시 전체 영향 |
| Rolling | 일부 인스턴스씩 교체, 용량이 일시적으로 줄 수 있음 |
| Rolling with additional batch | 새 배치를 추가해서 용량을 유지하며 교체 |
| Immutable | 새 인스턴스를 따로 띄운 뒤 검증 후 교체, 더 안전하지만 느리고 비용 증가 |
| Blue/Green | 새 환경을 따로 만들고 DNS/CNAME을 전환 |

시험에서 "가장 안전한 배포", "기존 환경을 건드리지 않고 새 버전 검증"이 나오면 immutable 또는 blue/green을 본다.

# CodeDeploy

CodeDeploy는 애플리케이션 버전을 EC2, 온프레미스 서버, Lambda, ECS에 배포하는 서비스다.
Elastic Beanstalk가 전체 애플리케이션 플랫폼에 가깝다면, CodeDeploy는 "배포 전략" 자체에 집중한다.

```text
EC2 / On-premises
→ CodeDeploy agent 필요
→ in-place 또는 blue/green 배포

Lambda
→ alias/version 간 트래픽 전환
→ canary / linear / all-at-once

ECS
→ blue/green 배포와 ALB target group 전환
```

EC2 배포에서 핵심 파일은 `appspec.yml`이다.
어떤 파일을 어디에 복사할지, 배포 전후 어떤 hook을 실행할지 정의한다.

시험 감각:

```text
배포 중 lifecycle hook 실행
Lambda 새 버전에 10%만 먼저 보내고 검증
ECS 서비스를 blue/green으로 전환
온프레미스 서버까지 같은 방식으로 배포
→ CodeDeploy
```

# CloudFormation

CloudFormation은 AWS 인프라를 템플릿으로 선언하고, stack 단위로 생성/수정/삭제하는 IaC 서비스다.

시험에서 중요한 포인트:

- 인프라 변경 전에 Change Set으로 실제 변경 내용을 확인할 수 있다.
- Drift Detection으로 템플릿과 실제 리소스 상태가 달라졌는지 확인할 수 있다.
- StackSets로 여러 계정/여러 리전에 같은 스택을 배포할 수 있다.
- Nested Stack으로 공통 인프라 조각을 재사용할 수 있다.
- DeletionPolicy로 스택 삭제 시 리소스를 보존할 수 있다.

시험 감각:

```text
인프라를 반복 가능하게 배포
여러 계정과 리전에 동일한 리소스 배포
템플릿과 실제 리소스의 drift 확인
→ CloudFormation
```

# Service Catalog

Service Catalog는 관리자가 승인한 인프라 템플릿을 사용자에게 셀프서비스 카탈로그로 제공하는 서비스다.

핵심은 "사용자에게 AWS 전체 권한을 주지 않고도, 승인된 제품만 만들게 한다"는 점이다.

```text
관리자
→ CloudFormation 기반 product/portfolio 정의

사용자
→ 카탈로그에서 승인된 product만 launch
```

시험 감각:

```text
개발팀이 표준 VPC/EC2/RDS 구성을 직접 만들게 하고 싶다
하지만 IAM 권한을 넓게 주면 안 된다
조직에서 승인한 템플릿만 셀프서비스로 쓰게 하고 싶다
→ AWS Service Catalog
```

# SAM, Serverless Application Model

SAM은 서버리스 애플리케이션용 CloudFormation 확장이다.
Lambda, API Gateway, DynamoDB 같은 서버리스 리소스를 더 짧은 문법으로 정의한다.

```text
SAM template
→ CloudFormation으로 변환
→ Lambda/API Gateway 등 배포
```

시험 감각:

```text
서버리스 앱을 IaC로 정의
Lambda/API Gateway를 로컬에서 테스트하고 배포
→ AWS SAM
```

# CDK, Cloud Development Kit

CDK는 TypeScript, Python, Java 같은 프로그래밍 언어로 인프라를 정의하고, 최종적으로 CloudFormation 템플릿을 생성한다.

```text
CDK code
→ synth
→ CloudFormation template
→ CloudFormation stack
```

시험 감각:

```text
개발자가 익숙한 언어로 인프라를 작성하고 싶다
반복문/조건문/재사용 가능한 construct를 쓰고 싶다
하지만 실제 배포 엔진은 CloudFormation이다
→ AWS CDK
```

# Systems Manager, SSM

SSM은 EC2와 온프레미스 서버를 중앙에서 운영하는 서비스다.
시험에서는 "SSH 없이 접속", "대량 패치", "명령 일괄 실행", "운영 자동화", "파라미터/비밀 관리"가 키워드다.

SSM을 쓰려면 보통 다음이 필요하다.

```text
대상 인스턴스
→ SSM Agent 설치/실행
→ 인스턴스 프로파일에 SSM 권한
→ SSM endpoint 접근 가능
   Public internet / NAT / VPC Interface Endpoint
```

주요 기능:

| 기능 | 시험 감각 |
| --- | --- |
| Session Manager | SSH key나 bastion 없이 인스턴스 접속 |
| Run Command | 여러 인스턴스에 명령 일괄 실행 |
| Patch Manager | OS 패치 자동화 |
| State Manager | 원하는 상태 유지 |
| Automation | 운영 작업 runbook 자동화 |
| Inventory | 인스턴스 소프트웨어/설정 수집 |
| Parameter Store | 설정값/비밀값 저장, KMS 암호화 가능 |

시험 감각:

```text
SSH 포트를 열지 않고 EC2에 접속
여러 EC2에 명령을 동시에 실행
온프레미스 서버까지 관리
패치 상태를 중앙에서 관리
→ AWS Systems Manager
```

# AWS Cloud Map

Cloud Map은 동적으로 변하는 리소스를 이름으로 찾게 해주는 서비스 디스커버리다.

예를 들어 컨테이너나 EC2 인스턴스가 계속 늘고 줄면 IP가 바뀐다.
Cloud Map에 서비스 인스턴스를 등록해두면 애플리케이션은 이름으로 현재 정상 리소스를 찾을 수 있다.

```text
서비스 인스턴스 등록
→ Cloud Map
→ DNS 또는 API로 discovery
```

시험 감각:

```text
마이크로서비스가 동적으로 늘고 줄어든다
서비스 이름으로 현재 엔드포인트를 찾고 싶다
ECS/EKS/EC2 기반 서비스 discovery가 필요하다
→ AWS Cloud Map
```
